Found by the planner-side cross-vendor review of PR #1160 at fd8bfdc947bb (store-sqlite reviewer): P2, confirmed. The owner deferred it to after the #1160 merge (2026-10-09); fix it on integration/beta-next.

**Finding.** Automatic native checkpoints copy the full current native row set every ~4 calls into an undeletable table, so checkpoint storage and open-time verification grow quadratically

**Where.** `crates/platform/chio-store-sqlite/src/admission_operation_store/security_participant_state/checkpoint/cadence.rs:6` (introduced by 5ec396fd5)

**Scenario.** The kernel calls checkpoint_native_security_history_if_due on every native egress; a checkpoint is due every 20 journal events (about 4 calls). Each checkpoint copies every current native row (up to 65,537 via LIMIT) into security_participant_checkpoint_rows, which has a no-delete trigger and no pruning. Because the current row set grows linearly with traffic (see the 65,536-row cap finding), retained checkpoint rows grow as O(K^2) in the number of checkpoints, each checkpoint holds the write lock for an O(current rows) copy, and checkpoint::verify_all at open rescans every retained snapshot.

**Evidence at fd8bfdc.** checkpoint/cadence.rs:6 'const EVENTS_BETWEEN_CHECKPOINTS: u64 = 20;'; checkpoint/rows.rs:92-125 'SELECT {columns} FROM {} WHERE security_authority_id = ?1 ORDER BY {columns} LIMIT 65537' then insert.execute per row; checkpoint/schema.sql 'security_participant_checkpoint_rows_no_delete' RAISE(ABORT, 'native checkpoint snapshot is immutable'); checkpoint.rs:364-375 verify_all visits every checkpoint's rows.
