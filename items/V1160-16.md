**Finding.** Reference MCP tool line reader rejects an exactly-4-MiB request and silently swallows the next request line

**Where.** `crates/tooling/chio-reference-tools/src/lib.rs:153` (introduced by 8b9f92439)

**Scenario.** A client (the Chio stdio MCP adapter forwarding an agent tools/call whose arguments are sized so the serialized JSON-RPC line is exactly MAX_LINE_BYTES = 4,194,304 bytes) writes that line plus '\n'. read_line reads MAX_LINE_BYTES + 1 bytes, which includes the terminating newline, so buffer.len() > MAX_LINE_BYTES and the line is treated as oversized even though it is complete. The discard loop then reads and drops the NEXT complete line from stdin (for example the adapter's notifications/cancelled or the next request). The tool answers the first line with a parse error carrying id null, so the adapter waits out its request deadline and terminalizes the connection. Any line queued after it is lost with no response. Result: an off-by-one (a maximum-length line is refused, contrary to the MAX_LINE_BYTES doc) and a framing desync on the reference tools' stdio boundary.

**Evidence at fd8bfdc.** lib.rs:19 `pub const MAX_LINE_BYTES: usize = 4 * 1024 * 1024;` /// The longest request line accepted. lib.rs:154 `let read = Read::take(&mut *input, MAX_LINE_BYTES as u64 + 1).read_until(b'\n', buffer)?;` lib.rs:158 `if buffer.len() > MAX_LINE_BYTES {` (no check that buffer already ends with '\n') lib.rs:159-166 `loop { discard.clear(); let read = Read::take(&mut *input, MAX_LINE_BYTES as u64).read_until(b'\n', &mut discard)?; if read == 0 || discard.last() == Some(&b'\n') { break; } }` consumes the following line. The adapter writer (chio-mcp-adapter/src/transport/utils.rs:221 send_line) does not cap outbound line length, and mcp-edge ingress admits up to 8 MiB, so a 4 MiB request can reach the tool.
