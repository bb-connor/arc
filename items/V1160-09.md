**Finding.** Rekor witness publish and verify reject a freshly integrated entry when the local clock lags Rekor, with no skew allowance

**Where.** `crates/economy/chio-anchor/src/witness/rekor.rs:142` (introduced by a2630c20a)

**Scenario.** This PR added RekorClient::validate_time, which rejects any integrated_time greater than local now (rekor.rs:142-143). publish calls it on the entry Rekor has just integrated (rekor.rs:718), and verify_inclusion also calls it (rekor.rs:790). Rekor sets integratedTime from its own clock in whole seconds. If the host clock lags Rekor by more than the response latency (for example 500 ms behind with 100 ms latency), publishes that land near a second boundary see integrated_time = local_secs + 1 and return NotYetValid. The entry is already appended to the log, yet publish returns an error and no WitnessReceipt is produced. The previous code only checked staleness and treated future timestamps as fresh. Plausible follow-on, not traced against a live Rekor: a retry submits the identical canonical DSSE entry (deterministic Ed25519 signature over the same batch), Rekor answers 409 Conflict, and input::response maps any non-2xx to AnchorWitnessError::Http. The batch could then never get a witness receipt.

**Evidence at fd8bfdc.** rekor.rs:137-151 `fn validate_time(&self, published_at: i64)` ... `if published_at > now { return Err(ClockError::NotYetValid.into()); }`; rekor.rs:718 `self.validate_time(entry.integrated_time)?;` in publish after the entry is logged; rekor.rs:790 same in verify_inclusion; rekor/clock.rs:29 `reading.unix_millis().as_secs()` (local whole seconds); rekor/input.rs `if !status.is_success() { return Err(AnchorWitnessError::Http { ... }) }`.
