**Finding.** Federated capability issuance checks expiry against a clock reading taken before the leader-forward await

**Where.** `crates/platform/chio-control-plane/src/trust_control/passport_handlers.rs:1061` (introduced by a76864ad1)

**Scenario.** Cluster mode: a follower receives POST /v1/federation/capabilities/issue and reads clock_now. forward_post_to_leader then makes up to two blocking POSTs to the leader, each bounded by the 15 s control HTTP timeout. If the old leader hangs, both can time out. update_peer_failure re-elects, and when next_leader == self_url forward_post_to_leader returns Ok(None), so the follower handles the request locally with `now = clock_now`, up to about 30 s stale. A delegation policy, presentation challenge, passport credential or lifecycle record that expired during that window still passes ensure_federated_delegation_policy_active, the presentation verification and consume_challenge_if_configured, and a federated capability is issued. origin/main read the clock after the forward.

**Evidence at fd8bfdc.** passport_handlers.rs:1061-1064 `let clock_now = match unix_timestamp_now() {...}` before :1068 `match forward_post_to_leader(&state, FEDERATED_ISSUE_PATH, &payload).await { ... Ok(None) => {} ...}`; :1081 `let now = clock_now;` then :1084 `ensure_federated_delegation_policy_active(policy, now)`; report_rendering.rs:276 `for _ in 0..2 {` and :313-315 `if next_leader == self_url { return Ok(None); }`; origin/main passport_handlers.rs:1000 forward then :1013 `let now = unix_timestamp_now();`. A lower-impact copy of the same pattern is in authority_handlers.rs handle_evaluate_federation_policy.
