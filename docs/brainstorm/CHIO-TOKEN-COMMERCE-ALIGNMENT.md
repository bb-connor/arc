## 2. The commerce architecture in one page (the primitives the plans must respect)

These are SHIPPED on `chio/autonomous-commerce-brainstorm` (130+ commits past `main`). Treat each as the
authority the plans bind to.

- **Transaction/settlement passport + proof-room anchoring.** `chio.transaction.passport.v1` is a signed root over a typed DAG (`chio.transaction.evidence-graph.v1`, 55 node roles); `chio.web3-settlement-proof-bundle.v1` is a strict composition with a fail-closed verifier that RECOMPUTES chain state. Anchoring is the SAME RFC6962 substrate for settlement passports, transaction-graph checkpoints, AND Pass issuance/revocation: `ChioRootRegistry.publishRoot`/`publishRootBatch` + `verifyInclusionDetailed`, with the anchor-batch family (`chio-anchor/src/batch.rs` `AnchorBatch::sign`; `bundle.rs` emitting `chio.anchor-proof-bundle.v1`/`chio.anchor-inclusion-proof.v1`/`chio.checkpoint_statement.v1`). Producer/explorer-"witnessed" state is a display aid, never proof (draft 05). One transaction root; one `chio proof` namespace; evidence classes asserted/observed/verified never collapse (draft 07).

- **Trust-market claims + settlement trust roots.** Provider trust assertions (passport verdict, portable reputation scorecard, federation admission, runtime/SPIFFE appraisal) are now VERIFIED and digest-bound into the order context before exposure and settlement ("bind commerce proofs to trust market context"). Settlement trust roots are the digest chain `passport -> bid -> selection -> quote -> approval/mandate -> budget hold -> payment verification -> fulfillment -> settlement packet`, aggregated into an `order-passport` and anchored in `ChioRootRegistry`. Receipts/claims verify against externally-pinned market authority keys (RR2-TM-01).

- **Risk-comptroller / facility-insurance capital model.** `chio.risk.comptroller-report.v1` is a deterministic, replayable projection over signed artifacts (facility-state, coverage, reconciliation, reserve, sanction, appeal, capital-instruction, actuarial-backtest). Hard invariants: capital instructions are custody-neutral INTENT (`intended_state=pending_execution / reconciled_state=not_observed`), external movement proven only by payout/settlement/web3 receipts; the pre-observed gate fails closed (`lib.rs:964` `risk payout preobserved instruction`); every `market_slash` reserve entry carries a `RiskSanctionBridge` and passes the double-consumption guard (`ledger.rs:61` `risk reserve double consumption`); claim-payout-priority over punitive slash and open-appeal holds are enforced (`RiskClaimAppeal`, `lib.rs:42,215,1046,1109`); premium pricing is a deterministic compliance-score band, NOT actuarial (`validate_risk_actuarial_limits`, `lib.rs:764`); the capital book fails closed on mixed currency, contradictory counterparty, or more than one live facility/bond (multi-source senior/first-loss/insurer/reinsurer/custodian roles are doc-06 Phase 6). Chio is NOT a regulated insurer/custodian/actuarial pricer; a licensed partner is principal/issuer of record for any external execution.

- **Provider admission + selection.** Folded, not standalone: `ProviderDiscoverySnapshot -> ProviderSelectionReport -> TrustScorecardSnapshot` (+ `ReputationImportReport`) in `chio-trust-market-context/src/artifacts.rs`. `validate_selection` binds selection to passport/order/discovery ids; selected subject must be present/available/fresh; ranking score must equal scorecard `computed_score`. `validate_reputation_import` enforces trusted issuer, accepted `import_verdict`, subject binding, capped `local_weight`, and that portable reputation CANNOT prove collateral or solvency. This is the attested-identity anti-farm substrate to REUSE, not duplicate.

- **Swarm authority / delegation.** `SwarmTaskGraph` is a signed upper bound; each hop carries a `SwarmDelegationWitnessChain` (subset proof); authority travels in a pinned-witness-key-signed `SwarmContinuationToken` bound to graph/route-plan/revocation epoch+root/nonce/audience/subject/mode. `verify_capability_full` still runs for side-effecting dispatch. Budget fan-out/fan-in reconciles at terminal receipt. Unknown is deny (`chio-swarm-authority/src/verifier.rs`; `spec/PROTOCOL.md` §6.3.2).

- **Lineage-disclosure privacy.** `chio-disclosure-lineage/src/verifier.rs`: signatures verify only against pinned `TRUSTED_LINEAGE_SIGNER_PUBLIC_KEYS` (`:22,412`); lineage roots must be bound; node/edge/evidence kinds are enumerated allowlists; a `DisclosureLeakageLedger` is mandatory even when empty (`validate_leakage_ledger`, `:664`); required derived facts `issuer_status`/`revocation_freshness`/`presentation_timing` must be accounted (`REQUIRED_DISCLOSURE_DERIVED_FACTS`, `:54`); sensitive identifiers (tenant, seller, capability) are hashed. Gifting "own receipts/lineage" uses a signed lineage-subgraph export scoped by a verifier privacy profile + leakage ledger, never full evidence export (`receipts.ndjson` / full capability snapshots are admin-only, `admin_full_evidence_v1`). Excess disclosure is a privacy failure even when crypto verifies.

### C1 [BLOCKING] Parallel slash authority duplicates the shipped sanction/reserve ledger

- Plan location: token plan Sec 3 line 48 (`ChioSlashableBondVault.impairBondDetailed`) and Sec 4 lines 70-72, 75 (`chio-reputation` emits `SlashInstruction`; `chio-federation` gates; `chio-revocation-oracle` gossips; new `chio-web3` relayer executes). Research doc Sec 3.3 / rec #6 / Sec 7.2 follow-up #4 ("permissionless clear-and-route", `clearBurnOrRedistributableShares` into an immutable `redistributionRecipient`). Benevolent doc M4 (`ChioSlashableBondVault` anchors issuer independence).
- Commerce feature it conflicts with: `chio.risk.comptroller-report.v1` sanction/reserve ledger + `RiskSanctionBridge` + double-consumption guard + pre-observed capital-instruction gate (`chio-risk-comptroller/src/lib.rs:182,257,260,964`; `ledger.rs:61,89-167`). The architecture map declares the comptroller IS the single slash lane. A `SlashInstruction` + `ChioSlashableBondVault.impair` that does not bind into the reserve ledger is a second, unbound slash authority; a permissionless atomic route is an OBSERVED execution by a non-partner caller, which the pre-observed gate fails closed on.
- **Direct answer to the call-out: yes, the token plan's Phase-2 bond/slash design duplicates the existing risk-comptroller design.** It is a duplication/under-binding, not a hard-boundary contradiction (the plan is correct on single-currency USDC, custody-neutral intent vs observed execution, and partner-as-principal). The fix is binding, not redesign.
- Fix: Reframe the slash path as `SlashInstruction -> signed transfer_funds capital instruction (pending_execution / not_observed, no observed_execution_ref) -> ChioSlashableBondVault.impair as the on-chain OBSERVED-execution leg -> recorded as a RiskSanctionReserveLedgerEntry (lane market_slash) bound by a RiskSanctionBridge (authority_receipt_ref / evidence_ref / jurisdiction_ref / sanction_subject / maximum_slash_units)`, passing `validate_risk_sanction_reserve_ledger` and the double-consumption guard. Add claim-payout-priority-over-punitive-slash ordering and open-appeal holds via the realized `RiskClaimAppeal`. Bind the slasher role to the trust-market `slash_authority_ref` -> jurisdiction `slash_authority_refs` + `collateral_slash` dispute type (`chio-trust-market-context/src/artifacts.rs`) and the `claim.market.slashing_court_operated` claim, not a free-standing role. The relayer is prepare-only, executed only by the licensed-partner signer.

## 4. Integration points (how Pass / token gate / contracts connect to commerce primitives)

These are the explicit wirings. C-prefixed items above are the blocking versions; the items here state
the positive target shape.

- **Pass capability tokens flow through the same kernel/receipt/swarm path commerce uses.** A Pass-minted `CapabilityToken` (subject-bound DPoP, `ToolGrant{max_total_cost,...}` for compute, `ResourceGrant{operations:[Read,Subscribe]}` for feeds) is metered by the SAME kernel `budget_store` that gates the commerce order-context `budget_reserved` gate. Therefore: (a) the synthetic `freetier:global:<window_ym>` pool term MUST be namespace-isolated so aggregate budget projections and the risk-comptroller reserve view never count a free-tier row as a real capability/commerce budget hold; (b) if a Pass holder delegates compute to swarm children, the swarm budget lease/fan-out MUST co-debit the `freetier:global` pool and every child capability MUST carry a `SwarmDelegationWitnessChain` attenuation witness (no witness = deny). Recursive Pass-compute delegation is out of M0; wire the pool co-debit in Phase 1 so a swarm cannot bypass the POOL ceiling. `verify_capability_full` still runs; the Pass is evidence, not a verifier.

- **Pass anchoring reuses the proof-room/passport Merkle anchoring (it does NOT duplicate it).** Direct answer to the call-out: the Pass anchoring does NOT duplicate the transaction-passport/proof-room anchoring; it is the SAME mechanism at the anchoring primitive (`ChioRootRegistry.publishRoot`/`verifyInclusionDetailed` + the anchor-batch family), differing only in leaf semantics (a credential-lifecycle set vs a per-transaction DAG vs settlement receipts). The Pass is a SUBJECT/identity node (`agent_passport` / reputation-credential class) eligible as a `subjectRef` in transaction and settlement evidence graphs, and is NEVER the transaction-passport root. Two binding requirements: (a) the M0 anchoring API path must wrap the `AnchorBatch` tree root into a `KernelCheckpoint` with a strictly-increasing per-operator `checkpoint_seq` and obtain a `SignedWeb3IdentityBinding` carrying `Web3KeyBindingPurpose::Anchor` + target chain in `chain_scope` + `settlement_address == operator_address`, matching `prepare_root_publication` (`chio-anchor/src/evm.rs:119-128`); the M0 spec Sec 3.4 as written would not compile against it. (b) The reused anchor schemas `chio.anchor-inclusion-proof.v1` / `chio.anchor-proof-bundle.v1` are now registered (registry.json + `KNOWN_SIGNED_ARTIFACT_SCHEMAS`, R-T05-16 closed at HEAD); the Pass introduces NO new signed-artifact schema. The VC credential family `chio.agent-passport.v1` correctly need not register in `KNOWN_SIGNED_ARTIFACT_SCHEMAS`.

- **Pass distribution reuses the provider-admission attested-identity substrate.** Bind Pass issuance / portable-reputation eligibility to `chio-trust-market-context::validate_reputation_import` (trusted issuer, accepted `import_verdict`, `subject_binding_ref`, `privacy_profile_ref`/`decay_policy_ref`, capped `local_weight`, CANNOT prove collateral or solvency) and to discovery-snapshot membership + signed `ProviderSelectionReport`/`TrustScorecardSnapshot`, rather than re-deriving the gate from `chio-reputation/tier.rs` + `chio-federation` alone. This enforces the benevolent doc's own goal (reputation must NOT unlock economic authority / bond discount) at the verifier layer. Reconcile the Pass `TrustTier` with the scorecard `computed_score` so two tier notions cannot fork.

- **Bonds reuse the risk-comptroller facility model.** The Phase-2 insurance/underwriting pool and bond economics surface through the comptroller report the order context ALREADY consumes: `CommerceCoverageRequirement` carries `risk_comptroller_report_ref`/`sha256`/`path` and `RISK_COMPTROLLER_REPORT_SCHEMA_ID = chio.risk.comptroller-report.v1` (`chio-commerce-order/src/types.rs:13-16`; `lib.rs:46-47`). Coverage/bond economics are not separate from commerce settlement; they feed this binding. Disambiguate two bond purposes as separately-ledgered instruments: operator-admission/Sybil STAKE bonds (the plan's Phase-2 bonds) vs reserve/collateral bonds backing facility/coverage (`chio-credit` lock/hold/release/impair), so admission-stake slashing can never consume claim-reserve.
