# Foundation acceptance scope

The [landing ledger](landing-ledger.md) owns the requirements and landing order.
This document defines what qualifying #1160 can establish. It does not declare
the candidate qualified, close an original finding, or change its acceptance
criteria. The preserved archive retains the full source and historical evidence.

## Ruling: review coverage and requirement completion are separate

An included source owner requires review before foundation landing. Its presence
does not make every product or hardening requirement a completed foundation
feature. The earlier assignment of 126 named findings to foundation review was
an ownership assignment. Each finding still needs its own source repair,
verification evidence and remaining acceptance in the ledger.

This follows the requested sequence: land a qualified process/security
foundation, then execute small hardening and product-evidence waves. Confirmed
authorization defects and failures of the selected native isolation, custody or
qualification contract block the foundation. Known limitations outside those
claims remain open with concrete follow-up acceptance. They cannot be reported
as fixed because a containing branch reaches `main`.

If later source or execution evidence shows that a deferred finding violates the
selected foundation contract, it returns to the blocking repair queue. This
ruling cannot waive required checks, native enforcement, trusted provenance,
independent review, protected merge rules or a confirmed P0/P1 defect.

## Required foundation boundaries

| Boundary | Acceptance before landing |
| --- | --- |
| Dependency and build trust | Genuine exact upstream/fork audit coverage; reviewed dependency closure and trusted definitions on `main`; no audit exemption or check bypass. |
| Capability authority | Caller-owned subjects, issuer lifecycle and expiry, signed security constraints, approval/replay binding, and fail-closed refusal where a constraint or assurance mode cannot be enforced. |
| Kernel and durable process execution | Preserve both histories and later repairs. Verify the selected admission, effect, cancellation, recovery, receipt and durable authority boundaries in the final source composition. |
| Native isolation and custody | Aggregate child transport bounds, bounded stderr reads, wiping secret ownership, supported native enforcement and failure controls. Synthetic fixtures cannot replace required native evidence. |
| Existing evidence assertions | Preserve signed source and independent trust checks. Remove unsupported Wrap verification/persistence claims and require independently pinned authentic receipts before paging. |
| Candidate identity | Exact reviewed source, immutable inputs, required hosted checks, real native/trusted capture and protected merge ancestry must agree. |

The dependency-ordered packet reports are preparatory source reviews. Their
inventories are review navigation, not an assertion that every line, constructor,
feature combination or deployment has been independently qualified. Their
findings and stated limits are retained in
[`foundation-packet-reviews-20261004.json.gz`](audits/foundation-packet-reviews-20261004.json.gz).

## Explicit remaining acceptance

component results, independent reviews and original failures belong in the
[landing ledger](landing-ledger.md). These source changes still require complete
owning checks and exact-candidate native, trusted and hosted qualification before
foundation acceptance. The two implementation plans retain the dependency order
and verification obligations:
[production readiness](../superpowers/plans/2026-10-05-production-readiness-closeout.md)
and [evidence/product repairs](../superpowers/plans/2026-10-05-evidence-product-closeout.md).

- EV3/EV4 now have a kernel-owned, nonauthorizing refusal recorder and real MCP
  capability-prefilter/authenticated restricted-session hooks. Host-only commands
  retain the original ingress reservation, acknowledge actual persistence and
  yield to cancellation and the owned deadline within a bounded drain. Anonymous
  invalid or unknown credentials remain outside this session-scoped contract.
  A refusal never establishes dispatch, nonce consumption, settlement or a
  successful persistence result after a store failure.
- ACP FullBundle v2 commits the exact ordered supplied receipt set and the
  configured profile. Full verification rejects absent or empty bundles and
  validates the set, count, signer, session, sequence and time bounds. Its portable
  retained-snapshot description does not independently prove store completeness.
  The CLI independently recollects the actual sealed read-only retained corpus
  for its stronger retained-snapshot check. Neither establishes whole-lifetime
  session closure, child inclusion proofs or monetary-spend proof. With no profile,
  scope and guard claims remain NotEvaluated.
- Ordinary SIEM receiver, retry and dead-letter paths use a bounded sink
  projection without the original free-form payload. Paging independently
  authenticates the original receipt with the accepted signer pin. Exporter
  delivery, receiver custody and operational retention still need their own
  acceptance.
- Strict CLI wrap (`--strict-execution-nonce`) and API Protect install the shared
  default guard profile and bind its identity to their policy. Strict wrap
  observes its tool output and applies the post pipeline; plain wrap remains
  manifest pass-through. The default velocity thresholds are unset and the
  advisory roster is empty. API Protect's caller-execution reservation observes the applicable
  pre-invocation boundary; it does not observe the caller's later external HTTP
  response. Optional guards and unsupported assurance modes remain explicit.
- Terminal raw-envelope maintenance is opt-in and owned by the existing local
  serving authority. Its bounded page and replay contract must pass the complete
  ownership, sidecar-byte, fencing, signing-floor and restart controls before
  acceptance. Unsupported replay profiles and live/resolved shared owners are
  held. This is not universal payload erasure: retained admission/context data,
  other payload owners, WALs, backups and already delivered outputs remain outside
  this contract. No existing user database is migrated or compacted by these tests.

The ledger also retains the following follow-up boundaries:

- Complete-history/session-closure and independent child inclusion proofs,
  universal payload retention/erasure and actual exporter delivery retain their
  dedicated acceptance. Receipt archival or a portable set commitment does not
  establish those properties.
- Historical tenant scans and provider identity lookup retain their storage and
  trust acceptance. Suspension discovery and report aggregation now have bounded
  reads, selected canonical-projection checks and propagated lineage failures.
  These report diagnostics do not prove externally authenticated exclusion
  completeness or independent kernel trust.
- Adapter task-registry durability and remaining consumer obligations retain
  their acceptance. The current batch repairs unsigned A2A numeric compatibility,
  native diagnostic provenance and configured guard credential custody; earlier
  source repairs cover discovery allocation, recursive readers and manifest
  documentation. Complete owning/platform verification remains required. Mobile
  component evidence below does not establish every device or consumer ABI.
- Type-level API closure, complete reader census, resource-scale campaigns,
  platform matrices and operational rollout remain distinct acceptance. A local
  focused pass does not supply any missing evidence.

These are concrete unclosed findings or unexecuted obligations, not assurances
that those APIs are production-qualified. Each original source requirement stays
in the ledger, including its history and the acceptance needed to close it.
Follow-up PRs receive a queue slot sequentially after the prerequisites and
foundation. Workbench, funded-work, research and Mercury proof development remain
separate tracks.

A foundation merge establishes only the reviewed and executed foundation
contract for its named source and supported profile. It is not full roadmap
completion, hardware quote verification, a FIPS-validated executable, complete
compliance evidence, an enabled automatic response deployment, release readiness
or pilot acceptance. The original roadmap gates remain authoritative for those
claims.
