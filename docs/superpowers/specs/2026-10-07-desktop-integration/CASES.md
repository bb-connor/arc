# Cases

Single source for every acceptance case in the native host program. Flows are
defined in [NORTH-STAR-FLOWS](NORTH-STAR-FLOWS.md). A case is executable only
when its owner gate exists.

Each row condenses the definition that QUALIFICATION (Q), CONSUMERS (C) and
FIRST-CLASS-INTEGRATIONS (H) carried at commit `620c703d8`. That full stimulus
and oracle text stays the acceptance detail for the row until the owner's
executable case manifest replaces it. Milestones are HOST-M1, HOST-M2 and
HOST-M3 (NORTH-STAR-FLOWS sections 3 to 5) and Platform (section 6). macOS
cells of HOST-M2 rows are deferred until after the success test (unified
roadmap section 11).

Rules for every row:

- A case is a test obligation, not a claim that the test exists or passes.
  Put the executable test in the named owner.
- Pair every negative with a useful positive control. A denial-only system
  cannot pass.
- Observe negatives independently of client status and signed claims: the
  actual resource, dispatch or effect counter, private-byte canary, ledger or
  native process census.
- "Applicable" never omits a case silently. The executable manifest names each
  owner-approved exclusion and its reason; an unclassified case fails.
- C09 and Q24 apply when passports are advertised or required by peer policy,
  C10 and Q25 when recursive authority is exposed, C11 and Q26 when runtime
  swarm admission is exposed, and Q31 wherever time-bounded authority or
  evidence is consumed.
