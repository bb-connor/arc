# VM and remote project execution

Status: Proposed normative design. Confidence: high in the inspected platform/source gaps; moderate in this architecture; unknown in installed enforcement until the acceptance matrix passes. No current Mac VM implementation or qualified profile is claimed. Source baseline and direct Apple references are in [Apple platform research](research/apple-platform.md).

## Outcome and authority boundary

`vm-project-v1` runs arbitrary project tools in a local Linux VM while a host Rust kernel admits every host-resource and external effect. The first useful job imports one committed tree, executes a portable fixed test recipe, and returns a staged diff/artifact. [Resource publication](10-project-resources.md) separately gates release and `publication-v1`. The operator, kernel and credentials remain outside the guest. [Kernel contracts](03-kernel-contracts.md), [authority integrity](04-authority-integrity.md), [host architecture](05-host-architecture.md), [operator protocol](06-operator-protocol.md) and [recovery](11-state-recovery.md) govern shared semantics.

| Profile | Execution location and boundary | Independent gate |
| --- | --- | --- |
| `vm-project-v1` | Local architecture-matched Linux VM with no direct network device; bounded host resource channel | Virtualization entitlement; measured guest/host configuration, lifecycle and adversarial probes |
| `remote-project-v1` | Declared remote worker and its own serving authority/brokers | Explicit export and placement; independently qualified remote launch, authority, identity and stop/recovery |
| `native-descendant-v1` | Native Mac descendant worker | [ES](08-endpoint-security.md), [NE](09-network-extension.md), supported containment and native build gate; VM evidence cannot substitute |
| `managed-endpoint-v1` | System-wide providers under an explicit administrator policy | Distinct installation, privacy, multi-user and failure contract; not automatically a worker sandbox |

`observe-v1` and `brokered-v1` have their scopes in [product scope](01-product-scope.md). A local VM shortage or unavailable entitlement refuses launch; it never silently relocates the task or runs a native shell. Remote placement changes data location and must be authorized before export.

Production launch eligibility and candidate qualification experiments have separate entry paths. Production requires a verified installed-qualification artifact for the exact tuple. The dedicated signed lab probe may exercise the exact production driver bytes before that artifact exists, but only under separately verified native fixture authority confined to declared synthetic resources, controlled receivers, fixed probe recipes and isolated lab custody. It does not bypass entitlement, identity, native admission, stop or isolation checks. Its candidate observations feed [independent qualification](17-qualification.md); they do not set production availability or manufacture a qualified artifact. There is no production enable flag, and fixture authority is rejected by the production entry path.

## Proposed supervisor and guest boundary

The new backend is owned by `integrations/macos/native/` and the proposed shared desktop controller. Existing baseline subprocess launch in `crates/protocol/chio-mcp-adapter/src/transport/stdio.rs` is not a qualified substitute. M0 supplies actual native-owner contracts; the supervisor consumes opaque native bindings and never manufactures a kernel operation, approval, stop generation or confinement receipt.

The host retains a `LaunchBinding` observation tying native run reference, fresh launch generation, installation/boot identity, VM instance, guest image/kernel/initrd hashes, architecture, input generation, tool recipe digest, policy digest, native authority binding generation and channel endpoint. The controller verifies all native-owned fields against the serving owner. A PID, guest-reported UUID, virtio CID or process name cannot establish that binding. Host identity for the launcher includes UID, audit token/process incarnation and executable identity; PID-based signalling must revalidate the live incarnation immediately before use or use a retained safe handle. VM operations address the owned `VZVirtualMachine` instance, not a guest-selected identifier.

The host creates the VM with zero `networkDevices`, no shared home, no clipboard/device passthrough, no host SSH/container sockets, no user credential/config mounts and no GUI/session transports. Read-only disk inputs come from the committed immutable import, not a changing host directory. The worker writes to an ephemeral guest disk. Output enters a host staging broker through bounded frames; names and metadata are untrusted. Host path traversal, device files, symlinks, hard links, extended attributes and expansion ratios are checked by [resource import/export](10-project-resources.md).

The proposed private guest protocol `chio.macos.guest.v1` is distinct from the operator protocol. Its closed vocabulary is `hello`, `launch.prepare`, `launch.ready`, `invocation.start`, `invocation.finished`, `resource.call`, `resource.result`, `artifact.chunk`, `artifact.finish`, `heartbeat`, `stop.notice` and `stop.ack`. Launch/invocation/stop control belongs exclusively to the host and isolated guest supervisor; worker resource requests cannot inject those messages. All effects in `resource.call` reach the original native serving owner; no arbitrary host shell, generic URL fetch, operator approval method, or credential query exists. `hello` negotiates version and identifies the host-enrolled launch/image; it cannot enroll a new launch. The server scopes each accepted connection to its actual owning VM object and a single-use launch challenge. Guest compromise permits impersonation of that guest's processes but never another launch. A challenge is transport binding, not attestation or positive authority.

[VM plan Task 0](../../plans/2026-10-07-macos-integration/03-vm-project.md) owns the reproducible architecture-matched kernel/initrd/rootfs, locked package closure/SBOM, guest PID 1, virtio peer and isolated supervisor. The worker receives its exact sealed task-input generation through an anonymous read-only FD 3 (at most 256 KiB of EOF-terminated UTF-8 JSON), with no provider or signing secrets; an optional FD 4 relays only bounded resource requests. It inherits neither the supervisor's vsock/control descriptor nor boot capsule. Root-owned supervisor/runtime files and native invocation/capture custody must remain inaccessible to the nonroot untrusted worker under the separately qualified guest isolation boundary.

The host's data-only oracle is external to the guest. Verified tests additionally require native-verified evidence from a qualified supervisory lane binding the exact immutable artifact, interpreter/runtime, fixed argv/case/input, fresh invocation and exclusive complete stdout/stderr/descendant closure. The initial test lane uses a fresh verification VM mounting the host-sealed candidate generation read-only, with no surviving editing agent. Guest root/kernel/supervisor compromise invalidates invocation attribution even if the outer VM boundary still blocks host effects. Guest-printed completion, guest-supplied digests or a signed wrapper around such reports leave test status `Unverified`; they cannot enable a verified-result publication claim.

Initial proposed channel bounds are 1 MiB per frame, 32 outstanding requests per VM, 16 MiB aggregate undecoded data, and 10 seconds for the initial handshake. Artifact payloads use bounded chunks and the separately admitted artifact total; increasing it needs policy authority. These are initial design limits, not performance claims. Strict decoding rejects unknown versions/methods, duplicate keys, malformed integers, invalid encodings, excess nesting and trailing data. Correlation IDs deduplicate transport only. Stable native operation references and original-effect recovery come from the native owner. Stdout, stderr, logs, diagnostics, metrics and staged artifacts are also output channels and cannot bypass integrity/release policy.

Virtualization configuration validation is necessary but insufficient: [Apple's Linux sample](https://developer.apple.com/documentation/virtualization/running-linux-in-a-virtual-machine) requires matching guest architecture, [virtio sockets](https://developer.apple.com/documentation/virtualization/vzvirtiosocketdevice) provide transport, and [NAT](https://developer.apple.com/documentation/virtualization/vznatnetworkdeviceattachment) supplies external connectivity rather than a policy boundary. Future networked guests require a new qualified configuration, not changing a default.

## Native Mac build decision

The initial project recipe is portable Linux. There are four later candidates: a narrowly specified trusted native build service, a separately qualified native descendant runner, a separately qualified macOS VM runner, or a declared remote Mac runner. These are explicit decisions with their own isolation and export tests. Build scripts, package hooks and plugins count as untrusted execution. A signing service does not execute project scripts and does not return private keys. General host `xcodebuild` dispatch behind an allowlisted executable is insufficient.

## Failure and implementation handoff

Refusals identify `profile_unavailable`, `guest_identity_mismatch`, `transport_bound_exceeded`, `isolation_not_established`, `native_prerequisite_missing`, `native_outcome_unknown` or `closure_unconfirmed`. These are proposed internal classifications mapped into [the shared operator contract](06-operator-protocol.md), not additional wire methods. The implementation tasks are in [VM project plan](../../plans/2026-10-07-macos-integration/03-vm-project.md). Resource import/publication work stays with its owner; execution waits for its immutable generation contract rather than substituting path hashes for a snapshot.
