# Recovery remediation execution

The integration destination is the recovery runtime pull request. Completion
requires reviewed fixes and qualification of the resulting source. Historical
acceptance and isolated candidate passes retain their original scope.

## Working rules

- Preserve every original finding and its acceptance obligation. Track introduced
  defects and uninstalled candidate defects separately in the review register.
- Keep at most two implementation streams active. One owner coordinates shared
  Kernel, Process and Store contracts. Review precedes installation of repairs.
- Preserve the maintained vendor fixes and unrelated workspace files when
  consolidating older candidates. Never copy an entire older tree over the branch.
- Use behavioral names in implementation, tests and tooling. Review identifiers
  belong in this planning and evidence directory.
- Reproduce, repair, run owning checks, review, integrate, and verify the combined
  source before recording closure. A prerequisite refusal is not a positive test.
- Retain failed observations. A later correction gets a new evidence record.
- Continue ordinary local development while sensitive or explicitly blocked work
  remains stopped. Unrun mandatory qualification gates remain open.

## Acceptance order

Start with formatting, manifest consistency, focused compilation and meaningful
regressions. Run owning tests and strict lints next. Full integration, supported
platforms, formal obligations and hosted qualification follow a stable candidate.
Confirm registered test names and counts before interpreting a run. Repeat a
passed check only after a relevant source, dependency or configuration change.

The final release decision requires every finding to have a reviewed disposition,
all required current-source checks to pass, and no unresolved finding at any
severity. A source-level closure does not imply whole-runtime qualification.
Merge authorization remains separate from readiness.
