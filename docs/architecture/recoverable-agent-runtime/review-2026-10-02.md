# Principal-engineering architecture review, October 2, 2026

Disposition: revise the proposed architecture before implementation. Revision 2 incorporates the corrections below. The core decision remains sound: Chio's native kernel owns effects and authority, with small pure planning/contract components around it.

This is a review of the proposed specification against inspected source, not a report of demonstrated production vulnerabilities. Confidence is high in the identified contract gaps and current Rust/process/flow findings, and moderate in integration cost until native implementation campaigns run. No production runtime changes, independent peer sign-off or release qualification are claimed.

## Material findings and corrections

| Finding | Revision 1 gap | Revision 2 decision and evidence |
|---|---|---|
| REV-01: complete process binding | Finalization was described as storing the full request hash. The actual store binding also covers known-outcome-only mode, route and security profile. Calling normal invocation afterward could conflict or tempt a weaker alternate path. | Reuse one owning binding derivation, distinguish request/process-binding digests and transfer one reserved quota charge. Grounded in `ProcessRuntime::invoke_with_recovery` and `ProcessStore::admit`; REC-21. |
| REV-02: admission acknowledgement gap | Native evidence was required once admission was linked, leaving the earlier lost-link boundary insufficiently defined. | Commit admission intent before the kernel call; resolve the existing native identity regardless of projection state; serialize closure and late submission on its protected tombstone. REC-19 and the admission seam model. |
| REV-03: partial effects versus output | A flat state vocabulary mixed success, output withholding, cancellation and effect finality. Partial application had no explicit terminal disposition. | Separate progress, native effect facts, release records and control intent. Any settled effect spends the step. Later release never reruns the producing tool. REC-20 and the partial-effect model. |
| REV-04: command replay and audience | Idempotency did not specify stale-revision ordering or whether retained response bytes could bypass current read authority. | Resolve a committed command before rejecting its original revision; compare immutable content; freshly authorize and project every response. OPS-11 and the replay model. |
| REV-05: native observation ordering | Committing artifact knowledge was required, but its connection to the existing native flow rows/fences and release acknowledgement was underspecified. | Use native scoped joins, protected release intent, exact recipient context and readback before byte release. Reject stale preparation; preserve frozen captured payloads. ART-12, existing flow-store source and the knowledge model. |
| REV-06: hidden provider retries | One captured operation could still be resubmitted by lower-level transport/SDK machinery. Multi-resource partial effects were not bounded explicitly. | P1 permits one effectful submission. Qualify later same-operation provider deduplication separately, with exact key scope/lifetime/body and complete effect cardinality. CON-12. |
| REV-07: parent-to-child control input | Labeled seed artifacts alone do not cover prompts, resource choices and launch metadata chosen by a restricted parent. | Mediate every parent-influenced input under current parent knowledge. Fresh lineage/context identity never clears those influences. ISO-10. |
| REV-08: transitive commitment disclosure | A safe explanation could still carry hashes of protected low-entropy facts in its full signed report. | Keep the report classified; expose a distinct audience projection with opaque references and qualified verification claims. | REV-09: Rust compatibility and ownership | Workspace toolchain pinning omitted existing Rust 1.93/proof and alloc-only contracts. The async wording could prohibit holding the real owned dispatch operation across I/O. | Preserve substrate MSRV, no_std/alloc and isolated/unified feature gates. SEC-09, OPS-12 and the revised validator. |

## Changes deliberately avoided

No additional live authority, general policy interpreter, universal context object, workflow-wide generic typestate hierarchy, distributed transaction fiction or blanket modern-Rust migration was introduced. Two proposed pure crates remain sufficient. Native verified evidence and scoped ownership remain the execution boundary. Schema and migration work stays with its owning kernel/store modules.

Rust's type system prevents many invalid constructions and aliases, but does not prove temporal authority, exactly-once external behavior or durable commit. The revised design assigns those obligations to protected transitions, explicit provider contracts and failure evidence rather than stronger-sounding type names.

## Verification and limits

The original bounded ownership model explores 325 states and 774 transitions. Four additional independent models explore admission, observation, replay and partial-effect seams. All baselines complete and all twelve deliberate mutations fail for their intended invariant. The [model evidence](model/evidence.json), [original traces](model/results.txt) and [review traces](model/review-results.txt) retain exact source-bound output and assumptions.

The [requirements registry](requirements.json) and [validation report](validation.json) track the revised obligations, owners, phases, links and source inventory. [Review inputs](review-inputs.json) record the pre-edit package hashes; current output hashes are in the validation report. Evidence is local and reproducible, not independently attested.

Full process/authority bridge model checking, actual SQLite cutpoints, provider idempotency qualification, MSRV/feature builds of the proposed crates, typed schema generation, confinement and matched useful workflows remain implementation work. The specification is ready for another architecture review and dependency-ordered planning; these checks do not approve an implementation or establish public availability.
