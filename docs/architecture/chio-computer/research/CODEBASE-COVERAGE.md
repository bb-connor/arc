# Codebase coverage for the Computer research

Inventory date: 2026-10-09. This is a repository architecture coverage map, not a test report or a claim of line-by-line review.

## Method and limits

- Inventoried every `crates/<group>/<crate>/Cargo.toml` at the pinned #1160, #1173 and #1179 heads: **158 distinct crate names across 12 groups**.
- Compared branch-specific manifests and sampled architecture/module roots. Deep reads focused on the owners directly affected by Computer: work, process, admission, consumption, recovery, artifacts, security, resource providers, host, and SDK boundaries.
- Read the unified and constituent architecture contracts and acceptance requirements. The selected source hashes form a reproducible corpus; recording alone does not mean every file was read.
- Reviewed SDK and top-level repository topology. External plugin repositories and every third-party vendored dependency were not independently audited.
- Crate descriptions below come from pinned manifests. The proposed relationship column is architecture analysis; it does not assert the proposed Computer functionality exists.
- The union spans divergent branches and is not a buildable merged workspace or a claim that all 158 are enabled in the default build. The older 108-crate AGENTS overview does not describe this inventory.

## Functional groups

| Group | Distinct manifests | Architectural relationship |
| --- | ---: | --- |
| core | 8 | Reuse bounded values, canonical signed types, errors and supervision; keep Computer-specific host behavior out of small core types. |
| economy | 16 | Optional pricing, discovery, funding or settlement integration through the existing financial owner; no additional Computer consumption ledger. |
| guards | 6 | Reuse existing native policy/guard admission and explicit fact or deny interfaces; no facade-specific policy engine. |
| kernel | 10 | Reuse native runtime, process and admission ownership; layer environment authoring and checked bindings at the existing facade/core boundary. |
| observability | 5 | Project existing evidence through governed telemetry; observation is not authority or work acceptance. |
| platform | 20 | Compose through existing qualified services/stores and manifests; retain per-owner transactions, migrations and custody. |
| products | 11 | Consumer or operational surface of the shared Computer/work contracts; no private copy of lifecycle or authority rules. |
| protocol | 28 | Adapter or transport integration under declared profiles; translation does not create permission, containment or acceptance. |
| sdk | 6 | Reuse bindings, receipt evaluation or guard authoring; public Computer clients must share canonical contracts and test vectors. |
| security | 14 | Reuse security/custody/recovery/semantic enforcement; never clone these owners through a Computer snapshot. |
| tooling | 9 | Extend existing contract/codegen/conformance/release tooling for the new resource and program descriptors. |
| trust | 25 | Reuse explicit identity, federation, attestation or evidence policies; signals and signatures alone do not grant authority. |

## SDK and non-crate surfaces

| Surface | Coverage and consequence |
| --- | --- |
| Python | Inventoried `chio-process`, core SDK packages, adapter-base and framework integrations (including LangGraph, LangChain, Autogen, CrewAI, Hermes and workflow integrations). Add Computer authoring to the shared public surface; preserve framework planning and context ownership. |
| TypeScript | Inventoried process, AI SDK, browser/mobile, server frameworks, workers/edge and conformance packages. Share canonical descriptors and owner transport; do not implement a JS budget/scheduler. |
| Rust, C++, .NET, Go, JVM, Swift and FFI | Existing portability and binding surfaces inform wire/type design. A shared format does not automatically qualify every language as a full Computer host. |
| Guard SDKs and WASM | Existing policy extension path. Program code execution is a separate host profile from running a guard. |
| `spec/`, `wit/`, codegen | Follow closed versioned wire contracts and the unified schema ledger; no conflicting branch-local version assignments. |
| `formal/`, `fuzz/`, `arena/`, `bench/`, `tests/` | Reuse qualification infrastructure, then prove/check new compiler and resource composition laws. Existing proofs are tied to their actual models/source. |
| `deploy/`, `packaging/`, `supply-chain/`, `xtask/` | Preserve installed-profile, migration, build and artifact-provenance qualification. |
| `contracts/` and financial integrations | Optional funded work and settlement profiles. Compute rights, cost caps, real funding and rail settlement are distinct. |
| `examples/` and `integrations/` | Use for two independent consumers and end-to-end evidence; examples do not own production state. |
| `third_party/` | Consume through existing audited dependency boundaries; no additional vendor-code audit was performed for this architecture research. |
| Documentation and roadmaps | Unified, kernel, work, recovery, host, security, reliability, transparency, formal, economy, earlier four-direction, strategy and internal-development programs are cross-walked in ROADMAP-CROSSWALK.md. |
