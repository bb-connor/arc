# Computer: incremental delivery and acceptance

Status: proposed acceptance contract, revision 2. No case below is reported as
executed by this documentation PR. Parent: [PROPOSAL.md](PROPOSAL.md).

## Prerequisite and delivery rule

The design assumes the unified and constituent programs complete at their
declared supported scope. Implementation must identify the exact qualified
integration/profile baseline; do not reimplement missing predecessors inside
Computer to make an example pass. Existing owner evidence can be reused when
its source/profile scope actually covers the composed path.

Allocate new wire/schema changes through the unified ledger. Respect existing
MSRV/no_std boundaries and default feature/dependency contracts. Record the
dependency delta; a new feature name is not proof of isolation.

## Ordered increments

| Increment | Work | Exit evidence |
| --- | --- | --- |
| I1: closed descriptions | C1 records, C3 descriptors and canonical compiler; no native dispatch | Shared Rust/Python/TypeScript vectors, bounds, occurrence identity and forged-plan refusal |
| I2: managed branches | C2 local workspace provider and exact ChangeSet publication | Isolation, labels, interrupted publication recovery, base conflict and stale-writer evidence |
| I3: existing work composition | Bind compiled work, protected verification and C5 closure/view | Real native execution, exact acceptance, six-dimensional observations and admission/closure races |
| I4: independent computers | C4 owner bindings and qualified transfer/spending/host profiles | Separate operators, issuer keys and stores; receiver refusal; lost-reply and partition evidence |
| I5: installed applications | SDK/CLI surface, dynamic collaboration and evidence export | Full hero plus a second application reusing the same owners, supported installation profiles and negative cases |

Same-domain remote placement may be exercised before I4, but it cannot substitute
for independent receiver ownership. Use deterministic non-LLM programs to isolate
contract behavior in I1-I3, then real admitted agent/model execution on the same
path for I4/I5. Do not publish the monetary or platform promise before its actual
profile passes the relevant acceptance.

## C1: environments

| ID | Scenario | Required observation |
| --- | --- | --- |
| C1-01 | Serialize another tenant's Computer/revision reference and submit it | No authority fabricated; bounded audience-safe refusal |
| C1-02 | Remount `/workspace` or change a default model route after grant issuance | Old grant cannot reach the new binding; stale basis explicitly refused |
| C1-03 | Concurrent launches claim one candidate, including a lost claim response | One mutating family; original request recovers its claim; a distinct request cannot reuse it |
| C1-04 | Retry launch after mutable package/profile/namespace changes | Original exact basis recovered or current admission refused; no silent substitution |
| C1-05 | Import oversized/deep manifests, forbidden URLs, credentials or authority-store contents | Bounded rejection before fetch/execution or private disclosure |
| C1-06 | Restore a branch after spend, revocation, stop and restricted observation | No replenished authority, erased history or reopened admission |

## C4: execution bindings

| ID | Scenario | Required observation |
| --- | --- | --- |
| C4-01 | A grants work that B's local policy refuses | B does not execute; A's grant cannot override receiver consent |
| C4-02 | Present A's delegated capability as B's root or copy issuer custody | Rejected; valid independent flow uses B's own offer/local capability |
| C4-03 | Lose responses during offer, seal, submit, dispatch and result transfer | Reconcile original owner identities; one permitted native dispatch, no substituted sealed material |
| C4-04 | Concurrent helpers/model calls/integration/verification contend for final allowance | Actual family ceiling holds; no alternate account or fresh-session bypass |
| C4-05 | Lose a model reply, restart either owner, then request more work | Unknown exposure retained; counters/holds not replenished |
| C4-06 | Partition a recipient holding a delegated monetary allocation | Parent cannot reclaim and respend outstanding exposure based only on timeout |
| C4-07 | Expire/revoke/stop during remote execution, reconnect, or replace host evidence | No deadline renewal; future unauthorized commitments refused; stale/unqualified host cannot receive protected inputs or publish |
| C4-08 | Parent fails after payable child acceptance, or source rejects its patch | Child's financial claim retains its contractual disposition; no automatic refund/free work |

## C5: execution and apply

| ID | Scenario | Required observation |
| --- | --- | --- |
| C5-01 | Call `join_tree()` immediately, then race child admission and graph extension with final completion | Waiting permits required work to run; final owner fences account for every committed descendant; no premature or false closure |
| C5-02 | Required remote owner is unreachable during closure | No successful join from a stale list or best-effort broadcast; bounded unavailable/pending observation |
| C5-03 | Accepted work has settlement pending or output currently withheld | Independent observations preserved; payment does not grant release; required withheld result prevents ready-for-apply success |
| C5-04 | Client disconnects and receives duplicated/rebased event hints | Reconnect queries original work; no cancellation or effect redispatch inferred from hints |
| C5-05 | Reuse another task's acceptance or edit code/checks after verification | Exact producer/contract/evaluator/output binding rejects substitution |
| C5-06 | Source changes, or revocation/integrity state changes, after apply preflight | Authoritative commit-point checks reject stale base or authority; no silent overwrite |
| C5-07 | Lose apply response around pointer publication and receipt durability | Recover original outcome, or retain native reconciliation state; no substituted/repeated apply |
| C5-08 | Export to a dirty live directory or combine unrelated resource owners | Explicit materialization/conflict/per-resource outcome; no implied multi-file or cross-service atomicity |
| C5-09 | Verify a selected success receipt with missing membership or wrong witness/key history | Evidence consumer refuses unsupported completeness/trust claim under its declared verification policy |

## Two application demonstrations

### Application A: accepted project change across organizations

Execute the exact hero from installed packages outside the source checkout:

1. A owns a project and candidate; B has independent keys, store and operator.
2. B admits the image and executes the composed program under the selected host.
3. A program requests an approved helper through existing bounded work extension.
4. All relevant charged execution uses the advertised consumption binding.
5. Inject a lost reply and recover the original operation without a second
   dispatch; retain the exact native evidence for the fault cutpoint.
6. Freeze the integrated revision, obtain exact configured acceptance, and join
   the execution membership under its real closure fences.
7. Release an authorized diff and apply. Repeat with a changed source to show
   conflict without automatic rebasing or replacement verification.
8. Export evidence and verify it independently against the declared key/profile
   and witness requirements.

### Application B: confined work beside private data

Use the same Computer/work contracts to admit a program beside another owner's
private resources and return only an authorized bounded result. Qualify P5 seed,
provider context, confinement, return and all-channel release. Include forbidden
predicate disclosure and schema-valid-but-unendorsed output as negative cases.
The parent cannot observe raw data merely by receiving a typed reference.

## Acceptance accounting

Record application infrastructure removed: namespace wiring, branch bookkeeping,
delegation/signing, original-operation retry handling, budget sharing, acceptance
verification, result transfer and apply conflict handling. Application planning,
prompts, domain integration logic and selected acceptance predicates remain
application responsibilities.

Record exact source heads, supported platform/resource/provider/spending profiles,
installed package identities, operator independence, retained fault evidence and
which cases ran. Distinguish local checks, hosted checks, release qualification
and external operation. Document syntax validation in this PR satisfies none of
the runtime cases above.
