## Minimal ordered prerequisites

1. Freeze the ownership map, shared desktop ADR and R1 layer decision now. Record proposed owner amendments beside their source pins, preserving the accepted Rust-kernel positioning. This is planning acceptance, not implementation qualification.
2. Select each profile's foundation/IPC slice and require its exact-source/native/trusted/hosted acceptance. Reconcile actual recovery/process ABIs only for functions that consume them. No desktop behavior inherits uncommitted recovery W: assumptions from K; Darwin IPC remains an additional macOS gate.
3. Complete the Observe lane independently: S5 Part A then Part B (desktop is the second consumer), authenticated bounded non-persisting read adapters, truthful hook-session attribution and the existing trust-control GET bindings above. Qualify Q04, Q09-Q11, Q16-Q17 and Q21. Recovery projection additionally waits for its landed source and non-persisting read adapter; work projection waits for the W1 query, as K:S5 section 17 already specifies. Basic receipt/hook observation does not wait for W1, M20, S4, S8 or S28.
4. After the Observe lane, create the read-only shared candidate and common controller, then adapt the workbench first. Keep absent work/recovery/mutation capabilities explicitly unavailable. Qualify the workbench's inherited findings and selected UI/test suite; freeze only the exposed profile after implemented-client acceptance. Add Omarchy/macOS presentation clients against that same contract.
5. Independently qualify selected operator actions: S3 phase 1 and the narrowly sequenced M20 retry-disposition delta for their effect paths; S4 phases 1-2 and live process cancel/revoke for task closure; S8 phase 1 for kernel stop; S28 plus production endorsement verification and the installed approval utility fix for attributable approvals. Tenant/recovery stop waits for S8 phases 4/5. No one action inherits another action's qualification.
6. For work/recovery additions, require complete source-bound dispositions of historical and later recovery findings plus current native qualification; implement W1.0 source reconciliation, W1.5 acceptance and W1.6 original-operation lookup. Their absence blocks only dependent views/actions. Historical findings are not a current open-count inventory and are not resolved by relabeling them historical.
7. Amend and qualify the selected S7 backend/profile for execution. Start from the existing mini-SWE Docker and Pi restricted session owners; establish launch evidence and effect boundaries before labeling a desktop profile confined.
8. Deliver sealed work as the first execution product: single-owner unpaid work commitment, fixed recipe, existing kernel-owned execution, review artifact and original acceptance contract. Observe can precede execution; approve/stop needs its operator gates. Protected and boundary interactive profiles follow with their distinct doc 19/S7 gates.

Not mandatory for the first desktop product: NK-01 through NK-03 as complete keystones, all of S9/S10/S1, W2-W4, foundation M11, witness topology, or S11 injection-safety claims. Their absence must remain visible where a later feature depends on them. This is the accepted dependency order for desktop planning, not evidence that the predecessors have passed.

## Review corrections verified against source

1. S8 phase 1 does not deliver all three scopes: kernel in phase 1, tenant in phase 4, recovery in phase 5. S28 is phase 3.
2. Current R:`docs/architecture/recoverable-agent-runtime/implementation/STATUS.md` explicitly treats the old second review's three P1 findings as historical. Do not copy “3 P1, 45 P2, 94 P3 open” as a current unresolved count. Historical does not mean resolved: the 158-original-ID inventory, merged/predecessor obligations and later independent findings still require complete source-bound dispositions and acceptance. Current source is not qualified; focused repairs or an old count cannot close that gate.
3. `PasskeyCapabilityVerifier` is production-exported code, not itself `cfg(test)` only: F:`crates/kernel/chio-kernel/src/custody.rs`; F:`crates/kernel/chio-kernel/src/lib.rs:480`. Say “production approval-path integration and qualification are missing,” not “the verifier exists only in tests.”
4. D:`docs/superpowers/specs/2026-10-07-omarchy-integration/reviews/2026-10-07-architecture-review.md:93,116` used the historical shorthand `recovery_events`. K:S5 already correctly names `admission_operation_recovery_events` in its source table, H10 and section 12.3. The correction belongs to the desktop review's attribution, not S5; R's storage is the same owner source, with no desktop event table.
5. S1 classifies seams/components; it does not already name `chio-operator`. Its outside-TCB placement is the approved desktop architectural decision applied using S1's classification.
6. W1's acceptance and transport contracts are planned. `WorkViewV1` is not a globally atomic snapshot and missing query state is not proof an original operation never happened.
