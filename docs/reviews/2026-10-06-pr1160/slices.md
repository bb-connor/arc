# PR #1160 slice reports

One section per review slice: scope summary, what was and was not read, the slice's findings (numbered as in findings.md), and its design and Rust-quality critique.

## Kernel admission, evaluation, dispatch and recovery

Reviewed chio-kernel src/kernel admission, recovery, terminal finalization, payment settlement, cleanup, terminal receipts, evaluation, dispatch, validation, session ops and credential reservation (about 36K lines). The main risk is liveness under fail-closed: startup reconciliation latches only on full success and runs on every request, so any single unrecoverable operation denies every later tool call, and four concrete payment paths (prepaid or Settling pre-dispatch compensation, over-reported or unconvertible cost, live-FX replay) produce exactly such operations. Several P2s concern metadata-driven control (chio_runtime and session reserved keys), cross-tenant request_id selection, DPoP release reuse across operations and cleanup skipped on clock errors. No fail-open authorization path, unwrap/expect/panic or unchecked indexing was found in non-test code, and receipt signing binds the exact operation projection.

**Design verdict**

The admission core has real strengths: a closed 19-variant AdmissionOperationState with transition_checked, version CAS plus store fences on every mutation, readback after uncertain writes, a signed terminal-receipt outbox validated against the exact projection and signature, bounded untrusted JSON, checked arithmetic, and no unwrap/expect/panic or unchecked indexing in non-test code. It falls short of elite production Rust in structure: phases live in 400 to 2,000 line functions on one god object, 361 stringly-typed error sites erase the transient-versus-poison distinction that recovery needs, a process-wide std Mutex is held across network I/O, two parallel admission state machines coexist, and over 1,500 lines of dead or compiled-out code ship in the slice. Most P1 bugs above are a direct consequence of these structural choices.

**Done well**

- Closed state enums with checked transitions and exhaustive matches (FrozenDispatchParticipants::from_operation forces a decision per attachment)
- Every durable mutation is CAS on version plus store fence; uncertain writes are resolved by exact readback, never assumed
- Terminal receipt outbox: signed before staging, validated against operation projection, signer binding and signature on recovery (admission_terminal_receipt.rs:1143-1250)
- Affine egress handles (Prepared/Acquired consumed by value) and non-Send callback-scoped authorities
- Untrusted JSON parsed through UntrustedJsonText with size caps; all counters use checked_add
- No unwrap/expect/panic/indexing in non-test code across the slice; callbacks wrapped in catch_unwind and denied on panic
- Async evaluation has few await points, none between durable dispatch commit and the dispatch itself

**Design issues**

- **function size and phase modeling** (major). Pricing, settlement, security release, receipt signing and projection are interleaved in one body that re-locks and re-samples time in several places. Choosing the wrong cleanup builder or skipping cleanup on a branch is the root cause of several findings (stranded DispatchCommitted, clock `?` skipping cleanup).
  - Evidence: terminal.rs:1025 finalize_durable_tool_return_with_security_release (937 lines); admission_coordinator.rs:480 begin_durable_tool_admission_for_transport (477); terminal.rs:452 completed_durable_tool_response (326); async_evaluation_core.rs:9 evaluate_tool_call_async_with_session_context_scoped (~1,980 lines, ~30 early returns each choosing a cleanup builder by hand); nested_flow_evaluation.rs (~1,680)
  - Better: A typestate pipeline of owned phases (Begun, BudgetAuthorized, CapturePending, DispatchCommitted, Returned, Resolved, Settled, Projected). Each phase is a small fn that consumes the previous phase, and each carries a `deny(self, reason)` and Drop that perform exactly the cleanup valid there.
- **error type design** (major). OutcomeUnknown, rail Pending, replay conflict and invariant violations become the same string. The recovery sweep cannot tell a transient failure from a poisoned row, so it can only refuse everything, and commit classification depends on call-site position rather than the source error.
  - Evidence: 279 KernelError::DurableAdmission(String) and 82 KernelError::Internal(String) constructions in admission_coordinator*/admission_cleanup/admission_terminal_receipt; durable_store_error, durable_outcome_store_error and tool_outcome_error (admission_coordinator.rs:1984-1996) all to_string(); validation.rs returns Result<_, String> from capability admission helpers
  - Better: A thiserror DurableAdmissionError { Rejected(Reason), OutcomeUnknown(..), Transient(..), Conflict(..), Store(#[from] AdmissionOperationStoreError), Clock(#[from] ClockError) } with a `retryable()` classifier used by recovery; stringify only at the receipt or wire boundary.
- **locking and blocking in async** (major). All durable admission traffic serializes behind the slowest external call and Tokio workers block.
  - Evidence: AdmissionMutationSequencer is a process-static std::sync::Mutex<()> per fence (admission_operation/sequencer.rs) held across SQLite IMMEDIATE transactions, payment rail HTTP (terminal.rs:1141-1445, admission_coordinator.rs:1615-1790) and oracle block_in_place; startup_reconciled std Mutex held across the full sweep on the request path; called from async evaluation without spawn_blocking; also taken for pure reads
  - Better: Per-operation exclusion (the live-owner set already exists) plus store CAS for correctness; journal intent under a short critical section and perform external I/O outside it; run blocking store and rail work on a dedicated blocking pool.
- **recovery policy** (major). Fail-closed is implemented as 'refuse all work while any row is bad'. That turns any single deterministic failure into a kernel-wide outage and makes bounded batches unable to make progress.
  - Evidence: recovery.rs:108-360 latch-on-success plus deferred error; admission_cleanup.rs:301-309 and 639-647 limit+1 refusal and abort-on-first-error; admission_terminal_receipt.rs:968-1058 collects errors per row (the one path that does it right)
  - Better: Quarantine semantics: a durable per-operation poison state with the typed error and an operator alert, progress-making cursored sweeps, and denial scoped to the affected request id.
- **two parallel admission state machines** (moderate). Identically named types with different variant sets and invariants; fixes land in one model and not the other, and readers cannot tell which applies (admission_cleanup.rs and admission_coordinator import different AdmissionOperationState types).
  - Evidence: crate::admission_operation::AdmissionOperationState (19 variants, admission_operation.rs:228) and crate::security_admission_operation::AdmissionOperationState (15 variants, assembled by include! of admission_operation.part{1,2,3}.inc, 3,583 lines); separate stores, separate recovery code (recovery.rs versus admission_cleanup.rs) with different batch semantics
  - Better: One generic operation core parameterized by kind (trait or const-generic kind marker) with a single store contract and recovery driver; real modules instead of include! fragments.
- **replay determinism** (moderate). Finalization is designed to be replayed but re-derives decisions from time-varying or config-varying inputs, then rejects its own earlier persisted decision as a conflict.
  - Evidence: terminal_payment.rs:89-101 live FX on every attempt; terminal.rs:1109, 1205-1235 purchase and recovery revalidation at current time; evaluation_contract.rs:19-36 recomputes the request hash from current hook and security config
  - Better: Persist every decision input (rate evidence, status verdicts, frozen plan and security binding) before the first commit that depends on it, and on replay read them back instead of recomputing.
- **dead and compiled-out code** (moderate). Uncompiled code is never type-checked, misleads reviewers about live behavior, and test-only alternates let coverage of the production path be overstated.
  - Evidence: admission_cleanup/recovery_and_compensation.inc (1,228 lines, never included); 10 #[cfg(any())] items (~356 lines) in admission_terminal_receipt.rs; #[allow(dead_code)] build_nonce_denial_after_monetary_cleanup (evaluation_helpers.rs:654-829); #[cfg(test)] alternate reserve entrypoints in credential_reservation.rs:346-414
  - Better: Delete dead code; route tests through the production reserve_for_admission path with fixtures.
- **boolean-flag state and duplication** (moderate). Illegal flag combinations are representable and the copies drift (capture does not enforce one-shot while flow/output joins do).
  - Evidence: DispatchCredentialReservation rollback_on_drop/retain_on_drop bools; PostAdmissionDropGuard armed/dispatch_started bools; NativeSecurity*Authority Cell flags (attempted/failed); ~700 lines of copied store_call/load_history/validate_successor across dpop/governed/runtime participant files; same_terminal_projection and same_operation_projection are identical (admission_terminal_receipt.rs:1268-1284); nested_flow_evaluation duplicates the core's dispatch arms
  - Better: Closed enums (OnDrop { Rollback, Retain, Settled }, AttemptState<T> { Unused, Entered, Failed, Confirmed(T) }) in a shared OneShot<T>; an OperationOwnedParticipant trait for custody; one generic dispatch stage behind a driver trait.
- **module layout and public surface** (minor). Path attributes hide the layout from tooling and test-harness types leak into the production API.
  - Evidence: mod.rs:25 `#[path = "admission_coordinator.rs"]` forces #[path] on every submodule (admission_coordinator.rs:8-81, validation.rs, session_ops.rs, credential_reservation.rs); DurableFinalizationCutpoint exported unconditionally (mod.rs:110-114) although only the admission-test-support feature uses it; inline #[cfg(test)] in return_context/caller.rs
  - Better: Plain `mod x;` with the 2018 foo.rs + foo/ layout; gate test-support types behind the feature; keep tests in sibling tests modules.

## Kernel active response, DPoP, approvals, process and runtime crates

No P0 or P1 issue was established. Every authority path checked fails closed: active response, DPoP, execution nonces, threshold approvals and the process worker all use the kernel authority clock, verify signatures before writing state, and deny on poisoned locks and store errors. The ten findings are P2 robustness and spec-of-behavior gaps. In active response, a transient store error compensates an existing approved response; startup recovery and the live paths disagree about the approval-committed-but-not-dispatched state; more than 4096 DispatchCommitted operations block publication forever; the enable/deactivate flag is never enforced on prepare or execute; and a weaker legacy public commit path remains. Elsewhere, receipt_store lost its loom gate (the kernel loom lane no longer compiles), mailbox leases still use SystemTime (same class as the two repaired Codex clock threads), oversized worker responses permanently hide the verdict and receipt, and the swarm verifier recurses over an unbounded, unsigned graph. Design-wise, the code is defensive and well bounded, but it is organized as a 214K-line god crate with include! fragments, duplicate same-named public type families, opt-in clocks and pervasive String errors.

**Design verdict**

Locally, the slice is careful, fail-closed Rust: checked arithmetic everywhere, bounded inputs, redacted Debug impls on secret-bearing types, typestate-sealed execution requests, deterministic domain-separated identities and IMMEDIATE-transaction CAS predicates. Structurally, it falls short of elite production Rust. chio-kernel is a 214K-line god crate. About 17K lines live in include! fragments that rustfmt never sees. Two incompatible admission-operation families share identical public names. Errors are mostly String payloads that erase the denial-versus-outage distinction the recovery logic depends on. Security clocks are opt-in defaults rather than required inputs. The state-transition policy is hand-written in several places, which is where the active-response findings come from.

**Done well**

- Sealed execution requests: ActiveResponseExecutionRequest has private constructors keyed by origin (Fresh/CommittedDispatch/CommittedAdmission). Recovery mode comes from the origin and cannot be chosen by the caller, and compile_fail doctests lock this in.
- Deterministic, domain-separated canonical identities (dispatch id, executor authority id, policy decision hash, operation seed) make crash retries converge on one dispatch.
- Executor readback is treated as untrusted and re-derived end to end: canonical bytes, body hashes, mutation history, signed completion receipt envelope, effect transition ids.
- The authority clock is used consistently. There is no SystemTime in the slice, and time-unit conversions use checked_mul with equivalent second and millisecond comparisons.
- Kernel-side DPoP clock binding is careful: `set_dpop_store` rebinds the store to the kernel clock and refuses a store whose replay clock was already observed (bind_clock plus require_pristine). The v2 durable profile pins authority independently of proof data and caps TTL and skew.
- DPoP verification writes no state before the signature check; nonce reservation happens only after `verify_strict`. Poisoned mutexes, capacity exhaustion and elapsed signed horizons all deny.
- Threshold approval verification de-duplicates token ids, digests and signers, enforces algorithm allowlists against both key and signature, and binds every vote to the proposal hash, request, intent, subject and an exact deadline.
- chio-process validates child delegation exactly (one hop, signed link, scope hash, issuer and budget family), uses IMMEDIATE transactions with CAS predicates for attempts and checkpoints, refuses non-private journal directories and files, and keeps bearer secrets as SHA-256 digests with a redacted Debug.
- Debug impls on raw outcomes, DPoP credentials and security-release contexts redact payloads, and every hand-rolled size bound uses checked arithmetic.

**Design issues**

- **include! fragments instead of modules** (major). `include!` splices text into one module, so there is no privacy boundary: every private item in part1 is visible to part2, part3 and the tests. Compiler diagnostics and backtraces point into files that rustfmt never visits, because rustfmt follows `mod` and not `include!`, so `cargo fmt --check` silently skips about 17K lines. IDE navigation, `cargo doc` source links and mutation or coverage tooling degrade too (scripts/generate-proof-report.sh and xtask/src/adapter_no_bypass/source.rs had to grow .inc special cases). The naming misleads as well: fragments called `admission_operation.part*.inc` belong to `security_admission_operation`, while a different `admission_operation` module and directory sit beside them. The 1,300-line fragments are no more reviewable than the original file; the split only games file length.
  - Evidence: crates/kernel/chio-kernel/src/security_admission_operation.rs:4-6 is a 6-line file that `include!`s admission_operation.part1.inc (1342 lines), part2.inc (971) and part3.inc (1270). part3.inc opens with the `#[cfg(test)] mod tests` block, so tests are spliced in too. All three were added in b39b13127 ("restore durable active response orchestration"). The repo has 16 .inc fragments totalling about 17K lines (also kernel/active_response_coordinator/execution_validation.inc, kernel/admission_cleanup/recovery_and_compensation.inc, chio-store-sqlite admission_operation_store/part_0{1,2}.inc, chio-core-types receipt/security_parts/*.inc). No xtask or script gate on file length motivates the split. The active-response coordinator does the same: active_response_coordinator.rs:1221 `include!`s active_response_coordinator/execution_validation.inc (825 lines of free functions that silently inherit the parent's imports), although its sibling admission_request.rs is already a real module.
  - Better: Turn the fragments into a real module tree: security_admission_operation/{types.rs, binding.rs, store.rs (trait), in_memory.rs, tests.rs}, with `pub(super)`/`pub(crate)` visibility chosen deliberately and `#[cfg(test)] mod tests;` in its own file. Apply the same to execution_validation.inc and recovery_and_compensation.inc. If file length is a goal, enforce it in xtask on .rs files and ban new `include!` of Rust source.
- **duplicate public type families with identical names** (major). Two incompatible state machines share one vocabulary in the TCB crate's public API. `use chio_kernel::AdmissionOperationState` silently picks the security variant, so a caller can compile against the wrong store trait or schema constant, and grep and review cannot tell the two apart. This kind of mix-up becomes a fail-open bug the first time someone persists one family's state under the other's schema.
  - Evidence: chio_kernel::admission_operation defines `AdmissionOperationStore` (admission_operation/store.rs:119), `AdmissionOperationState` (admission_operation.rs:228), `AdmissionDispatchState`, `AdmissionOperationKind` and `ADMISSION_OPERATION_SCHEMA = "chio.admission-operation.v1"` (admission_operation.rs:81). chio_kernel::security_admission_operation defines the same five names with different shapes and `ADMISSION_OPERATION_SCHEMA = "chio.security-admission-operation.v1"` (part1.inc:9, 74, 1029). The crate root re-exports the security family as `chio_kernel::AdmissionOperationStore` and friends (lib.rs:617-626), while chio-process matches on `chio_kernel::admission_operation::AdmissionOperationState::OutcomeUnknownAfterDispatch` (chio-process/src/lib.rs:598-608).
  - Better: Give the security family distinct names (`SecurityAdmissionOperation`, `SecurityAdmissionStore`, `SECURITY_ADMISSION_OPERATION_SCHEMA`) and stop root re-exporting either family. Or factor the shared lifecycle into one generic `AdmissionStateMachine<P: AdmissionProfile>` so the two profiles cannot drift.
- **chio-kernel is a god crate; crate boundaries** (major). Almost every change touches one compilation unit that CODEOWNERS treats as the TCB, so review scope, incremental build time and blast radius are all maximal. Downstream crates couple to receipt-metadata projections instead of a typed outcome API. "core" no longer means portable or minimal outside chio-kernel-core.
  - Evidence: crates/kernel/chio-kernel/src holds about 214K lines of .rs/.inc. ## SQLite security state, serving owner and receipt store

The SQLite security-state, serving-owner and receipt-store code in this PR is defensive by default. Writes use BEGIN IMMEDIATE, deferred transactions are read-only, fencing tokens are compare-and-swap inputs with checked increments, append-only tables carry RAISE triggers, and catalogs are verified byte-for-byte. I found no fail-open authorization path. The real defects are at the edges. A post-commit telemetry clock read can permanently close the receipt writer. The session throttle trusts a caller-supplied time, so a backward clock step resets its windows. The security-state open path runs migrations on whatever a symlink points to, binds file identity from the path rather than the descriptor, and creates the database with umask permissions. The bigger problem is structural: a 22K-line store type sits behind one connection, schema versioning is stuck at 0 with shape-detected migrations for schemas that never shipped, and errors are lossy throughout.

**Design verdict**

The persistence code is unusually rigorous about invariants. Typestate write owners, exact-catalog verification, checked arithmetic, fencing CAS and poison-aware connection recovery are all well done. Structurally it falls short of elite Rust. One 22K-line `SqliteSecurityStateStore` implements about 15 port traits over a single mutex-guarded connection. SQL lives in raw strings decoded into positional tuples. Errors collapse into four context-free kinds. Schema evolution has no version discipline. The result is correct-looking code that is expensive to review, profile and debug.

**Done well**

- Write discipline: every mutating security-state path uses BEGIN IMMEDIATE, and every Deferred site is read-only (flow_state.rs, scheduler.rs, issuance_freeze.rs, capability_set_suspension.rs, response_simulation.rs, lineage_fence.rs).
- SecurityStateWriteTransaction (transaction.rs) is a real affine owner: it forces DropBehavior::Rollback, asserts TransactionState::Write, and only returns ownership on success.
- StoreConnection (store_connection.rs) recovers a poisoned mutex by verifying an explicit ROLLBACK and an anchor consistency check, then fences with a named reason. The tests exercise rollback-denied and commit-before-anchor phases.
- Exact-predecessor migrations are done right in serving_owner/global_commit_chain/schema_migration.rs: catalog equality per historical shape plus a scan for smuggled projection kinds before any DDL.
- Fencing tokens use checked_add, a durable per-tenant sequence (scheduler.rs:1306-1345) and CAS UPDATE ... WHERE token = ? with row-count checks. Lineage fences reject stale owners on renew, takeover and release.
- The crate root sets #![forbid(unsafe_code)] plus deny(indexing_slicing, panic, as_conversions) outside tests, and each allow carries a reason string.

**Design issues**

- **module organization** (major). The parent module is a dependency sink, so every child is coupled to everything. Ownership of a table or invariant cannot be found by module. Two public types share one name, and their source lives under another module's path as .inc fragments that rustfmt, rust-analyzer and code owners handle poorly.
  - Evidence: security_state.rs:1-132 is an import hub (an 85-line `use chio_security_types::ports::{...}`). 22,423 non-test lines across 93 files implement one struct. Child modules pull dozens of items via `use super::{...}` or `use super::*` (declassification/port.rs:3, global_commit_chain/projection_reference.rs:3). `security_admission_operation_store.rs` is 4 lines of `include!("admission_operation_store/part_0{1,2}.inc")` from a sibling module's directory and defines a second `SqliteAdmissionOperationStore`, re-exported as `SqliteSecurityAdmissionOperationStore` (lib.rs).
  - Better: Split into per-aggregate repositories (flow, scheduler and leases, overlays, throttles, declassification, correlation, dispatch). Each owns its DDL fragment and SQL and depends only on a small shared `db` module (codec, error mapping, transaction owners). Compose them in a thin store that implements the ports by delegation. Replace the .inc includes with a real module and give the security admission store a distinct type name.
- **schema versioning and migrations** (major). Downgrade protection relies on a version that never moves, so a future additive change made the same way lets an older binary open a newer DB and ignore new restrictive state. The shape-detected migrations are dead in practice (they target pre-release shapes), and two of them are destructive: one silently resets outbox state, and one wipes rather than refuses an unknown schema.
  - Evidence: SECURITY_STATE_STORE_SUPPORTED_SCHEMA_VERSION = 0 (schema.rs:12) with `CREATE TABLE IF NOT EXISTS` plus `ensure_*_column` ALTERs (response_schema.rs:181-513). The ALTERs add columns that the CREATE statements already contain, for a store that does not exist on main (all security_* tables are new in this PR). correlation_schema.rs:328-334 drops `security_attested_finding_response_outbox` during the legacy batch rebuild, and response_schema.rs:545-566 then reseeds every batch item as pending/pending/not_started, discarding planned, admitted and completed progress and completion evidence. declassification_schema.rs:323-375 drops any unknown-shaped declassification tables, including the lifecycle singleton, when they are empty.
  - Better: Ship a single canonical v1 DDL verified by exact catalog, as participant_source/schema.rs already does. Delete the pre-release migration paths. Add future changes as numbered forward-only steps with an exact predecessor catalog, as in global_commit_chain/schema_migration.rs. Bump the stamped version on every change so FutureSchema refuses older binaries. Refuse, never drop, any unrecognized shape.
- **error handling** (major). An `integrity_failure` from any of about 200 sites cannot be traced to its check, and real corruption surfaces as a retryable `unavailable`. That invites retry loops over a damaged database, and incident triage requires a debugger.
  - Evidence: 343 `map_err(|_| PortError::...)` sites in security_state. PortError constructors carry no detail. codec.rs:8-21 maps every non-constraint rusqlite error, including SQLITE_CORRUPT, NOTADB and IOERR, to `unavailable`. No tracing at the store boundary.
  - Better: Use a store-local `thiserror` enum with `#[source]` and a static site tag (or `#[track_caller]` location). Log it once at the port boundary and map it to the PortError kind there. Classify CORRUPT, NOTADB and FULL as integrity or storage failures, not unavailable.
- **SQL boundary typing and statement caching** (moderate). A column reorder silently mis-assigns tuple fields of the same type. The hot authorization paths pay SQL compile cost per call. The three projection-kind lists can drift.
  - Evidence: Positional row tuples: lineage_fence.rs:15 `(String, i64, Vec<u8>, i64, String, i64, i64, String)`, scheduler.rs:62, response_schema.rs:323-332. 59 `prepare` calls vs 5 `prepare_cached` even though `AUTHORIZATION_STATEMENT_CACHE_CAPACITY` is set at open. `ScopedReader::prepare` (scoped_sql.rs:47-75) re-prepares and re-validates parameter names on every call. Projection kinds are string literals repeated in the SQL CHECK (global_commit_chain.rs:47), the migration list (schema_migration.rs:15-27) and the dispatch match (projection_reference.rs:11-145).
  - Better: Use named row structs with `TryFrom<&Row>` that read columns by name, and newtypes such as `FencingToken(NonZeroU64)` and `Digest32` at the decode edge. Use `prepare_cached` in ScopedReader and cache the parameter-shape validation per SQL string. Add a `ProjectionKind` enum with `ALL` and `as_str()`, and generate the CHECK list from it.
- **per-operation catalog scans and the single connection** (moderate). Every guard evaluation pays two to three schema scans while holding the only connection, which compounds the scan costs already raised on capability_set_suspension.rs:846.

- **clock handling consistency** (moderate). Each store has a different answer to what happens when time moves backward: a hard error, a permanent outage, a silent quota reset, or nothing.

Integration tests are split with `include!("security_state_parts/part_0N.rs")` (tests/security_state.rs, tests/security_state_contract.rs). `security_state_lifecycle_owner_proof` and `reset_declassification_lifecycle_for_owner_takeover` are public but have no production caller, and `ProductionSecurityStateLifecycleOwner` has only a test implementation. Unsigned local anchor and marker files are decoded through `decode_signed()` (rollback_anchor.rs:676, path_identity.rs:95), which misleads readers.
  - Better: Move black-box tests to tests/ as real modules, and keep unit tests next to the code they cover. Either wire the lifecycle-owner proof into the host or make it `pub(crate)` behind a test feature. Rename `decode_signed` or add a `decode_canonical_untrusted` alias for unsigned local records.

## SQLite admission operation and budget stores, manifest, Postgres

The admission-operation and budget persistence in chio-store-sqlite is very defensive. Writes use IMMEDIATE transactions with version compare-and-set and changes()==1 checks, terminal rows are frozen by triggers, every decode compares bytes against canonical JSON, integer crossings are checked, and a poisoned connection is rolled back or fenced. I found no P0 or P1. Four P2 robustness defects remain. Two hot-path queries (the caller sibling-share snapshot and the recovery page) now scan and fully re-verify an unbounded, ever-growing set of operations while holding global locks. The native security-participant journal has a hard lifetime cap and no compaction, so an authority stops accepting native mutations for good once the cap is reached. Caller-report resolution keys on a bare request_id across tenants, so a request_id collision blocks reconciliation of an operation the timer-driven sweep never revisits. The manifest, http-core, transaction-passport and Postgres hunks are sound: Postgres keeps verify-full TLS, transaction-local tenant binding, bound parameters only, and SECURITY DEFINER job functions that recheck the tenant. Structurally, the slice carries two parallel admission stores (one a 2.4K-line include! fragment that nothing in production uses), duplicated raw-SQL plumbing with no typed row layer, stringly-typed errors, and about 64K lines of tests compiled inside src.

**Design verdict**

Measured against elite production Rust, the fail-closed discipline is strong. Transactions, compare-and-set, triggers, canonical byte equality and checked integer crossings are applied consistently, and the budget accounting is sound. The structure does not match that standard. Two admission stores live in one 292K-line crate, the core types of a manifest crate sit in a textual include fragment, and raw-SQL plumbing is duplicated with no typed row layer. Errors are stringly typed and invariants travel as positional u64s and runtime pointer checks rather than types. Verification on every load, multiplied by unindexed scans, is the common root of the robustness findings.

**Done well**

- Write paths open IMMEDIATE transactions, re-check the serving-owner fence and anchor inside the transaction, CAS on `version` with `changes() == 1`, and map commit failure to OutcomeUnknown with owner poisoning instead of guessing.
- SQLite triggers freeze terminal operations, enforce single-step version increments, make commits, nonce issuances, reservations and retained requests append-only, and require an exact live serving lease per commit.
- decode_row re-encodes every persisted operation and rejects non-canonical bytes and column or JSON disagreement, so storage tampering is detected rather than interpreted.
- Migrations run in one IMMEDIATE transaction with FK renaming disabled outside it, verify predecessor catalogs, and finish with `pragma_foreign_key_check`.
- integer::checked and the `as_conversions` deny remove silent narrowing at the SQLite boundary, and budget arithmetic uses checked domain types under `deny(clippy::arithmetic_side_effects)`.
- Authority time is max(decision, observed) with bounded skew, so a delayed caller cannot extend leases, nonces or approval windows.
- Filesystem custody walks directories with openat/O_NOFOLLOW, pins dev/inode for every ancestor, and checks that SQLite opened the same inode.
- The Postgres store forces verify-full TLS, binds tenant scope transaction-locally with set_config, uses only bound parameters, and routes worker transitions through SECURITY DEFINER functions with a pinned search_path that recheck the enabled tenant under FOR SHARE.

**Design issues**

- **module organization and include! fragments** (major). Textual includes have no module privacy or path hygiene, degrade rustdoc, IDE navigation and error spans, and let one file's `use` set leak into another. Two same-named store types behind different traits invite the wrong one being wired. A single crate this size serializes compile time and blurs ownership between the admission, budget, receipt and finding-market domains.
  - Evidence: security_admission_operation_store.rs is two include! lines over admission_operation_store/part_01.inc and part_02.inc (2,368 lines, a second SqliteAdmissionOperationStore with its own schema); chio-manifest/src/lib.rs (42 lines) includes lib_parts/part_01.inc (1,027 lines of the crate's public types); finding_challenge_store.rs includes 12 files; chio-store-sqlite/src totals about 292K lines including tests.
  - Better: Make every fragment a real `mod` with explicit `pub(crate)` surfaces. Delete or isolate the unused security store. Split chio-store-sqlite into domain crates (admission, budget, receipt, finding-market) that share a small `chio-sqlite-core` for connection, serving owner, clock and integer helpers.
- **state machine enforcement at the SQL layer** (moderate). A future write path that skips apply_command, such as a migration or repair tool, can persist any edge, and the mismatch is caught only on the next read. The duplicated columns exist only to be re-verified.
  - Evidence: admission_operation_store.sql:229-271 enforces version +1, terminal immutability and claim freezing; the allowed edges live only in chio-kernel `AdmissionOperationV1::apply_command`. The `state` and `terminal` columns duplicate JSON fields, and decode_row (admission_operation_store.rs:1259-1273) cross-checks them on read.
  - Better: Add an `admission_state_edges(from_state, to_state)` table with a `BEFORE UPDATE OF state` trigger that raises when the edge is absent, generated from the same Rust edge list by a build-time test. Derive `state`/`terminal` as `GENERATED ALWAYS AS (json_extract(operation_json, '$.state')) STORED` columns so they cannot diverge.
- **verification on every load (read amplification)** (major). Defense in depth turns every point read into O(participants) work and every scan into O(rows x participants), which is the root of the P2 scans. There is no way to express 'already verified in this transaction'.
  - Evidence: load_by_operation_id_tx and load_by_replay_key_tx (admission_operation_store.rs:1337-1505) each run decode + re-encode plus about nine verifier queries. begin_prepared_operation_tx loads twice, advance_named_participant_tx reloads what its caller just loaded, and caller_budget_shares and recoverable_page multiply this by table size.
  - Better: Return a `VerifiedOperation<'tx>` witness that borrows the Transaction and can only be built by the verifier. Cache it by (operation_id, version) for the transaction's lifetime and pass it down instead of re-loading. Push scan filters into indexed columns so verification runs only on matched rows.
- **duplication and the missing typed query layer** (major). Each invariant lives in N string copies, and a guard added to one copy is silently missing from the others. The repeated 64 MiB bound is a magic number unrelated to each column's real limit.
  - Evidence: The 18-column operation SELECT is copied in load_by_operation_id_tx, load_by_replay_key_tx and recoverable_page. About 15 private copies of sqlite_i64/stored_u64/sqlite_error remain (channel_lifecycle_store, economic_state_cache, finding_*, fiscal_store, settle_attempts, sealed_decoy_registry, enterprise_migration_state) alongside the new integer.rs. `UntrustedJsonText::from_wire(bytes, 64 * 1024 * 1024)` appears 104 times in non-test src. The usage CAS UPDATE is hand-copied across trait_impl.rs release/reverse/reduce/settle/cancel, while composite/model.rs already has write_usage(before, after). Path custody helpers (validate_durable_path, reject_symlink_components, sidecar checks, file identity) are re-implemented in enterprise_migration_state.rs, sealed_decoy_registry.rs, authority/custody and part_01.inc.
  - Better: Use per-table row modules (`OperationRow::COLUMNS`, `impl TryFrom<&Row>`, `fn cas(tx, &before, &after)`), one `sql::{to_i64, from_i64, map_err}` module, a `decode_durable::<T>(bytes, Bound::Operation)` helper keyed to each column's CHECK bound, and one shared path-custody module. rusqlite + a thin repository layer is enough; no ORM is needed.
- **error model** (moderate). Callers cannot tell retryable conflicts from corruption or capacity exhaustion. That matters for the recovery sweep and the caps above, and operators lose the artifact path in passport failures.
  - Evidence: AdmissionOperationStoreError::Invariant(String) and BudgetStoreError::Invariant(String) carry conflicts, corruption, misuse and capacity alike, with hundreds of `invariant("...")` sites. Cross-store calls flatten typed errors with `map_err(|error| invariant(error.to_string()))` (participant.rs, caller_wait.rs, budget composite/caller_resume.rs). chio-transaction-passport and chio-finding-market-store-postgres now ignore their `_label`/`_field` parameters, so decode errors no longer name the failing artifact or field.
  - Better: Add structured variants (`Conflict`, `Corrupt { table, reason }`, `CapacityExhausted { bound }`, `#[from] Budget(BudgetStoreError)`), map cross-store errors with `From` impls, and either use or delete the dead label parameters (keep the path in `TransactionPassportError::Input`).
- **test placement and test hooks in production paths** (moderate). Library test builds are slow, and the tested clock path is not exactly the shipped one. Black-box tests coupled to private modules block refactoring, and copy-pasted suites drift.
  - Evidence: About 64K lines of tests compile under cfg(test) inside src (admission_operation_store_tests 35K via #[path], budget_store tests 7.3K). commit_chain.rs:103-107 swaps the production clock for `super::tests::legacy_clock::fixture_clocks` under cfg(test). admission_operation_store.rs:1648 re-exports a test fixture into crate scope. The `admission-test-support` cutpoints sit inside the production capture transaction and native capture response. About 20 near-identical `connection_recovery.rs` files differ only in the store type and probe call.
  - Better: Keep only white-box unit tests in src and move end-to-end durability and recovery suites to tests/ behind a narrow `test-support` feature. Generate the connection-recovery suite with one macro or generic harness. Inject a `CommitClockPolicy` or `CommitObserver` trait object (no-op by default) instead of cfg(test) branches and feature-gated cutpoints.
- **hard lifetime caps without a retirement path** (moderate). Bounds are correct for input validation, but on append-only durable history they become service-lifetime limits that end in permanent fail-closed with no operator procedure.
  - Evidence: Native participant journal: 65,536 events / 64 MiB per authority, 16 authorities (security_participant_state/history/ordered.rs:71, records.rs:101). Caller execution ledger: 64 claims for its lifetime with deletes forbidden (caller_execution_ledger.rs:293, caller_execution_ledger.sql:51). Caller shares: 16,384 per parent including permanent outcome-unknown operations.
  - Better: Pair each bound with a checkpoint or epoch-rotation mechanism (signed snapshot plus archive), and expose occupancy so operators can act before the bound.
- **type-level invariants and API shape** (moderate). Transposed amounts or millisecond/second mixups compile. The allow reason is a deferral note repeated mechanically, not a justification.
  - Evidence: 62 identical `#[allow(clippy::too_many_arguments, reason = "Keep the existing explicit boundary parameters together; changing the owning API is separate...")]`. budget_store append_mutation_event takes 17 positional parameters, six of them adjacent u64 amounts. VerifiedCallerWait binds itself to a transaction with `std::ptr::eq` at runtime (caller_wait.rs:20). Times are bare `u64` milliseconds or seconds mixed in one function (threshold windows divide by 1_000 inline).
  - Better: Use parameter structs or newtypes (`ExposureUnits`, `RealizedUnits`, `UnixMillis`, `UnixSecs`) and a lifetime-branded witness (`VerifiedCallerWait<'tx>` constructible only from `&'tx Transaction`) so the compiler enforces what ptr::eq checks. Then delete the allows.
- **write-protocol consistency in budget_store** (minor). Two writers skip the fence and anchor checks every other writer performs. Fence reasons are discarded, and refunds stall on a wall-clock regression that only affects audit timestamps.
  - Evidence: reaper.rs mark_hold_reserved_until and reserve_invocation_hold lock the connection directly and write in autocommit, without begin_write, and map ConnectionFenced to a generic 'mutex poisoned' (pre-existing pattern, now inconsistent with StoreConnection). begin_write gates every budget mutation on a wall-clock fence (store.rs:288), so an NTP step back blocks releases and reaping.
  - Better: Route every write through begin_write and every lock through `self.connection()`. Gate on the monotonic reading and record max(previous, now) for audit fields.

## Control-plane security pipeline (adapters, event consumer, scheduler)

The slice adds about 22K lines of production code (52K with in-tree tests) for the active-defense pipeline: signed response-authority IPC, verified event ingress, temporal correlation, durable planning and admission, a dedicated-thread TTL scheduler, effect backends and a SIEM outbox. Point checks are strong. Signatures are checked before use, configs are bounded, writes are read back, and there are no unwrap, expect or unsafe calls in production code. The defects are at the pipeline level. One backed-off declassification receipt stops correlation and planning for up to an hour and blocks startup and shutdown drains. A routine producer key rotation permanently wedges the global ingress queue. Readiness probes that do full-history SQLite audits, authority IPC and signing run on every event and every tick. A multi-tenant producer set is accepted while the scheduler only expires one tenant's overlays, and SIEM alerts that exhaust their retries are parked silently. Apart from the native flow adapters used by chio-cli and the authority server, nothing in the repository wires the host, orchestrator, scheduler or SIEM delivery into a binary.

**Design verdict**

Each component is written carefully: point checks are exact, invariants are re-checked after every durable write, and production code has no panics, unwrap or unsafe. The pipeline as a whole falls short of elite production Rust. About 22K production lines ship with no binary wiring for the host, orchestrator, scheduler or SIEM delivery. Readiness, error and concurrency abstractions are each reinvented per module, and cross-subsystem coupling and operational lifecycle (rotation, retention, backoff) were not designed as first-class concerns. The defects above come from these structural gaps, not from local coding mistakes.

**Done well**

- The response-authority IPC is well designed. It checks SO_PEERCRED before parsing, decodes canonically with bounds, uses domain-separated signatures in both directions, binds the response to the request digest, samples freshness after acquiring the replay lock, keeps a bounded replay cache, and enforces one absolute I/O deadline.
- Fail-closed defaults throughout: MissingContextPolicy::Deny, label joins fall back to InformationLabel::Top, unknown approval combinations are rejected, and dispatch ids are rederived and compared before use.
- Idempotency and ack loss are modeled explicitly: load before execute, exact read-back after commit, fencing tokens on every scheduler and effect mutation.
- Bounded collections (BoundedVec, CanonicalBody), checked arithmetic, and catch_unwind around policy callbacks and ticks, with a terminal crash state that cleanup cannot hide.

**Design issues**

- **module organization and scope** (major). A large, mostly unwired subsystem sits inside chio-control-plane and is exported publicly through security.rs's broad re-export list. The surface is hard to review, it is not exercised by any binary, and it couples the control-plane crate's compile time and API stability to an experimental pipeline.
  - Evidence: security/** is 51,924 lines, 22K of them production. External consumers are only chio-cli native_broker.rs (NativeFlowResolver, FlowResolverConfig, StructuredClassificationAdapter) and chio-active-response-authority (the protocol server and client). ProductionActiveDefenseHost, ProductionActiveDefenseOrchestrator, the scheduler worker, SqliteSiemOutbox::deliver_due and migration_evidence have no production caller.
  - Better: Extract a `crates/security/chio-active-defense` crate (or put it behind an `active-defense` feature). Keep only the wired flow adapters in chio-control-plane, and expose the host through one builder-style entry point instead of about 90 re-exported types.
- **readiness abstraction** (major). `Result<(), E>` probes double as deep integrity audits and hot-path liveness checks, have side effects on health state, run under locks, and give different answers through different entry points.
  - Evidence: ensure_ready, ensure_bootstrap_ready, ensure_configured, ensure_recovery_ready and response_coordinator_is_ready across recovery.rs, correlation.rs, worker.rs, registry.rs, teardown.rs and native_evidence.rs. Probes run PRAGMA quick_check, full-table audits, authority IPC and a readiness signature, and registry.rs:91 and :143 run them while holding the registry RwLock write guard.
  - Better: Run one typed startup audit once. Have the worker keep a `Health` snapshot (an enum with causes and timestamps) updated in the background, and make readiness a cheap read of that snapshot. Never perform I/O while holding the registry guard: validate first, then swap with a compare-and-set on `Arc::ptr_eq`.
- **async and thread custody** (major). Hand-built lifecycle machinery with global state is hard to reason about, cannot cancel a running tick, and mixes blocking work into async APIs that callers will reasonably run on a shared runtime.
  - Evidence: worker.rs:236-410 (dedicated OS thread, current_thread runtime, five oneshot channels and two watch channels), custody.rs (global static reaper registry, Condvar polling every 10 ms, join permits), orchestration/teardown.rs (detached teardown retention); a sync tick runs inside `tokio::select!`; `ProductionActiveDefenseHost::start` (async) does sync SQLite and sink I/O (teardown.rs:715); `deliver_due` (async) uses a std Mutex<Connection>; `resume_incomplete_until_drained` uses std::thread::sleep with up to a 1 h budget.
  - Better: Run a supervisor task that drives `spawn_blocking(tick)` with a `tokio_util::sync::CancellationToken` and owns its `JoinHandle` in a struct whose `Drop` cancels. Make sync work explicit (`spawn_blocking` inside the async host methods). Drop the global reaper in favor of structured ownership.
- **error handling** (moderate). A single coarse error type (kind plus code) is used inside the modules as well as at the port boundary, so the cause of almost every failure is discarded. Operators cannot tell a corrupt row from a key mismatch from a clock fault, which is exactly what the wedge findings need for diagnosis.
  - Evidence: 281 `map_err(|_| ...)` sites and 279 bare `PortError::integrity_failure()` in production files; `Result<Self, String>` constructors (protocol.rs:151, client.rs:47); `ActiveDefenseRuntimeReadiness::ensure_ready -> Result<(), String>` (security.rs:117); readiness errors built with `format!` (active_response/config.rs:27).
  - Better: Use per-module `thiserror` enums with `#[source]` internally and convert to `PortError` only at trait boundaries, keeping wire redaction there. Replace String config errors with typed enums.
- **duplication across adapters** (moderate). The same protocol is copied six times, so a fix to one backend's ack-loss or version logic does not reach the others. A magic decode bound is repeated, and work is repeated per event.
  - Evidence: effect_port/{containment,egress,suspension,throttle,issuance,alert}.rs repeat the load-snapshot, compare-version-hash, predict, apply, compare-prediction and installed-hash skeleton. There are 18 copies of `UntrustedJsonText::from_wire(.., 64 * 1024 * 1024).and_then(decode_signed).map_err(with_source(..))`, whose 64 MiB bound is dead because CanonicalBody caps at 1 MiB. The event body is re-parsed 3 to 4 times per event (verification.rs:140, correlation.rs:140 and :312, chio-quarantine).
  - Better: Define `trait OverlayKind { type Snapshot; type Contribution; fn predict_apply(..); fn predict_remove(..); fn version_hash(..); }` with one generic `OverlayBackend<K: OverlayKind>`. Add a single `decode_canonical::<T>(&CanonicalBody, PortErrorKind)` helper. Carry the parsed `SecurityEventBody` inside the verified record instead of re-decoding it.
- **configuration validation** (moderate). Cross-field invariants are checked in several places and incompletely, and operational changes such as key rotation and retiring an executor generation are not representable.
  - Evidence: ProductionActiveDefenseConfig is a struct with all-pub fields (orchestration.rs:45-56), validated piecemeal in new_with_lifecycle (787-798) and again in ProductionCorrelationConsumer::new (correlation.rs:213-225). There is no tenant cross-check, no receipt-producer policy pin, and one key per producer. SecurityDurability (durability.rs) is a caller-declared claim, not something derived from the stores.
  - Better: Use a `ValidatedActiveDefenseConfig` newtype produced by `TryFrom<RawConfig>` that checks every cross-field invariant once. Give producer keys validity windows. Derive durability from the store handles (for example a `Persistent<SqliteSecurityStateStore>` typestate).
- **test placement and naming** (minor). Test bulk inflates the crate, makes navigation and grep slow, and couples tests to private internals.
  - Evidence: 30,137 of 51,924 lines are tests inside src/, with 180 files under tests directories, 28 `#[path = ..]` attributes, and sentence-length filenames such as adapters/effect_port/tests/alert_and_throttle_are_probed_but_cannot_make_an_incomplete_router_ready.rs that break tooling (ugrep reports 'File name too long').
  - Better: Move behavioral tests to `crates/.../tests/` against the public API, behind a `test-support` feature for fixtures. Keep unit tests next to code with short names, and drop the #[path] indirection.
- **cfg sprawl and API ergonomics** (minor). Platform gating is scattered and easy to get wrong. A long positional constructor invites argument transposition between same-typed `Arc<dyn ..>` parameters.
  - Evidence: Per-field and per-statement `#[cfg(target_os = "linux")]` in active_response_authority/{protocol,client,transport}.rs; `ProductionActiveDefenseHostConfig::new` with 12 positional arguments under `#[allow(clippy::too_many_arguments)]` whose reason string narrates process history (orchestration.rs:88-91); glob imports `use chio_security_types::ports::*` (response_simulation.rs:6-7).
  - Better: Use `mod linux;` and `mod unsupported;` behind one cfg with a shared surface, a builder or a named-field config struct, and explicit imports.

## Control-plane trust control, CLI and products

Static review of chio-control-plane outside src/security (trust_control routes and ingress, keyring_runtime, evidence_export, policy, durable_admission, server_transport), chio-cli (process_host runner/socket/child/container/evidence, mcp provision and cage policy, supervise credentials, input, dispatch, doctor), chio-api-protect, chio-proof-room, chio-wall, economy and observability deltas, plus all 43 new unsafe sites in chio-cli. The slice is security-literate: descriptor-relative file access, pidfd signalling, async-signal-safe pre_exec closures, fallible clocks mapped to 503, signed-payload rehash after package parse, and redacting untrusted-JSON errors are applied consistently. No P0 or P1 was established. Four issues remain: a pre-authentication 128 MiB JSON DOM parse added in front of the trust-control receipt routes, a cage launch-policy trust root that accepts weak Ed25519 keys with non-strict verification (the sibling of the FROST and sender-constraint threads), a pinned remote capability authority that ignores the kernel authority clock, and non-zeroized seed handling in the new keyring handoff. Design debt is concentrated in chio-cli structure (binary-only crate, path-include module tree, glob re-exports, parameter-soup dispatch), a stringly god error type shared from a library crate, eight divergent private-file custody implementations, and blocking kernel/SQLite work on tokio workers.

**Design verdict**

The new code in this slice is careful at the syscall and trust-input level and is noticeably better than typical production Rust on fail-closed discipline, descriptor hygiene and redaction. It falls short of elite structure: chio-cli is a 117K-line binary-only crate assembled from 209 `#[path]` modules and glob re-exports, the shared error type is a stringly god enum living in a library crate, private-file custody is reimplemented about eight times with diverging rules, and kernel and SQLite work runs synchronously on tokio workers. Most of the 43 new unsafe blocks are correct but avoidable given rustix is already a dependency.

**Done well**

- Descriptor-relative filesystem access with identity re-checks: runner/socket.rs (openat/O_PATH/O_NOFOLLOW, dev+ino leases), keyring_runtime.rs read_private_file (pre/post fstat identity), evidence_export/package_io.rs per-component openat walk
- Process control via pidfd (ProcessFd::kill, wait4 reaper in spawn_blocking), PR_SET_PDEATHSIG with getppid race check, cancellation-safe Guard that kills on drop; pre_exec closures do no allocation or locking
- All 43 new chio-cli unsafe sites carry SAFETY comments whose invariants match the code; returned descriptors are wrapped in OwnedFd/File immediately and libc return values are checked
- Fallible clock reads throughout trust_control (ClockError mapped to 503) and remote-authority lifecycle checks that take the maximum of observed times, so stale caches cannot extend issuer trust
- Evidence package import re-hashes the parsed payload against the signed envelope (envelope.rs verify_payload), which neutralizes the hash-then-reread pattern in package_read.rs
- UntrustedJsonText with redacting Debug/Display and duplicate-key rejection applied at HTTP ingress, JSON-RPC (chio-link), dead letters and CLI input
- Secrets delivered via systemd credentials and sealed read-only memfd descriptors (supervise/descriptor_credentials.rs) rather than argv; clap secret args use env with hide_env_values

**Design issues**

- **module organization** (major). Glob inheritance hides real dependencies, defeats dead-code and unused-import lints (hence the allows), makes every module able to reach every other, and forces whole-crate recompiles. The binary-only layout blocks reuse and integration testing of command logic.
  - Evidence: crates/products/chio-cli has no lib target; src/bin/chio.rs is `include!("../main.rs")`; main.rs pulls in the tree with 209 `#[path]` attributes and re-exports roughly 200 symbols through `#[allow(unused_imports)] pub(crate) use` blocks so that 135 files can start with `use super::*;`. Large files: cli/dispatch/proof/fixture.rs 6263 lines, cli/chio/dispatch/pheromone/iroh_mount.rs 3353, cli/dispatch/proof.rs 3266, cli/mcp/provision.rs 1962, cli/runtime.rs 1936, cli/dispatch/finding/operator.rs 1901. Test trees live in src: cli/dispatch/finding/unit_tests.rs 2141, cli/session/tests.rs 1955, and control-plane trust_control/service_runtime/*_e2e_tests/** compiled into the library test target.
  - Better: Split into a `chio-cli` lib crate with an explicit `mod.rs`/`foo.rs` tree and real `use` paths, plus thin per-domain modules or crates (process, mcp, trust, proof, finding). Keep main.rs to parse-and-dispatch. Move e2e and multi-thousand-line unit suites to tests/ so they link against the public API.
- **command dispatch pattern** (moderate). Positional Option/bool soup is easy to transpose silently (two adjacent `Option<&Path>` swap without a type error), and a single exit code prevents scripts from distinguishing denial, input and transport failures.
  - Evidence: cli/dispatch/mod.rs run() clones 12 global options and destructures each `Commands` variant into positional calls such as `cmd_run(&policy, &command, agent_public_key, json_output, receipt_db, revocation_db, authority_seed_file, authority_db, budget_db, session_db, control_url, control_token)`; chio-wall/src/commands/evidence.rs:60 calls `evidence_export::cmd_evidence_export` with 14 positional arguments including eight `None` and two bare bools; 27 `#[allow(clippy::too_many_arguments)]` in chio-cli; every failure exits with status 1.
  - Better: Introduce a `GlobalContext` built once from `Cli`, give each subcommand an args struct implementing `trait Run { fn run(self, ctx: &GlobalContext) -> Result<ExitCode, CliError> }`, use options structs or builders for export/serve entry points, and map error classes to distinct exit codes.
- **error handling** (major). Stringly errors cannot be matched, tested or mapped to registry codes reliably, and a library error named for the CLI couples every consumer to CLI presentation.
  - Evidence: crates/platform/chio-control-plane/src/error.rs defines `pub enum CliError` with about 30 `#[from]` variants and `Other(String)` in a platform library that chio-cli, chio-mcp-remote and chio-wall reuse. `cli_other_error(format!(..))` appears about 717 times in control-plane and about 1617 times in chio-cli. Control flow depends on variants by accident, for example keyring_runtime.rs load_optional_authority_seed_handoff matches `CliError::Io(NotFound)` to mean 'absent'. Good counterexamples in the same PR: json_ingress.rs InputError, active_defense_migration.rs ShadowMigrationError, proof-room UploadVerificationError, runner/child.rs LaunchFailure.
  - Better: Per-module thiserror enums with `#[source]` causes, converted at the command boundary through the existing RegisteredSourceError/registry mechanism; rename the library type (for example ControlPlaneError) and keep CliError as the presentation wrapper in chio-cli.
- **duplication of private-file custody** (major). Each copy encodes slightly different rules (owner checked or not, exact vs maximum mode, symlink-following chmod, nlink handling after crash between link and unlink), so hardening applied to one is missed in the others.
  - Evidence: keyring_runtime.rs read_private_file/atomic_write_private_file (nlink 1, mode & 0o177, no owner check); signing_custody.rs read_private_signing_custody; durable_admission.rs PreparedPrivateDirectory::write_new_secret; supervise/credentials.rs and descriptor_credentials.rs (uid plus mode & 0o077 plus systemd exception); mcp/provision.rs open_regular_file (mode == 0o600 exactly) with path-based chmod; dispatch/finding/operator.rs write_secret_new/write_exact_or_new (hard-link publish); active_defense_migration.rs write_atomic; process_host/diagnostics.rs read_private.
  - Better: One shared crate (for example chio-secure-fs) exposing descriptor-relative `open_private(dir, name, Policy)`, `create_new_private`, and `atomic_publish` with an explicit `Policy { max_mode, owner, nlink, max_bytes }`, returning `Zeroizing` buffers for secrets; delete the local helpers.
- **async correctness** (moderate). Blocking work on tokio workers stalls unrelated requests, timers and health checks, and the single kernel mutex serializes all mediation behind disk latency.
  - Evidence: chio-api-protect proxy/mediated.rs:341 holds `mediation_kernel.lock().await` (tokio Mutex over the whole ChioKernel) while calling `reserve_caller_execution_blocking`; mediated/authenticated.rs:74 and :124 call `start_caller_execution_with_credentials_blocking` and `reconcile_authenticated_caller_execution_blocking` directly on the worker; trust_control handlers call SQLite synchronously (finding_handlers.rs handle_upload_finding_dependency put_recipe_blob, authority_handlers.rs SCIM registry.save); proof-room server.rs proof_room_upload_verify writes up to 32 MiB and verifies synchronously inside an async fn. trust_control/frost/coordinator.rs already uses a `blocking(..)` helper correctly.
  - Better: Run kernel and store calls through `spawn_blocking` with `Mutex::lock_owned`, or a dedicated kernel actor thread fed by an mpsc channel; apply the frost coordinator pattern uniformly.
- **typed verification** (moderate). Missing keys index to Null and compare equal to other missing keys, so structural drift fails silently or only through incidental inequality; panic-freedom depends on ordering of prior checks.
  - Evidence: process_host/run_evidence/verify_calls.rs and verify.rs verify signed run evidence by indexing `serde_json::Value` (`evidence.runner["plan"]["workers"]`, `receipt.metadata[..]["chio_runtime"]["verified_swarm_request_binding"]`, `input[field] == call.request[field]`) and `caps[process]` map indexing whose safety depends on earlier set-equality checks.
  - Better: Deserialize runner plan, snapshots and receipt metadata into typed structs with deny_unknown_fields, compare typed fields, and use `.get()` with typed errors instead of `Index`.
- **clock injection** (moderate). Several independent time sources inside one service make clock-custody guarantees unverifiable and invite the authority-clock divergence Codex already reported in chio-process.
  - Evidence: trust_control calls the free function `unix_timestamp_now()` (SystemClock, underwriting_and_support/policy_support.rs:950) with a repeated four-line match in about 33 handlers, finding_status_handlers.rs adds a separate `status_clock_now`, TrustServiceState carries `finding_challenge_clock`, the keyring composition carries its own clock, and the pinned remote authority hardcodes SystemClock.
  - Better: A single `Arc<dyn Clock>` on TrustServiceState and an axum extractor (for example `Now`) that reads it and maps ClockError to 503; thread the same clock into every authority and store constructor.
- **duplicated product modules** (minor). Parallel twins drift and double the review and test surface for every change.
  - Evidence: chio-proof-room/src/bundle_a.rs (989 lines) and bundle_b.rs (806), fixture_a.rs (1254) and fixture_b.rs (1374); this PR's diff stats are mirror images (144/165 and 165/144).
  - Better: One implementation parameterized by a profile type or trait, with the A/B differences expressed as data.
- **unsafe usage** (minor). All sites are sound as written, but most duplicate safe wrappers that rustix (already a dependency) provides, and raw `libc::close` in doctor probes bypasses RAII.
  - Evidence: 43 new sites in chio-cli: runner/child.rs (pidfd_open, pidfd_send_signal, wait4, pre_exec), runner/socket.rs (openat, unlinkat, mkdirat, geteuid), doctor/security/platform.rs (uname, prctl, memfd_create, raw libc::close), supervise/* (geteuid, fcntl, kill, signal/raise), cage_policy.rs (F_DUPFD_CLOEXEC). container.rs:164 SAFETY text mentions getgid that is not called.
  - Better: Use rustix::process::pidfd_open/pidfd_send_signal, rustix::fs::{openat, unlinkat, mkdirat}, rustix::process::{geteuid, getrlimit, setrlimit} and OwnedFd for probe descriptors; keep unsafe only for `pre_exec` registration.

## Secret broker, keyring, secure IPC, hardware custody

The slice adds four security crates: chio-secret-broker (43.7K src lines, about 18K of them tests under src/), chio-keyring (about 13K), chio-secure-ipc, and changes to chio-custody-hw. The broker's custody engineering is strong: descriptor-anchored file checks, sealed memfd key delivery, strict canonical decoding, client-side SO_PEERCRED pinning and an idempotent durable attempt state machine. Its daemon supervision, however, decides fatal-versus-client by stringly-typed error variant. As a result, a capability for a disabled credential, or an authority hiccup during a privileged audit, terminates brokerd for every tenant. The keyring has four P1s: the macOS ACL custody check fails open (the broker inherits it), it verifies signatures non-strictly and accepts weak Ed25519 lifecycle keys, a witness signs forks despite holding conflicting gossip, and a late witness signature after activation makes the store unopenable. Secondary issues are secret residue from Vec growth in the outbound HTTP head, unbounded retention of mobile challenges until capacity is exhausted, and widespread duplication of IPC and file-custody primitives that chio-secure-ipc was created to own.

**Design verdict**

Line by line, the security engineering is above typical production Rust. Custody is anchored to descriptors, unsafe is denied crate-wide with justified exceptions, parsers are bounded and zeroizing, and signing is domain-separated over canonical bytes. The architecture is not at that level. Error handling is stringly typed, yet the same variants drive availability decisions. The crates hand-copy the IPC, framing, deadline and file-custody primitives that chio-secure-ipc and chio-sqlite-file-identity were created to own. Core paths are long linear functions with repeated compensation blocks instead of RAII guards or typestate. Roughly 40% of the broker's src/ is test code. The essential production code is closer to 20K lines than 36K.

**Done well**

- Descriptor-anchored custody: DurableBrokerDatabaseFile walks from / with openat+NOFOLLOW, retains the parent descriptor, rebinds dev/inode, and inspects ACL xattrs on the fd (secret-broker sqlite.rs:356-690). The keyring additionally brackets sqlite3_open with SQLITE_FCNTL_HAS_MOVED.
- Sealed key delivery: read-only fd, F_GET_SEALS requiring SEAL|SHRINK|GROW|WRITE, fstat owner and exact 32-byte length, trailing-byte check, F_DUPFD_CLOEXEC adoption with single retirement (encrypted_blob_backend.rs:114-161, chio-secure-ipc lib.rs:393-425).
- The broker IPC client pins the daemon pid/uid/gid with SO_PEERCRED and re-checks socket inode stability around connect (ipc_client.rs:407-452).
- Capability and request proofs use verify_strict plus weak-key rejection. Every decode re-encodes and requires exact canonical bytes. IPC request parsing uses bounded, pre-reserved zeroizing buffers (service/wire.rs).
- Durable attempt state machine with deterministic ids, a (key, nonce) uniqueness table, never-redispatched unknown_outcome, and startup reconciliation that drains durable receipts before querying live authority.
- Crate-level deny of unsafe_code, indexing_slicing, panic and as_conversions outside tests. Each unsafe block carries a SAFETY comment stating a checkable invariant.
- The mobile challenge store consumes atomically and compare-and-sets the App Attest counter inside one IMMEDIATE transaction.

**Design issues**

- **Error model drives availability** (major). Variants are chosen ad hoc at each call site, and two endpoints apply different variant-based rules for deciding what kills the daemon. That is the root cause of the P1 and P2 crash paths. format!-built messages discard source chains, and redaction is a post-hoc rewrite (BrokerError::redacted).
  - Evidence: chio-secret-broker lib.rs BrokerError (11 String-payload variants); missing_credential -> Storage (encrypted_blob_backend.rs:412); classify_broker_ipc_handler_result (service/ipc/response.rs:12-36); privileged_audit.rs:745-760 allowlist; chio-keyring KeyringError::StateInvariant(&'static str) covering about 100 conditions, and the IPC Failure { reason: String }
  - Better: Use layered typed errors (CredentialLookupError::{NotFound, Disabled, Corrupt}, AuthorityError::{Unavailable, Misbound}) with #[source], plus one `fn disposition(&self) -> Disposition { Client, Transient, Fatal }` shared by every endpoint, with the wire diagnostic code derived from the kind rather than from the message.
- **Duplicated security primitives across crates** (major). Fixes land in one copy only. The keyring listener lacks the peer authentication and lifecycle lock that secure-ipc has, and the keyring witness lacks the gossip check that its verifier copy has. The broker depends on chio-keyring only for a Darwin ACL helper, so the keyring ACL bug spreads to the broker.
  - Evidence: Socket lifecycle/identity/cleanup in chio-secure-ipc lib.rs:104-352, broker service/ipc/lifecycle.rs, broker privileged_audit.rs:1335-1450, and keyring ipc.rs:1455 (weaker); deadline IO in service/ipc/deadline.rs, privileged_audit.rs:880-975, rustls_transport.rs DeadlineTcpStream and host_https.rs DeadlineTcp; length-prefix framing in secure-ipc read_bounded_frame, wire.rs read_frame_with_limit and read_bounded_sensitive_frame, privileged_audit.rs read_frame, keyring ipc.rs read_canonical_frame; file custody in broker sqlite.rs, keyring lib.rs, custody-hw mobile_challenge/sqlite.rs DatabaseCustody, host_https.rs private_bytes
  - Better: Make chio-secure-ipc the single owner: a SecureUnixListener with a PeerPolicy (exact pid/uid/gid, uid-only, uid+gid) and socket mode/group parameters, one generic AbsoluteDeadlineIo<S>, one framing codec parameterized by limit with a zeroizing buffer. Move trusted-path walking and ACL FFI into a small chio-secure-fs crate that the broker, keyring and custody-hw all use.
- **Control flow size and compensation by copy** (major). Every new early return must remember to release the claim. Phase boundaries (resume, capture, revalidate, commit, dispatch, finalize) are implicit, and include! fragments have no privacy boundary or name.
  - Evidence: service/custody/execution.rs execute_inner (lines 169-783, about 615 lines) with 9 copies of `release_captured_attempt_claim` + `execution_failure_after_capture_release` and 6 calls to require_migrations_enforced; keyring sqlite.rs include!s sqlite_parts/part_01.rs (1451 lines) and part_02.rs (579 lines)
  - Better: Use an RAII CapturedClaim guard that releases on Drop unless commit() consumes it. Split execution into phase functions returning typed results, and use typestate for attempt records (Registered -> Prepared -> Captured -> Committed) so illegal transitions do not compile. Replace include! with named submodules (schema, witness_signatures, activation, receipts, loaders).
- **Zeroization discipline** (moderate). Marker impls assert a property the compiler does not check, and growth leaves unscrubbed heap copies, which contradicts the README claims.
  - Evidence: Growing Zeroizing<Vec> in rustls_transport.rs:216 and host_https.rs:186; serde-grown Vec<u8> for the audit reference head (privileged_audit.rs:83); manual `impl ZeroizeOnDrop for X {}` markers (daemon.rs:160, provision.rs:324, service/wire.rs:110, 436, 613); keyring seed fill(0) on dead buffers (service.rs:123-132); TenantKey::from_bytes(*bytes) stack copy (encrypted_blob_backend.rs:51)
  - Better: Derive ZeroizeOnDrop with #[zeroize(skip)] on non-secret fields. Use one fixed-capacity SecretBuf that refuses to grow (the existing ZeroizingCanonicalJsonWriter pattern) for every secret-bearing encoder and decoder.
- **Key derivation** (moderate). One raw key is used for two primitives with no derivation, and the same master key covers every tenant scope. Domain separation exists only as an HMAC prefix.
  - Evidence: encrypted_blob_backend.rs:383 keys HMAC-SHA256 for the reference index with tenant_key.as_bytes(); chio-store-sqlite encrypted_blob.rs:353 uses the same 32 bytes as the ChaCha20-Poly1305 key
  - Better: Derive labelled subkeys with HKDF-SHA256 (aead, reference-index, per-tenant) at load, and zeroize the master after derivation.
- **Inconsistent signature verification strictness** (moderate). Security depends on every configured key being non-weak, and nothing validates that at config load. The keyring P1 is the concrete consequence.
  - Evidence: Broker capability.rs and proof.rs use verify_strict, while authority_ipc.rs:678/714/763/839, provision.rs:147/267, privileged_audit.rs:308/341 and all of chio-keyring use permissive verify
  - Better: Use a single crate-level verify helper that always calls verify_strict, and reject is_weak_ed25519 keys when parsing config and policy.
- **Blocking in async and per-call history work** (moderate). Executor threads stall on child teardown, and hot-path latency grows with history size.
  - Evidence: native_mcp.rs:316 calls blocking server.shutdown() inside an async fn, and PreparedDelivery::drop blocks (native_mcp.rs:49-55); keyring WitnessedActivationSet::verify_complete rebuilds Merkle prefixes (O(n^2)) under the store mutex on every sign or append; DurableBrokerDatabaseFile::validate walks from / on every credential lookup (encrypted_blob_backend.rs:379)
  - Better: Use spawn_blocking or an async shutdown for confined children. Verify incrementally from the persisted head, and revalidate path bindings at open and at write boundaries only.
- **Test placement and public surface** (moderate). The library build carries test-only code and cfg(test) plumbing. Internals freeze into the public API, and the TCB listener's peer check is untested in its own crate.
  - Evidence: About 13.5K lines of test files plus about 4.9K lines of inline test modules under chio-secret-broker/src versus 2.6K in tests/; chio-keyring re-exports every module with `pub use x::*`; chio-secure-ipc has no test of authenticate or socket replacement, and `listener_refuses_same_process_and_non_private_parent` asserts a bare is_err without exercising the same-process rule
  - Better: Move process-boundary suites to tests/ behind a test-support feature. Curate re-exports and keep signed-envelope fields private behind constructors. Add positive and negative SO_PEERCRED tests to chio-secure-ipc.
- **Dependency and lint hygiene** (minor). Two TLS crypto providers are linked, versions drift, and the lint justifications are not invariants.
  - Evidence: chio-secret-broker Cargo.toml pins rustls with the ring provider while the workspace rustls uses aws_lc_rs; it declares subtle, libc, webpki-roots and rcgen locally instead of workspace = true. The allow reasons at daemon.rs:339 and authority_ipc.rs:803/853 narrate history ('changing the owning API is separate...'). nonce_store.rs adds a one-line `retained_replay_outcome` bool wrapper.
  - Better: Use workspace deps with feature selection, replace the too_many_arguments allows with parameter structs, and inline the trivial wrapper.

## Cage sandbox, quarantine, decoy, flow and security kernel

The cage stack (chio-cage, chio-cage-init, chio-cage-plan) is carefully engineered and fails closed on almost every path. The serious gaps are policy-semantic: forbidden directories do not protect their descendants from hard-link aliases (P1), and the fd-255 execveat rule does not constrain absolute pathnames, so the documented exec guarantee is false. Runtime-integrity and ownership assumptions also break in realistic deployments: shared objects without x bits skip the writability check, admission-created write files are unusable under a root host, and datagram broker sockets are not rejected. In the active-defense crates, four of the six decoy surfaces are never fed to the detector, so they cannot trigger. Spot checks of chio-flow label propagation, quarantine effect-journal recovery and approval expiry, security-kernel hook error handling (errors deny; production wires MissingContextPolicy::Deny), and the active-response-authority accept and worker loop found no fail-open path. The quarantine, decoy, flow, security-kernel and security-types crates were covered by targeted reads, not line by line.

**Design verdict**

The cage stack (chio-cage, chio-cage-init, chio-cage-plan) is unusually careful systems code: closed vocabularies, canonical re-encoding checks on every wire artifact, sealed memfds, pidfds, openat2 strict resolution, no pre_exec, KILL_PROCESS default with an arch check, and a SAFETY comment on every unsafe block. The weaknesses are structural rather than sloppy: about 100 raw libc unsafe blocks where rustix would give typed safe wrappers, pervasive per-field cfg(target_os) instead of a platform boundary, stringly-typed digests revalidated by four copies of the same validator, a launch path that busy-polls and blocks the calling thread, and a profile digest that silently changes between compile and launch. It is close to elite in intent and below it in API shape. The active-defense crates read the same way: forbid(unsafe_code), errors consistently mapped to deny, and zeroized key material, with a fail-open configuration variant and include! fragments as the main style debts.

**Done well**

- Closed wire decoding: deny_unknown_fields everywhere, FdPurpose decoded through an empty-struct shadow enum so unit variants cannot smuggle sibling fields (chio-cage-plan/src/model.rs:173-209), SeccompProfilePlan decoded through try_from into the same validator (seccomp_plan.rs:178-368)
- Canonical round-trip checks on the launch envelope (chio-cage-init/src/bootstrap.rs:93-101) and every status record (chio-cage/src/launch/linux.rs read_status)
- Helper executed from the retained descriptor via /proc/self/fd with env_clear and no pre_exec callback; pidfd self-transfer, SO_PEERCRED parent binding, PDEATHSIG armed after the final credential change and re-checked with getppid
- Correct x86_64 and aarch64 syscall numbers, KILL_PROCESS mismatch action, explicit plan-vs-host architecture check, prlimit64 pinned to pid 0, RLIMIT_NOFILE hard limit below the fd-255 exec slot
- Bounded ELF program-header and dynamic-table parsing with checked arithmetic; clippy indexing_slicing and as_conversions denied with reasoned allows; mutation feature is compile_error in release

**Design issues**

- **unsafe surface and FFI** (major). Every raw call is a hand-audited ABI site inside the TCB, and the private extern block can drift from libc's signatures (for example socklen_t width) without a compile error. The cmsg packing in descriptor_transfer.rs reimplements what rustix::net::{sendmsg, recvmsg, SendAncillaryBuffer} already provides safely.
  - Evidence: chio-cage-init/src has 61 unsafe blocks and chio-cage/src 41 (fcntl, dup3, close_range, prctl, setres*id, getsockopt, sendmsg/recvmsg with hand-built cmsg buffers, pidfd_open, waitid, memfd_create); chio-cage/src/linux.rs:85-104 redeclares syscall, geteuid, fchmod, fchown, fgetxattr, getsockopt in a private extern block even though libc is a dependency of the same crate
  - Better: Use rustix (already a workspace dependency, used by chio-active-response-authority) for openat2/ResolveFlags, pidfd_open, pidfd_send_signal, waitid(P_PIDFD), close_range, memfd_create plus seals, prctl, setresuid/setresgid, SCM_RIGHTS, and getsockopt(SO_PEERCRED/SO_TYPE). That removes most unsafe blocks and the private extern block, leaving unsafe only for ptrace and execveat.
- **platform abstraction** (moderate). Linux-only state is threaded through portable types field by field, so every new method needs two hand-written branches and the non-Linux surface is easy to get subtly different from the Linux one.
  - Evidence: chio-cage/src/launch.rs (EnforcedChild has four cfg(target_os) fields and every method has paired cfg branches), lib.rs CompiledCage/RetainedResource/BrokerIpc cfg'd fields, `#[path = "launch/linux.rs"] mod platform;`
  - Better: Make the public types thin wrappers over a `platform::Inner` that is a Linux struct on Linux and an uninhabited enum elsewhere (so non-Linux methods are `match self.inner {}`), and keep all cfg in one `platform` module.
- **typestate and digest stability** (moderate). The profile digest an operator or policy observes after compile() is not the digest that launches or appears in enforcement receipts, and the transition is validated only by a partial field comparison. The bootstrap in cage-init (bootstrap.rs child_main, ~220 lines) enforces its NNP, Landlock, seccomp, exec ordering only by statement order.
  - Evidence: CompiledCage::bind_target_stdio (chio-cage/src/lib.rs:685-715) rewrites fd_table, profile.fd_table_digest, profile_digest, and plan_digest at launch; CageReceiptSigningContext::with_launch_bindings (receipt.rs:239-257) accepts any new profile digest as long as manifest/helper/target bindings match; CompiledCage::plan() is documented as not yet a wire plan
  - Better: Split CompiledCage<Unbound> and CompiledCage<StdioBound> (or bind stdio inside compile) so each state has one immutable digest, and express cage-init stages as consuming types (Received -> Verified -> Remapped -> IdentityApplied -> Confined) whose only path to exec goes through Landlock and seccomp.
- **blocking lifecycle API** (moderate). A cage launch stalls a tokio worker for the whole launch timeout and Drop can block indefinitely. PR_SET_PDEATHSIG ties target lifetime to whichever caller thread spawned it, which the README pushes onto callers.
  - Evidence: launch/linux.rs:395 and :1216 loop with std::thread::sleep(2ms) and a fresh 64 KiB vec per read_status call for up to 60 s; EnforcedChild::drop blocks up to 4 s and transfer_child_custody_with (launch.rs:993-1005) can loop forever; chio-mcp-remote calls it from an axum handler (http_service.rs:558 -> spawn_session -> StdioMcpTransport::spawn -> chio_cage::launch_prepared) on a tokio worker
  - Better: poll(2) on the status socket and the helper pidfd instead of sleeping, reuse one buffer, and run launches and reaping on a dedicated long-lived launcher thread owned by chio-cage (exposed through a sync handle and an async wrapper). That also makes the PDEATHSIG owner thread explicit.
- **stringly-typed digests and duplicated validators** (moderate). Every digest field is a String that each consumer must remember to validate, and parent and child validators can drift.
  - Evidence: validate_sha256_hex (chio-cage-plan/src/model.rs:416), validate_digest (enforcement.rs:418), validate_digest (chio-cage-init/src/validation.rs:619), validate_digest (chio-cage/src/receipt.rs:546); validate_identifier twice; hash_file (cage-init) and read_stable_content (cage linux.rs) are two stable-hash implementations with different change detection; plan-shape checks are copied between validate_envelope and validate_compiled_plan
  - Better: Add a Sha256Hex newtype with a validating Deserialize in chio-cage-plan, one shared plan-shape validator used by both parent and helper, and one streaming hasher (sha2::Sha256 updated per 64 KiB read, instead of buffering up to 256 MiB in hash_file and read_stable_content).
- **public API surface** (minor). A trust-root-free persistence function sits beside the trusted one, test conformance hooks ship in release, and the re-export list obscures what the crate owns.
  - Evidence: persist_signed_cage_receipt and verify_signed_cage_receipt accept any self-embedded signer (receipt.rs:367 and 448) and have no production caller; validate_cage_target_fd_binding_production_paths and CageTargetFdBindingMutation are doc(hidden) pub in release builds (launch.rs:46-92); lib.rs:1449-1567 re-exports ~70 items one `pub use` per line; run_cage_init returns Result<(), _> although success never returns
  - Better: Keep only the _with_trusted_key variants public (or require a TrustRoot argument), move conformance hooks behind the enforcement-mutants feature or into chio-test-support, collapse the re-exports into one grouped `pub use chio_cage_plan::{...}`, and make run_cage_init return Result<Infallible, BootstrapFault>.
- **error handling** (minor). The closed wire code is right, but errno and the child's stage are discarded, so field failures are hard to diagnose, and post-filter failures lose their record to SIGSYS.
  - Evidence: BootstrapFault { code, stage: &'static str } built from map_err(|_| ...) at nearly every call in chio-cage-init; parent maps every child failure stage to "helper_failure" (launch/linux.rs failure arm); errors after seccomp install call is_status_socket -> getsockopt, which the target filter kills
  - Better: Keep the closed code on the wire but carry the raw errno and the child stage in a non-wire diagnostic field for tracing, and pre-resolve the status fd before installing seccomp so the failure path needs only write(2).
- **fail-open configuration knob and include! fragments in active-defense crates** (minor). A public permissive variant in a security crate is one constructor argument away from fail-open, and the .inc fragment hides part of ResponseExecutor from tooling, rustdoc source links, and module privacy.
  - Evidence: MissingContextPolicy::Allow (crates/security/chio-security-kernel/src/lib.rs:50) makes every guard allow when the authoritative security context is missing (for example tripwire.rs:286-299); production uses Deny (chio-control-plane/src/security.rs:193-235). chio-quarantine/src/executor.rs:1377 pulls ~470 lines of impl methods in with include!("executor_parts/effect_journal_methods.inc")
  - Better: Make missing context always deny (or gate Allow behind a test-only feature), and move the effect-journal methods into a child module with its own `impl<S, E, R, A> ResponseExecutor<S, E, R, A>` block.

## Protocol edges, provider adapters and guards

Ingress hardening in crates/protocol and crates/guards is broad and mostly sound: bounded readers, duplicate-key rejection, strict DPoP, signed durable fences and injected clocks are applied consistently in chio-mcp-remote, chio-mcp-adapter and the guard crates. The most serious gaps are pre-existing fail-open stream gates in the OpenAI Responses and Cohere adapters (P1, mitigated only because no production binary consumes them yet). New issues introduced or left as siblings of resolved Codex threads: ACP edge and proxy still parse unsigned peer envelopes with signed-number rules (the proxy poisons its transport on 1e-05), remote MCP durable records are written without the 8 MiB bound used to reopen them, a dead session worker leaves POST streams and the session lock wedged, the unauthenticated MCP rate limiter can be driven into rejecting every new client, and external-guard resilience primitives deny all calls during a backward wall-clock step. Design debt is concentrated in include!/.inc fragment modules, a duplicated eight-crate provider family with two competing traits, ad hoc decoder selection, and blocking SQLite I/O on async workers.

**Design verdict**

The slice is defensively written and well above typical production Rust on input bounding and fail-closed defaults, but it falls short of elite on structure: large include!-assembled modules, a protocol crate built on a CLI error type, stringly-typed persisted state, blocking I/O inside async handlers, and an eight-crate provider family whose copies have already drifted on security fixes. The decoder API is good, but leaving the numeric contract to each call site has produced the same interop bug in A2A, ACP and data-guards.

**Done well**

- UntrustedJsonText is a single ingress choke point: size and UTF-8 checks before parsing, duplicate-key rejection at every depth, serde's recursion limit, and error types whose Display and Debug never echo input.
- chio-mcp-adapter ingress budget measures JSON structure (nodes, decoded text, wire bytes) before DOM allocation and releases it through RAII reservations; framing refuses to drain an oversized tail.
- Trusted-proxy identity is explicit: fixed peer set plus a constant-time shared secret, single-valued bounded headers, and identity headers stripped from untrusted requests.
- DPoP and sender-constraint verification use strict Ed25519 with weak-key rejection at registration, decode and runtime, and replay custody bound to the expiry window.
- Session-credential calls are fenced with signed durable records and an explicit delivery acknowledgement before the next call, which is a sound exactly-once-delivery design.
- Clock injection replaced SystemTime in edge tasks, nested flows, rate limiting and policy conditions, with overflow-checked arithmetic and clock errors surfaced as typed denials.
- Guard registry pulls are digest pinned with per-descriptor and aggregate bounds, cross-origin token realms are refused, and the policy compiler rejects fields it cannot enforce at load time.
- The new shared OpenAI-compatible assembler (provider-adapter-core streaming/assembly.rs) validates identity stability, representation changes, finish reasons and the terminator before any evaluator runs, with tests asserting the evaluator is never reached on malformed tails.
- Bedrock's bounded_response interceptor validates the original bytes (size, duplicates) before the AWS SDK decoder sees them, and the Bedrock stream gate rejects unknown event kinds; this is the right fail-closed model for the other gates.
- Secret hygiene improved: redacted Debug for AuthScheme and config, set_sensitive on auth headers, reqwest errors stripped with without_url, redirects disabled on the provider client, ProviderError no longer echoes provider bodies.

**Design issues**

- **provider adapter family duplication** (major). Security fixes must be applied N times and already diverge (Cohere kept the fail-open event-keyed gate after Groq/Mistral moved to the strict assembler; Gemini kept name-derived ids after Ollama moved to positional ids). The crate count multiplies compile time and review surface without adding isolation.
  - Evidence: 8 provider crates (openai, anthropic, gemini, bedrock, ollama, mistral, cohere, groq) total about 17K src lines plus about 8.5K in tests/. After normalizing provider names, groq vs mistral native.rs differ by 0 lines, streaming.rs by 8 of 106, response.rs by 36 of 156, lib.rs by 253 of 967, tests/registry_security.rs by 32 of about 410. apply_redactions is byte-identical (md5 7204ca00) in groq, mistral, cohere, ollama, gemini and a second identical variant in openai, anthropic, bedrock; deny_payload is copied in 5 crates and differs in format from core deny_reason_text ("policy_deny: x" vs "policy_deny:x"); non_empty_str in 7; ensure_supported_api_version in 6; the registry admission block (new_with_registry, ConfigManifestMismatch, RegistryToolSidecarUnavailable) in 8, with openai omitting the name/version/public_key check the others perform. Copy-paste drift is visible: groq response.rs checks Gemini's promptFeedback.blockReason.
  - Better: One chio-provider-adapters crate with feature-gated dialects. Shared pieces: an AdmittedTools newtype built once from the registry, a single redaction and denial-lowering module, one input module. Per-dialect differences expressed as data (endpoint/path template, auth scheme, JSON pointers for call id/name/args and args encoding, stream protocol enum: OpenAiChatChunks, OpenAiResponses, AnthropicMessages, BedrockEventStream, GeminiParts, CohereV2, NdJson). OpenAI-compatible providers (Groq, Mistral and future ones) become configuration rows over the existing assembler.
- **trait design in provider-adapter-core and fabric** (major). No caller can be written generically over providers, so mediation (evaluate, lower, forward) is re-implemented per provider by every integrator. async on pure CPU lifting adds boxing with no I/O. Lowering keyed by tool name (Gemini, Ollama) instead of call identity is not prevented by the type system.
  - Evidence: Two competing abstractions: chio_tool_call_fabric::ProviderAdapter (async lift returning one ToolInvocation, async lower; implemented only by openai, anthropic, bedrock, with lift_one erroring when a response has more than one call) and chio_provider_adapter_core::Provider (provider_id/api_version only, implemented by all 8). Everything else is inherent methods with divergent names and result types: lift_batch, lower_function_response vs lower_tool_message, gate_sse_stream returning GatedStream, GatedSseStream (openai, with buffered_blocks), GatedNdjsonStream (ollama), gate_converse_stream returning GatedConverseStream.
  - Better: A single sync trait, for example `trait Dialect { fn lift(&self, &[u8]) -> Result<Vec<ToolInvocation>, ProviderError>; fn gate(&self, input: StreamInput<'_>, eval: &mut dyn Evaluator) -> Result<GatedStream, ProviderError>; fn lower(&self, call: &CallRef, verdict: VerdictResult, result: ToolResult) -> Result<ProviderResponse, ProviderError>; }` with one GatedStream type and a CallRef newtype carrying the provider call id, so lowering cannot be keyed by name. Keep transport separate and async.
- **fail-open defaults on unrecognized stream content** (major). Each gate enumerates what it must evaluate and forwards everything else, so every new provider tool or event type is an unmediated bypass until someone notices.
  - Evidence: openai streaming.rs:149 `_ => self.forward_or_buffer(frame)` and is_tool_call_item allowlist of tool types; anthropic streaming.rs block_kind maps unknown block types to BlockKind::Other and forwards them; cohere streaming.rs forwards every frame that is not event tool-call-end; core response.rs:83 returns Ok(None) for unknown tool_call types; SseParseOptions::ignoring_unknown used by Cohere and the OpenAI-compatible gate. Contrast bedrock streaming.rs EventKind::Unknown => Err.
  - Better: Per dialect, a closed enum of recognized events/items with explicit `Passthrough` (no client effect) and `ToolCall` classes, and `Unknown => Err(ProviderError::UnsupportedContent)`. Make rejecting_unknown the only SSE policy for gates.
- **include! fragments and .inc files** (major). Textual inclusion erases module boundaries and privacy: every item is visible to every fragment, imports are implicit, rust-analyzer and rustdoc treat the code poorly, and the remote MCP crate is effectively one 7K-line module. cfg(test) enum variants in production types change match exhaustiveness between test and release builds.
  - Evidence: chio-mcp-remote/src/lib.rs include!s 8 files (session_core.rs 1,125 lines, http_service.rs 1,356, http_service_auth.rs 1,151, session_resume.rs 1,105, session_identity.rs 696, ...) into one namespace consumed via `use super::*`, interleaved with #[path] modules; chio-acp-proxy/src/lib.rs has 14 include!, chio-a2a-adapter 10, chio-a2a-edge 8, chio-acp-edge 7, chio-policy/src/evaluate.rs 4; this PR adds chio-mcp-adapter/src/transport/stdio_parts/transport.inc (1,619 lines) and lifecycle_and_tests.inc (1,020 lines, production child lifecycle mixed with cfg(test) seams such as ManagedChild::TestProcess).
  - Better: Convert fragments into real modules (session, http, auth, resume, store) with pub(crate) APIs and explicit `use` lists; move test seams behind a trait (e.g. a ChildProcess trait with a test implementation in tests/) instead of cfg(test) variants.
- **ingress decoder choice is per call site** (major). The numeric contract is a property of the data type (signed record, unsigned peer envelope, I-JSON external document), but nothing ties it to the type, so the same class of interop bug recurs crate by crate.
  - Evidence: UntrustedJsonText exposes decode_document/decode_signed/decode_external/decode_canonical and call sites pick ad hoc: chio-mcp-remote aliases decode_signed as `decode_json` (lib.rs:17) and uses it for both persisted records and internal edge lines; ACP edge/proxy and structured classification picked decode_signed for unsigned peer data; A2A was fixed only after review.
  - Better: Encode the contract in types: e.g. `PeerEnvelope<T>`/`SignedRecord<T>`/`ExternalDocument<T>` extractors, each with exactly one parser, and a clippy `disallowed-methods` entry that forbids calling decode_signed outside signed-record modules.
- **streaming is fully buffered and evaluation is sync inside async** (moderate). Time to first byte equals full generation time, long generations hit the 60 s total timeout and fail, and a kernel evaluator that blocks (evaluate_tool_call_blocking_*) runs on an async worker thread. The OpenAI, Anthropic and Bedrock gates are already incremental state machines but are fed a finished buffer.
  - Evidence: ProviderHttpTransport::post_sse/post_ndjson return Vec<u8> after collecting up to 16 MiB under a 60 s total reqwest timeout (http.rs:641, DEFAULT_TIMEOUT); gates take &[u8] and return Vec<u8>; send_chat_completion_stream and peers are async fns that invoke a sync FnMut evaluator.
  - Better: Accept a Stream<Item = Result<Bytes>> and drive the existing state machines incrementally: release passthrough frames immediately, hold only the active tool block, and take an async Evaluator trait (or spawn_blocking at the boundary). Use a read-idle timeout for streams instead of a total request timeout.
- **per-call irreversible evaluation with all-or-nothing release** (moderate). If evaluate is the kernel, calls before the denied one already received allow verdicts (signed receipts, possible budget or approval consumption) for invocations that are never forwarded or executed, so the receipt log overstates authorized-and-delivered calls.
  - Evidence: core streaming.rs:60-70, gemini streaming.rs:62-72, cohere streaming.rs:58-68, ollama streaming.rs:77-87, anthropic and bedrock finish loops evaluate calls in order and return Err on the first deny, discarding the whole stream.
  - Better: Make the batch semantics explicit: either a two-phase admission (preflight all, then commit) or progressive release where allowed blocks are forwarded and a deny terminates the stream with a synthetic denial result tied to its receipt.
- **error handling in chio-mcp-remote** (moderate). A CLI error type leaks into a protocol crate, string matching breaks silently on dependency upgrades, a typo in a state literal is a fence bypass or a permanent fence, and logs cannot distinguish replay from bad signature.
  - Evidence: Protocol library returns chio_control_plane::CliError everywhere with crate-wide #![allow(clippy::result_large_err)] (lib.rs:2); `error.to_string().contains("length limit")` to classify body errors (http_service.rs:1041); persisted credential state machine is `state: String` compared to "pending"/"completed_unacknowledged"/"acknowledged"/"fenced" (session_credentials.rs:43,677,719,812); SenderConstraintError implements Debug as Display (input.rs:105) so ten variants log as the same URN.
  - Better: A crate-local thiserror enum with a stable code() method; downcast to http_body_util::LengthLimitError; `enum CallState { Pending, CompletedUnacknowledged, Acknowledged, Fenced }` with serde rename; derived Debug with the wire URN kept in Display.
- **blocking I/O on async workers** (moderate). Each request performs several synchronous SQLite opens and fsyncs on a Tokio worker, which stalls unrelated sessions under load and makes latency proportional to disk.
  - Evidence: session_credentials authenticate_request (twice per POST), reserve_call, finish_call (inside the stream! block) and acknowledge_call call open_db, which runs open_session_state_db custody checks, PRAGMA synchronous=FULL and three CREATE TABLE IF NOT EXISTS per call; RemoteSession::touch persists with fsync while holding a std Mutex; approval redemption reloads and re-parses the policy file on every approved call (approvals/redemption.rs:104).
  - Better: Create schema once at startup, hold a connection behind a dedicated store task or spawn_blocking boundary, and cache the policy fingerprint (re-verify on reload events) instead of reparsing per call.
- **lossy broadcast used for request-correlated responses** (moderate). Responses can be dropped under lag and streams cannot observe worker death, so correctness depends on timing.
  - Evidence: One tokio::broadcast(256) per session carries both notifications and responses (factory.rs:465); POST handlers subscribe, treat Lagged as continue, and wait for a matching id with no deadline (http_service.rs:479-528, 573-614).
  - Better: Keep the broadcast plus replay window for notifications only, and route responses through a per-request oneshot registered before send, with a deadline tied to the upstream request timeout.
- **error taxonomy** (moderate). Callers cannot distinguish protocol violations programmatically, redaction is done by overriding Debug on whole enums rather than by typing secrets, and the stable-code contract is inconsistent.

## Core types, trust crates, tooling, spec and wire

The core/trust/tooling/spec slice is fail-closed on every path I traced: crypto text decoding is bounded before allocation, receipts and lineage now verify strictly, signing backends bind identity atomically, FROST round two is recipient-sealed, and the new UntrustedJsonText contracts reject duplicate keys and lossy numbers before typed projection. **Design verdict**

Line-level code is careful and fail-closed. Typed boundary errors, bounded decoders, domain-separated preimages and zeroized custody are mostly applied correctly, and the PR fixed real panics (PublicKey::as_bytes) and loose verifiers. The structure is below elite production Rust. Active-defense and credential logic lives in include!d fragments that rustfmt and module privacy never see, and the substrate crate has absorbed a domain state machine that is also duplicated elsewhere. Cross-cutting invariants such as Ed25519 strictness, digest encoding and validated construction depend on each call site remembering them rather than on the type system.

**Done well**

- crypto/wire.rs: a single non-recursive parser for key and signature text, length-bounded before hex decoding, rejects nested hybrids and mismatched alg sets
- UntrustedJsonText separates external I-JSON, unsigned-document, native-signed and exact-canonical contracts. Its Display and Debug never echo input, and it carries registered URN codes
- SigningOutcome and sign_bytes_for_identity bind key, algorithm and signature in one backend operation, closing rotation TOCTOU, and every path self-verifies
- Active-defense receipt digests use per-kind NUL-terminated domains and embed the kind tag, and evidence ids hash domain||kind||digest. ChioReceipt, lineage and export envelopes now verify strictly
- FROST round two now uses recipient-sealed X25519/HKDF/ChaCha20-Poly1305. The plaintext type has no serde impl and no public constructor, zeroizes on drop, and the transport signatures are strict with weak keys rejected in validate_config
- MerkleConsistencyProof ships with RFC 6962 fixed roots and paths and an all-pairs test through 16 leaves, and bounds the path before Vec growth

**Design issues**

- **include! fragments and function size** (major). Fragments escape `cargo fmt --check`, share one privacy scope, cannot carry module docs or tests of their own, degrade rust-analyzer, and let one allow attribute cover hundreds of lines of future indexing
  - Evidence: receipt/security.rs include!s security_parts/definitions_and_projection.inc (1,383 lines) and lifecycle_and_validation.inc (1,737 lines). Neither is reachable by rustfmt: lines exceed 100 columns at definitions_and_projection.inc:1262 and lifecycle_and_validation.inc:8, 211, 795 and 1225. validate_response_snapshot_lifecycle is a single ~500-line function under a blanket #[allow(clippy::indexing_slicing)] (inc:8). chio-credentials/src/lib.rs still include!s 14 production files into one namespace (lib.rs:82-95), as does chio-reputation (lib.rs:81-85)
  - Better: Convert to real modules (receipt/security/{kinds,bodies,digest,projection,lifecycle}.rs). Split the lifecycle replay into a ReplayState struct with one validator per ResponseMutationRecord variant, and replace indexing with get(), zip or iter_mut so the allow can go
- **crate layering and duplicated state machine** (major). Two copies of a security state machine will diverge, so receipts and snapshots can end up validated under different rules. The wire-substrate crate also grows by domain logic that kernel-core and wasm targets must compile
  - Evidence: chio-core-types/Cargo.toml adds chio-security-types, so the substrate crate under crates/core now depends on crates/security. Active-response lifecycle rules exist twice: response_approval_path_is_valid, reserved_failure_timing, late authoritative takeover and effect receipt ordering appear in lifecycle_and_validation.inc:840-1107 and again in chio-response-model/src/state.rs:569-1005. The error-code literals 'active_response.dispatch_committed_resume_expired' and 'response.applying_lease_expired' are defined in three crates (core .inc:30-35, chio-response-model state.rs:31-35, chio-quarantine state_machine.rs:15-17)
  - Better: Make chio-response-model (or chio-security-types) the single owner of lifecycle validation and a typed ResponseErrorCode enum. Keep only receipt body types and digest functions in core, or move chio-security-types into crates/core if it really is substrate
- **Ed25519 strictness is opt-in** (major). Each repaired Codex finding is one instance of a class the API keeps re-enabling, and a new artifact type gets loose verification by default
  - Evidence: PublicKey::verify and verify_canonical stay permissive (crypto.rs:439-470). The PR hardens specific paths (receipts, lineage, checkpoints, FROST, DPoP, sender keys) and adds about 30 scattered is_weak_ed25519() checks across platform, kernel and trust crates. Capability tokens (token.rs:893), delegation links (attenuation.rs:165), governed approval tokens (governance.rs:1407), declassification grants (declassification.rs:62), security events (security_event.rs:76) and the OID4VP holder binding (chio-credentials/src/oid4vp.rs:992) still use the loose verifier
  - Better: Make verify strict by default and rename the permissive form (for example verify_legacy_permissive, with a deprecation lint), or introduce a TrustedPublicKey newtype whose constructor rejects weak and small-order keys and is required by every verifier signature
- **verification cache inside the primitive** (moderate). The cache hides redundant verification at call sites and doubles hashing cost on misses. A process-wide hidden cache in a no_std-oriented crypto crate is surprising
  - Evidence: crypto/ed25519_verification.rs memoizes successes per thread, keyed by (key, signature, SHA-512(message), len, strict). It is sound, but every cache miss now adds a full SHA-512 pass over the message, up to 16 MiB inputs on presentation and observation paths, and sign_bytes_with_identity plus sign_bytes_for_embedded_key verify the same signature two or three times per signing
  - Better: Verify once at the boundary and carry the result in a typestate (Verified<T>, like VerifiedCapability in kernel-core). Remove the redundant self-verification in signer_binding.rs:27-44
- **error type design** (moderate). Callers cannot match on the reason, every message renders as 'canonical JSON error: ...' even for state-machine or negotiation failures, and kernel code must string-match
  - Evidence: Error::CanonicalJson(String) is the catch-all at 89 sites in chio-core-types. That includes all 47 lifecycle violations via response_snapshot_error (definitions_and_projection.inc:1381), failures to negotiate invocation features (features.rs:142), and response-plan bounds (governance.rs). The typed ActiveDefenseReceiptValidationError exists but is flattened to a string in active_defense_body_digest (definitions_and_projection.inc:710)
  - Better: Add typed variants (Error::ResponseLifecycle(LifecycleError), Error::FeatureNotNegotiated(&'static str), Error::Validation{field, rule}) and keep CanonicalJson for encoding failures only
- **digest and identifier newtypes** (moderate). Encodings differ per artifact (0x versus bare, case-insensitive parse), validation is repeated by hand, and string comparison of keys fails on spelling
  - Evidence: SHA-256 has at least three representations: Hash (0x-prefixed hex serde, hashing.rs), chio_security_types Digest32, and bare String validated ad hoc (governance.rs validate_response_plan_digest, threshold_approval.rs is_sha256_digest, plan_body_hash/operator_capability_hash/policy_hash fields). lifecycle_and_validation.inc:795 reimplements hex::encode. CapabilitySecurityBinding.workload_signer_public_key is a String compared by string in the kernel
  - Better: Use one Sha256Digest newtype with a single canonical wire encoding and FromStr and serde validation, use PublicKey-typed fields in bindings, and use the hex crate
- **validated construction bypassed by derives and pub fields** (moderate). Parse-don't-validate is applied only halfway. The invariant holds only when callers choose the right constructor
  - Evidence: ThresholdApprovalRequest::new validates ids (threshold_approval.rs:28-48) but the type derives Deserialize (line 17) with no validation. GovernedResponsePlanIntentBody gains a validating new(), a custom Deserialize and twelve getters, yet keeps every field pub (governance.rs:793-805), so callers can still build or mutate an invalid body
  - Better: Use private fields with #[serde(try_from = "...Wire")] so deserialization and construction share one validated path. Drop the pub fields now that getters exist
- **generated wire bindings placement** (moderate). Every `cargo test -p chio-core-types` and `clippy --all-targets` expands serde derives for thousands of types to exercise 12 schemas. Each schema edit produces a 100K-line diff in a CODEOWNERS TCB crate, and its location implies it is part of the library
  - Evidence: src/_generated/chio_wire_v1.rs is 129,664 lines and 4.57 MB (+105,582/-17,143 in this PR). _generated/mod.rs declares no submodules and lib.rs does not reference it. The only consumer is tests/protocol_primitives_generated.rs via #[path] under a crate-wide #![allow] block. It uses ::std paths inside a no_std crate's src tree. docs/security/trust-boundary-inventory.json lists its try_from sites as trust boundaries. It is reproducible (typify =0.4.3 plus pinned rustfmt via the xtask --check byte comparison) and drift-checked by spec-drift.yml and enterprise-hardening
  - Better: Move it to a dedicated publish=false chio-wire-v1-bindings crate used only as a dev-dependency. Generate one module per schema behind per-family features (or generate in that crate's build.rs into OUT_DIR) so the parity test compiles only what it checks, and drop it from the trust-boundary inventory
- **#[path] chains and repeated lint boilerplate** (minor). Redundant #[path] makes module resolution fragile and surprising, and duplicated boilerplate drifts
  - Evidence: canonical.rs declares `mod secret;` but `#[path = "canonical/signed_json.rs"]` and `#[path = "canonical/untrusted.rs"]` for its siblings. frost_ceremony.rs uses #[path] for sealing.rs, which then needs #[path = "sealing/keys.rs"] because path-loaded files resolve like mod.rs. The same 15-line #![cfg_attr(not(test), deny(...))] block is copied into 26 crate roots. chio-adversarial-suite/src/bundled.rs hand-lists 70 include_str! cases
  - Better: Use default module resolution. Generate the case list in build.rs. Centralize lints in [workspace.lints] where Cargo allows it, and keep crate-local additions minimal
- **source chains can expose rejected input** (minor). Reporters that walk the chain (anyhow {:#}, tracing error fields) will print the redacted content anyway
  - Evidence: UntrustedJsonError Display and Debug print only the rule code, but source() returns the serde_json::Error (untrusted.rs:137-144), whose messages can quote offending string values. Wrappers such as CredentialError::SignedJson, AttestError::Input and RunnerError::Input use #[error(transparent)], which forwards source()
  - Better: Store a redacted classification instead of the raw serde error, or expose the cause only through an explicit unsafe-to-log accessor rather than Error::source

## Workflows, scripts, xtask, supply chain and formal

The CI and supply-chain slice is defensive. Every third-party action is SHA-pinned. No pull_request_target job checks out PR code. Aggregator jobs test each needs.*.result. The trusted capture runs owner-authorized tooling against a candidate that must descend from the authorized SHA through commits that touch only the evidence files. I found no fail-open gate. The real defects are in the merge-authority design the PR body lists as remaining landing gates. The admin override audit reads check names that never exist on the real merge commit. The documented ruleset allows only squash and rebase merges, while the landing requires a merge commit. The required contexts are posted on the test merge commit, not the PR head. The PR's ci.yml changes (unlabeled trigger, cancel-in-progress, an advisory nextest job) feed a sticky tombstone policy, so routine events permanently revoke authority. The isolation boundary uses a default-allow seccomp denylist that is weaker than Docker's default profile, and its image build depends on exact Alpine package revisions the CDN does not keep. **Design verdict**

The workflow-level hygiene meets a high bar: pinned actions, minimal permissions, exact result aggregation and a capture that separates authorized tooling from candidate code. The gate layer itself is not production-grade engineering. Roughly 67.7K lines across 177 new Python and bash scripts restate other files' text, AST shapes and hashes. The core trust protocol lives in thousands of lines of inline bash and jq in YAML. The Rust-native xtask path the repo already has is mostly bypassed. The mechanism does stop locally fabricated evidence and post-authorization tampering. It does not provide independent review, because the same owner authors, authorizes, triggers and approves (0 required reviews). The four Actions-app mirror contexts carry no authority, since any workflow job with checks: write can create them.

**Done well**

- All third-party `uses:` are 40-hex SHA pins; downloaded tools (elan, syft, cosign, osv-scanner, cargo-mutants crate) are SHA-256 checked
- pull_request_target controller performs only GitHub API calls and never checks out PR code; capture checks out candidate and authorized tooling separately and builds the image only from the authorized tree
- Candidate must descend from CHIO_AUTHORIZED_SECURITY_SOURCE_SHA through at most 32 single-parent commits touching only the three evidence files
- Container runs with network none, read-only rootfs, cap-drop ALL, no-new-privileges, pids/memory/ulimit bounds, distinct candidate and verifier uids and a token-authenticated broker
- Aggregators (`security-contract-required`, `apalache_verdict`) test every `needs.*.result == success`; `run_gate`/`finish_gates` preserves every failure; exact-test-inventory scripts reject zero-test passes
- Release flow now stages drafts until provenance verifies and requires exact-source CI, vet, audit and qualification runs
- xtask adapter_no_bypass uses syn visitors rather than regex, which is the right pattern for Rust source policy

**Design issues**

- **CI contract checker architecture** (major). It is a change detector that pins the exact text and AST shape of workflows, the Dockerfile, the seccomp JSON and other Python scripts. Every edit to a protected file needs a matching edit here and in the 5.5K-line test. CI runs it from the PR head (`ci.yml:173`, `enterprise-hardening.yml:334`), so a hostile PR edits all three together. It cannot bind untrusted changes. It duplicates what authorized_source_sha plus TRUSTED_EXECUTION_FILES already guarantees in the trusted capture. It also enforces broken behavior as written (finding on admin-override-audit).
  - Evidence: scripts/check-security-ci-contract.py: 8,313 lines, `validate()` 3,287 lines, `validate_security_entrypoint()` 1,325 lines, about 1,500 string-literal lines, 376 ContractError sites, literal workflow bodies such as EXPECTED_ADMIN_AUDIT_RUN (line 1111); scripts/tests/check-security-ci-contract.test.py: 5,538 lines of text mutations asserting rejection
  - Better: Keep a small digest manifest of protected files checked by the trusted workflow, require code-owner review on those paths, use actionlint plus zizmor for generic workflow properties (pins, permissions, injection, pull_request_target), and assert a handful of real invariants (required needs, no continue-on-error on gates). Test the runner behaviorally (hostile_probe) instead of pinning its AST.
- **Trust protocol in inline workflow bash** (major). The security-critical state machine (binding, mirror publication, tombstones, revalidation loops) is written in untyped bash and jq spread across YAML. It is tested by scraping function bodies with regexes, and the defects above (wrong SHA for contexts, sticky tombstones on cancellations) are design-level and hard to see in this form.
  - Evidence: enterprise-evidence-finalizer.yml 3,382 lines, enterprise-linux-capture.yml 1,435, security-contract-revocation.yml 1,150, enterprise-evidence-controller.yml 541; scripts/tests/check-security-definitions.test.py regex-extracts bash functions (`shell_function`, `shell_region`) from YAML to test them
  - Better: Implement the controller, finalizer and revoker as one typed program (a Rust xtask binary or a typed Python package) with explicit state types, a fake GitHub API for unit tests, and property tests for tombstone and idempotence rules. Keep workflows to checkout, build or verify the pinned tool, and call it.
- **Gate sprawl and toolchain split** (major). Rust source policy is enforced by many independent regex lexers in Python, each with its own blind spots and allowlists. The repository's planned `cargo xtask check` gate CLI is bypassed, and there are now two parallel gate stacks.
  - Evidence: 177 new files under scripts/ (+67,717 lines); regex Rust analysis in check-security-clocks.py (alias tracking at 139-160; `<SystemTime>::now()` or a macro-built path evades `\bSystemTime\s*::\s*now`), check-trust-boundaries.py, check-rust-hardening.py, check-accounting-arithmetic.py, check-rust-file-hygiene.py; xtask has syn-based adapter_no_bypass while `SupplyChainCommand` stays `pending_group!`
  - Better: Move Rust-source gates into xtask using syn (one parse per file, shared visitors, typed allowlists in TOML with expiry), expose them as `cargo xtask check <gate>`, and call one binary from CI. Keep Python only for workflow and JSON plumbing.
- **Hash-pinned implementation anchors** (moderate). Any refactor of about 100 kernel and store functions forces re-blessing hashes. The gate reduces to 'someone regenerated the digests' and gives no evidence that the model still corresponds. Duplicated entries double the churn.
  - Evidence: formal/proof-manifest.toml +3,041 lines of per-symbol sha256 for `abstraction_anchor` mirrors, with identical entries repeated per model (dpop_acquisition.rs listed for both RevocationPropagation.tla and PostAdmissionDropGuard.tla); xtask/src/formal_mirrors/dispatch_anchors.rs 1,717-line hand-maintained path and symbol inventory
  - Better: Annotate anchored items in source (an attribute or doc marker naming the model), generate the manifest, deduplicate by (source, symbols), and require model review only when the anchored signature or the model changes. Body-hash drift belongs in a report, not a blocking gate.
- **Supply-chain forks** (moderate). cargo-vet now treats these security-relevant crates as first-party, with no audit criterion; the supply-chain/reviews/*.md files are prose that no tool checks. Same-name path packages may also drop out of RustSec matching in cargo-audit and cargo-deny, because the lock no longer records a crates.io source (not verified offline). Only seccompiler and nono have digest pins in check-linux-enforcement-stack.py.
  - Evidence: Cargo.toml adds 11 `[patch.crates-io]` path forks under upstream names and versions (ignore, regress, nono, sigstore-verify, sigstore-crypto, sigstore-merkle, sigstore-trust-root, seccompiler, crmf, cmpv2, enumflags2_derive); supply-chain/config.toml sets `audit-as-crates-io = false` for each; Cargo.lock entries lose their `source` line
  - Better: Keep a machine-checked fork manifest (upstream crate checksum, patch diff hash, rationale, upstream PR link) verified in CI for every fork. Run an explicit advisory query keyed by upstream name and version for each patched crate, or rename forks (`ignore-chio`) so the deviation is visible to every tool.
- **Separation of duties and mirror authority** (moderate). The PR body presents 'trusted capture, signing and three-file evidence-only publication' as an assurance step. In practice the repository owner authors the source, sets the authorized SHA, triggers the controller and merges with no reviewer. The guarantee is provenance (owner-authorized code ran on a hosted runner), not review. Any same-repo workflow job with `checks: write` can create the 15368 mirror contexts with any conclusion, including a sticky failure that permanently tombstones a tuple. Only the App-bound `Security contract` carries authority.
  - Evidence: enterprise-evidence-controller.yml requires `github.actor == github.repository_owner` and `author_association == 'OWNER'`; documented ruleset has `required_approving_review_count: 0`, `require_code_owner_review: false`; four mirror contexts pinned to integration 15368 (GitHub Actions)
  - Better: State the guarantee precisely in docs. Either drop the mirrors from the ruleset or post them from the dedicated App. Add a second-party approval (another maintainer or a required review App) if independent review is part of the claim.
- **Rust quality in xtask additions** (minor). Error context is flattened to strings at the module boundary, so callers cannot match failures, and the rest of xtask already has a typed XtaskError.
  - Evidence: xtask/src/rust_packages.rs: `type Result<T> = Result<T, Box<dyn Error>>`, string errors (`"output has no parent".into()`), `map_err(|err| XtaskError::Process(err.to_string()))`, serde_json `metadata["packages"]` indexing; support.rs workspace_root rewrite is careful (no env fallback, stops at Git boundaries)
  - Better: Add XtaskError variants (or a module thiserror enum) with path context, and deserialize cargo metadata into typed structs (cargo_metadata crate or serde structs) instead of indexing Value.
- **Isolation copy invariants** (minor). Chained symlinks (`a/b -> ..`, `a/c -> b/..`) pass the lexical check but resolve outside the copy root. This is harmless today because the copy is consumed only inside the container under `/source`, and writes use O_NOFOLLOW with non-symlink parent checks. The code still claims an invariant it does not enforce.
  - Evidence: scripts/run-security-execution-container.py:561-578 rejects symlinks by lexical `posixpath.normpath` only
  - Better: After materialization, resolve every symlink with `os.path.realpath` against the copy root and reject escapes. Alternatively, reject symlinks whose target traverses another symlink.

**Design verdict**

The per-fork engineering is careful. Each fork records its archive checksum and upstream commit, the production deltas are small, correct and well-tested, and nono-chio is a tight, fail-closed adapter. The vendoring strategy around them is not production-grade. 95% of the vendored source is dead, the semantic signal is about 2.2K changed lines (about 2,000 of them in the dead sigstore-verify patch) inside 161K vendored lines, first-party style gates force structural rewrites of upstream code, and no fork has an upstream exit path. Every security bump of these crates therefore becomes a manual re-fork.

**Done well**

- Every CHIO-PATCH.md pins the registry archive SHA-256 and upstream commit. The claimed checksums match Cargo.lock at 3d3e4b4d9, and the production deltas I diffed against registry sources match the descriptions exactly
- Fixes are minimal and correct: seccompiler's try_into runs before PR_SET_NO_NEW_PRIVS and returns the existing FilterTooLarge error; Merkle uses size/2 + size%2; prehash verification no longer double-hashes; ignore's basename and serial-filter fixes match the parallel walker
- Several forks backport upstream commits exactly (crmf 2f3e066, cmpv2 aeee92c/4f2771d/e4ffe7a, merkle eed06c3, sigstore-crypto 267dacd, regress 5e5141c) rather than inventing fixes
- Licenses are retained in every fork, with publish = false and a standalone [workspace] each
- Replacing 32K lines of upstream nono in the runtime graph with nono-chio (forbid(unsafe_code), BorrowedFd lifetimes, HardRequirement, FullyEnforced plus no_new_privs checks, no network-grant API) was the right call
- Upstream-generated regress Unicode tables are hash-pinned rather than rewritten

**Design issues**

- **vendoring strategy and maintenance burden** (major). Full-source vendoring for one- to sixty-line fixes multiplies review and update cost by about 70x. Each upstream security release needs a manual re-fork, re-split, re-hash and re-qualify. Four of the fixes are already upstream, so their forks exist only to hold back newer releases.
  - Evidence: 567 files and 161,299 lines under third_party. Live: seccompiler-chio 6,467, enumflags2-derive-chio 719, nono-chio 563. Production deltas: seccompiler 5 lines, enumflags2 1, regress 8, crmf 1, merkle 1, ignore about 10, nono about 14, sigstore-crypto about 20, trust-root about 60, cmpv2 about 50, sigstore-verify about 2,000. Coupling: 47 [patch] lines across 4 manifests, 11 cargo-vet policy entries, 16 supply-chain review docs (about 2.7K lines, 13 of them about crates not in any lockfile), 14 hard-coded paths and hashes in check-linux-enforcement-stack.py, about 30 stub-surface and 2 size allowlist entries, NOTICE, and 6 Dockerfile COPY lines
  - Better: Delete the dead forks. For seccompiler, Chio's compiler path already caps filters at BPF_MAX_LEN, so a caller-side assertion in chio-cage-init install_seccomp plus a cargo-vet audit of the registry crate removes the fork. Otherwise upstream the fix and use [patch.crates-io] seccompiler = { git = "https://github.com/rust-vmm/seccompiler", rev = "<fix>" } until a release. For anything that must stay vendored, store only the upstream archive hash plus a unified diff and reconstruct it in CI, as the aws-lc fork already does.
- **first-party hygiene gates applied to vendored code** (major). House file-size, stub and text rules force structural divergence from upstream, so a plain diff against the registry crate is noisy and every upstream bump means re-doing the splits. The include! fragments are exactly the pattern the repo's own review checklist calls out, now added to third-party code, and they did not even reduce the counted size.
  - Evidence: regress parse.rs split into parse/helpers.rs, and tests.rs/unicodesets.rs split into include! fragments. ignore walk.rs split into walk/{stack,entry_checks,tests}.rs. nono capability/keystore/diagnostic/sandbox::linux tests moved to child modules, plus diagnostic/context.rs and sandbox/linux/abi.rs extracted. About 11.6K moved lines in total, plus em-dash, whitespace and Clippy-indentation edits to upstream docs
  - Better: Exempt third_party/** from first-party style gates. Hold vendored code to one invariant instead: it reconstructs byte for byte from the upstream archive plus the documented patch.
- **update story and upstream exit criteria** (major). A path [patch] freezes the crate at the forked version for every semver-compatible requirement, so cargo update cannot pick up upstream security releases, and nothing tracks when a fork could be dropped
  - Evidence: No CHIO-PATCH.md or review links an upstream issue or PR for any Chio-authored fix; enumflags2-0.7.12.md:159 says 'No upstream issue, advisory identifier, fixed release, or external disclosure'. Forks are pinned at nono 0.53.0 (index cache shows 0.77.0), sigstore-* 0.6.x (0.11.0), regress 0.11.1 (0.12.0), ignore 0.4.32 (0.4.33)
  - Better: Each fork record should carry an upstream PR/issue URL and a 'drop when upstream >= X' condition, plus a scheduled job that diffs the fork's patch against the latest upstream release and flags when the fix has landed or the fork has fallen behind a security release
- **provenance gate design** (moderate). The gate keeps 32K lines of dead code in place as a 'reference' that is never machine-compared. Its token greps check spelling rather than behavior, and a refactor that keeps the tokens but changes semantics passes.
  - Evidence: check-linux-enforcement-stack.py:301-313 requires the dead nono-upstream-chio tree and its ignore/regress standalone patches to exist; validate_sources (:329-390) asserts substring tokens such as 'PathBeneath::new(grant.fd' and 'ABI::V6' in source; nothing compares nono-chio/src/abi.rs against the upstream probe it claims to extract
  - Better: Record the extracted probe's upstream commit and blob hash, and diff the probe against that blob in the gate. Replace token greps with behavioral tests, which nono-chio partly has already.
- **cargo-vet coverage of live forks** (moderate). The 6.4K lines of upstream seccompiler compiled into the confinement helper, and the enumflags2 proc-macro that runs at build time, have no audit record cargo-vet can check, only prose reviews
  - Evidence: supply-chain/config.toml:411-442 sets audit-as-crates-io = false for all forks, making them first-party and out of cargo-vet scope; aws-lc-rs alone gets the stricter policy plus reconstruction plus regression scheme
  - Better: Audit the registry versions in audits.toml (cargo vet certify) and keep the Chio delta as a separately reviewed diff that the reconstruction gate checks, so both halves are machine-verified
- **nono-chio adapter API and errors** (minor). The directory-versus-file invariant behind 'ReadDirectory does not grant descendant reads' depends on a caller-supplied bool. Passing a directory fd as is_directory=false with PathAccess::Read would grant ReadFile on the whole subtree. The current caller, chio-cage-init sandbox.rs:90, takes the bool from an fstat-verified identity, so this is safe today. Stringly-typed errors also drop the source chain.
  - Evidence: third_party/nono-chio/src/lib.rs:70 add_path_fd(fd, access, is_directory: bool); lib.rs:118-148 map every landlock::RulesetError to Error::Filesystem(String)/Network(String) via to_string(); abi.rs probes Scope for V6, but enforce() never applies Scope
  - Better: Take a GrantTarget::{File, Directory} enum and validate it with fstat on the BorrowedFd (for example rustix::fs::fstat) inside the adapter. Keep typed sources with #[source] landlock::RulesetError. Either apply Landlock scopes on ABI 6 or document that seccomp's signal and socket bans (chio-cage-plan seccomp_plan.rs:296-306) cover them.
- **semver and type-level validation in forks** (minor). Substituting an API-incompatible crate under the same version through [patch] breaks or silently changes any registry dependent built against 0.2.0. A direct serde_json::from_str::<TrustedRoot> call bypasses the new validation.
  - Evidence: cmpv2-chio changes PollRepContent from a struct to a newtype and PkiFailureInfoValues from u16 to u32 while staying at version 0.2.0. sigstore-trust-root-chio validates validity periods only in TrustedRoot::from_json, while TrustedRoot still derives Deserialize
  - Better: Keep patched forks API-compatible, or switch dependents to the fixed upstream pre-release. Validate inside the type with #[serde(try_from = "RawValidityPeriod")] so every deserialization path checks the period (parse, don't validate).

## SDKs, examples and integrations

The core process-worker clients (Python chio_process, TS @chio-protocol/process) are careful: bounded framing that matches the Rust worker limits, absolute deadlines, redacted transport errors, credentials delivered over stdin or private files rather than argv, and no automatic retry. DPoP v2 signing in TS and C++ is pinned to a shared Rust vector byte-for-byte. The Go type deletions are diff churn: all 142 base structs and their fields survive unchanged, and strictness moved from the test decoder into public UnmarshalJSON methods for every mapped type except ReceiptRecord. The most serious defect is in the Hermes restricted launcher: after the sandboxed host exits, the unsandboxed launcher writes three evidence files into the directory the sandbox let the host write, following any symlinks the host left there. The rest are parity and packaging gaps: the TS client lacks known_outcome_only and prepare_invocation, the chio-hermes dependency floor is wrong, and the Docker example publishes well-known default tokens on every host interface.

**Design verdict**

The SDK and example code is defensive and consistent in intent: bounded I/O, fail-closed parsing, explicit operation keys, and no blind retries. Structurally it is hand-written and duplicated rather than generated. The chio.process.v1 worker protocol has no schema in spec/schemas and no section in spec/PROTOCOL.md, so the Python and TS clients encode it independently and have already drifted. Go strictness is bolted on with reflection and string-patched generator output. The Rust example code is serviceable but not production-grade: Box<dyn Error> everywhere, lossy unwrap_or_default, and 15-field config literals with security booleans and no secure builder.

**Done well**

- Python and TS process clients enforce the same request/response bounds as worker.rs, use absolute deadlines, redact transport errors, and never auto-retry
- Worker credentials travel over stdin bootstrap or 0600 files, never argv (process-starter, invocation.py, container.py staging under a protected /tmp)
- DPoP v2 in TS and C++ is tested byte-exact against a shared Rust vector, including Unicode White_Space parity
- Go regeneration retained every base struct and field (verified 142/142); strict decoders reject duplicate keys, unknown fields and lossy numbers
- Container launcher pins image digest and daemon socket, drops all caps, uses no network, and verifies an ownership label before forced removal
- Strict JSON ingestion (duplicate keys, nonfinite numbers, size caps) is applied consistently in Python snapshot, broker and hermes token inputs

**Design issues**

- **wire types hand-written and duplicated** (major). The worker frame grammar, error-code vocabulary and limits live in Rust code plus a crate-local WORKER_PROTOCOL.md, so each SDK re-implements them. Drift has already happened: TS lacks known_outcome_only, prepare_invocation and the broker client. LangGraph passes MCP `isError` values to the model while ai-sdk-process fails the run on them.
  - Evidence: chio_process/__init__.py, packages/process/index.mjs + hand-written index.d.ts, worker.rs Operation enum; constants PROTOCOL/MAX_* repeated in three languages; spec/wire-schemas.lock only records the domain string
  - Better: Derive JSON Schema for Request/Operation/response envelopes (schemars on the Rust types) into spec/schemas/chio-process/v1, generate Python TypedDicts and TS types from it, and add a frame-level fixture corpus that every client and worker.rs test consumes, as protocol-primitives-v1.json does for wire primitives.
- **TS package typing** (moderate). Declared types can silently diverge from runtime behavior (options shape, result validation) and nothing type-checks the implementation.
  - Evidence: sdks/typescript/packages/process ships index.mjs with a separately maintained index.d.ts; build is `node --check`
  - Better: Write the client in strict TypeScript (like ai-sdk-process) and emit .d.ts from source; keep zero runtime dependencies.
- **Python async idiom** (moderate). Async hosts consume a thread per in-flight call, and cancellation cannot reach the exchange. The SDK's main client (chio_sdk.ChioClient) is async, so the two Python surfaces disagree.
  - Evidence: chio_process.ProcessClient is synchronous; chio_langgraph.process.ChioProcessToolNode.ainvoke uses asyncio.to_thread over a ThreadPoolExecutor
  - Better: Provide an AsyncProcessClient over asyncio.open_unix_connection with the same bounded framing. Use asyncio.shield for the in-flight exchange so caller cancellation never drops a dispatched operation's reply.
- **Go strict decoding architecture** (moderate). Each closed type needs a hand-written UnmarshalJSON. Coverage is opt-in, and ReceiptRecord was missed. Nested strict types re-parse their subtree, so cost is quadratic in depth. String patching of generator output breaks when oapi-codegen formatting changes.
  - Evidence: protocol_validation.go checkProtocolShape (reflection over json tags) + decodeProtocolObject double-decode; regen-types.sh injects validateAggregateBudgetJSON via text.replace on generated source
  - Better: Generate strict UnmarshalJSON for every schema with additionalProperties:false (oapi-codegen templates or a small go:generate pass over the schema set) so strictness is uniform and checked by the drift lane.
- **Rust example API ergonomics** (moderate). Embedders copy the example and inherit insecure toggles and a fixed key. Every new field is a breaking change for consumers.
  - Evidence: examples/rust-runtime-consumer/src/main.rs KernelConfig literal (15 fields incl. allow_ephemeral_receipt_log/allow_ephemeral_revocation_store = true) and ToolCallRequest literal (16 fields); fixed signing seed
  - Better: Expose KernelConfig::builder(keypair, policy_hash) with secure defaults and explicit `.allow_ephemeral_receipt_log()` opt-ins, plus ToolCallRequest::new(...) with a builder for optional authorization extensions. Use Keypair::generate in the example with an opt-in persisted key.
- **Python SDK structure** (minor). Hidden imports, two inconsistent credential channels, and monkeypatched generated models make the API harder to type and reason about.
  - Evidence: chio_sdk/client.py respond_approval/submit_for_approval do `from chio_sdk.approval_contract import ...` inside the method with no cycle; control_token is a constructor field for mint/approvals but a required per-call argument for start/report_mediated_execution; models.py monkeypatches generated pydantic classes
  - Better: Use module-level imports and a single credential source (constructor, overridable per call). Replace monkeypatched methods with free functions or thin wrapper types, as scope_is_subset_of now does.
- **security launcher code shape** (minor). The terminal-state classification is the security-relevant summary, but it is dense, untested in isolation, and passes secrets through stringly-typed namespace attributes.
  - Evidence: chio_hermes/restricted.py main(): outcome/exit_code classification in single 200+ character lines; transport tokens threaded by mutating argparse.Namespace (args.gateway_transport_token = ...)
  - Better: Extract a pure classify(records, outcomes, host_code, interrupted) function with unit tests, and pass a frozen LaunchContext dataclass instead of mutating args.
- **examples vs qualification harnesses** (minor). User-facing examples are buried among qualification tooling, which raises the chance users copy harness shortcuts (demo tokens, inherited env with provider keys).
  - Evidence: ~60K added lines under examples/ (mini-swe-recovery, repository-review, reference-swarm, shared-resource-swarm, postgres-job-swarm) are mostly qualify_*/probe_*/compare_* scripts
  - Better: Keep minimal, secure-by-default examples in examples/, move qualification harnesses under qualification/ or tests/, and lint examples for default credentials and 0.0.0.0 binds.
