### F001 [P0] Fix Darwin ACL scan: acl_get_entry returns 0 on success, so ACLs pass

Location: [`crates/security/chio-keyring/src/lib.rs:581`](https://github.com/bb-connor/arc/blob/d0496c14d824a327f00b98576132834306ff6694/crates/security/chio-keyring/src/lib.rs#L581). Slice: Secret broker, keyring, secure IPC, hardware custody. Confidence: high (raised from P1).

Darwin acl_get_entry(3) returns 0 when it yields an entry and -1 (errno EINVAL) after the last entry. The man page on this macOS host confirms this. Linux libacl and FreeBSD return 1 instead. trusted_file_has_extended_acl loops `while entry_result == 1` (lib.rs:581), so on macOS the loop body never runs for an ACL that has entries. entry_result stays 0, which is not < 0 (lib.rs:598), so no error is recorded and the function returns Ok(false) for every non-empty extended ACL, allow entries included. Only an ACL object with zero entries fails, and it fails closed. Every custody check depends on this function: trusted parent chain (lib.rs:439, lib.rs:465), the durable SQLite file check (lib.rs:679 via validate_path_binding), and custody-sensitive policy, config and witness-seed reads (lib.rs:340). The function is also exported as darwin_descriptor_grants_extended_acl_authority (lib.rs:616), which chio-secret-broker uses for its database custody (crates/security/chio-secret-broker/src/sqlite.rs:675). Scenario: on macOS, `chmod +a "user:mallory allow write,add_file,delete_child"` on the key-log directory or policy file leaves the mode at 0700/0600. The check still passes, and mallory can rewrite or replace the trusted policy, seed or database inputs while every custody gate reports them safe. Existing tests cannot catch this: apple_acl_inspection_accepts_a_file_without_an_extended_acl covers only the no-ACL path, and apple_acl_policy_accepts_deny_only_and_rejects_allow_entries tests only the tag helper.

Reviewer note: raised to P0. This is a custody check that fails open on macOS. Darwin returns 0 from `acl_get_entry` on success, so the `while entry_result == 1` loop never inspects an entry; an empty ACL errors (EINVAL) but any non-empty ACL, including one inherited from a shared parent directory, passes.

Fix direction: On Darwin, treat 0 as 'entry returned' and loop `while entry_result == 0`. Treat -1 with EINVAL as end of list (after ACL_FIRST_ENTRY, as an empty ACL), and treat any other errno as an error. Add a macOS test that installs an allow ACE (acl_set_fd or `chmod +a`) on a temp file and asserts rejection, plus a deny-only case that asserts acceptance.

### F002 [P1] Complete pre-dispatch compensation for settled prepayments and Settling releases

Location: [`crates/kernel/chio-kernel/src/kernel/admission_coordinator.rs:1788`](https://github.com/bb-connor/arc/blob/d0496c14d824a327f00b98576132834306ff6694/crates/kernel/chio-kernel/src/kernel/admission_coordinator.rs#L1788). Slice: Kernel admission, evaluation, dispatch and recovery. Confidence: high.

`compensate_durable_admission_before_dispatch` only handles payment journals in HoldPlaced or Authorized (admission_coordinator.rs:1670-1765) and then requires Settled+Release or Closed-without-authorization (1766-1777). Two reachable journal states can never pass. (1) PrepaidFinal: authorization applies PrepaymentSettled (validation.rs:2388-2392), which sets state Settled with settle_action None (payment/journal.rs:302-311). No branch refunds it and neither terminal predicate matches, so compensation always returns 'pre-dispatch payment release is not durable'. Durable prepaid rails are supported and tested (tests/durable_admission_sqlite.rs:326-350, 1535). Every post-payment pre-dispatch denial (post-payment revalidation, session cancellation, finding-pool claim, security pre-dispatch hook in async_evaluation_core.rs:1430-1610) refunds on the rail and then calls compensation with `?` (evaluation_helpers.rs:613-618). The caller gets Err with no signed deny, and the operation stays non-terminal with a journal that still says Settled after the rail refunded. A crash after prepayment is worse: startup compensation never refunds, so the agent is charged for a tool that never ran. (2) ReversibleHold recovery: with no confirmed unwind, the function journals BeginRelease (1710-1722), then calls adapter.release (1741-1748). A rail error or Pending leaves the journal Settling. On every retry the HoldPlaced and Authorized branches are skipped and the predicate fails, so the authorization is never released. `continue_durable_payment_settlement` (terminal_payment.rs:136-170) re-drives Settling journals; this path has no equivalent. In both cases the executable-hold and nonce-preflight releases this PR added at 1788-1791 are never reached, so budget stays reserved, and the participants released at 1635-1639 are already gone while the operation remains replayable. With the startup latch finding, the next restart denies all requests. The unreferenced admission_cleanup/recovery_and_compensation.inc (664-760) contains a Settling re-drive that the live path lacks. The gate lines themselves are unchanged from base.

Fix direction: Treat Settling(Release) and ReconcileFailed(Release) as resumable: call adapter.release again (idempotent by operation id) and complete the journal. For PrepaidFinal, accept a confirmed Refunded unwind or issue the refund here, then journal a typed refund completion (or Close) and accept it in the terminal predicate. Add durable tests for prepaid pre-dispatch denial and for a recovery release that fails once then succeeds.

### F003 [P1] Stop one unrecoverable admission from failing every later tool call

Location: [`crates/kernel/chio-kernel/src/kernel/admission_coordinator/recovery.rs:358`](https://github.com/bb-connor/arc/blob/d0496c14d824a327f00b98576132834306ff6694/crates/kernel/chio-kernel/src/kernel/admission_coordinator/recovery.rs#L358). Slice: Kernel admission, evaluation, dispatch and recovery. Confidence: high.

`reconcile_durable_admission_startup` (recovery.rs:108-131) sets `startup_reconciled` only when `reconcile_recoverable_admissions` returns Ok. Every evaluation calls it with `?` before durable admission (evaluation/async_evaluation_core.rs:355, evaluation/nested_flow_evaluation.rs:359), and chio-control-plane durable_admission.rs:263 propagates it at attach. The sweep defers per-operation failures but returns the first one at the end (recovery.rs:358-360). So one operation that can never reconcile leaves the flag false. Every later tool call then re-runs the whole sweep and returns a bare Err with no signed receipt, kernel-wide, until an operator repairs the row. Reachable triggers found in this slice: (a) pre-dispatch compensation of a prepaid or Settling-release payment can never succeed (admission_coordinator.rs:1766-1777, separate finding); (b) a tool-reported cost above the authorization or a cross-currency oracle failure fails finalization deterministically (terminal_payment.rs:93-106); (c) a replay after partial finalization recomputes a live FX quote or purchase status and conflicts with the persisted Resolved record (terminal.rs:1397); (d) a deterministic exact-output guard denial at finalize (terminal.rs:414 via evaluate_durable_post_return_output) leaves the operation Finalizing; (e) a restart with a changed post-invocation pipeline or security hook changes the recomputed request hash (terminal/evaluation_contract.rs:19-36). Separately, several `?` abort the sweep outright, contradicting the comment at recovery.rs:140-144: try_own_operation (165), durable_nonce_issuance_is_live (208), durable_caller_reservation_is_live (214), load_original_request_for_finalization (296), load_durable_tool_return (309), recovery_request (311) and claim_admission_recovery in the catch-all arm (350). The no-progress break at 353 also stops at the first page: if 256 head rows are all skipped, later operations are never visited, yet startup is marked reconciled. Each failing request runs the sweep while holding the std::sync::Mutex `startup_reconciled`, including payment rail release and capture HTTP calls, so concurrent requests block Tokio workers and the rail receives one retry per inbound request. The deferred-failure design predates this PR; this PR moves it into the new recovery.rs and adds the new `?` sites.

Fix direction: Latch startup reconciliation once every recoverable row has been visited. Persist a quarantine marker with the typed error for rows that fail, retry them with backoff off the request path, and deny only requests whose request id maps to a quarantined operation. Convert the remaining `?` into per-operation deferral, page with a cursor instead of re-querying from the head, and never hold a std Mutex across the sweep.

### F005 [P1] Settle over-reported or unconvertible costs instead of failing finalization

Location: [`crates/kernel/chio-kernel/src/kernel/admission_coordinator/terminal_payment.rs:103`](https://github.com/bb-connor/arc/blob/d0496c14d824a327f00b98576132834306ff6694/crates/kernel/chio-kernel/src/kernel/admission_coordinator/terminal_payment.rs#L103). Slice: Kernel admission, evaluation, dispatch and recovery. Confidence: high.

### F006 [P1] Stop a post-commit clock error from permanently closing the receipt writer

Location: [`crates/platform/chio-store-sqlite/src/receipt_store/writer_accounting.rs:174`](https://github.com/bb-connor/arc/blob/d0496c14d824a327f00b98576132834306ff6694/crates/platform/chio-store-sqlite/src/receipt_store/writer_accounting.rs#L174). `WriterCommandPermit::finish(committed = true)` reads `self.health.clock` only to stamp `last_commit_unix_ms`. On any `ClockError` it calls `accounting_error`, which sets `accounting_poisoned = true` (writer_accounting.rs:66). Nothing ever clears that flag. ### F007 [P1] Stop a backed-off declassification receipt from halting response planning

Location: [`crates/platform/chio-control-plane/src/security/scheduler_worker/outbox.rs:228`](https://github.com/bb-connor/arc/blob/d0496c14d824a327f00b98576132834306ff6694/crates/platform/chio-control-plane/src/security/scheduler_worker/outbox.rs#L228). Slice: Control-plane security pipeline (adapters, event consumer, scheduler). Confidence: high.

`drain_one_batch` returns `DeclassificationOutboxNoProgress` whenever `acknowledged == 0` and `remaining > 0`. The two numbers come from different queries. The batch query (`PENDING_BATCH`) only selects rows with `next_attempt_at <= now`, but `count_pending_declassification_evidence` (`COUNT_PENDING`) counts every unacknowledged row, including rows still in retry backoff. `record_declassification_evidence_retry` schedules retries with `declassification_retry_deadline_unix_ms`, starting at 1 s and doubling up to 3,600,000 ms. So once any receipt is backed off and nothing else is due, every drain reports no progress. The error then spreads. `SqliteResponseWorkerPort::tick` calls `outbox.maintain_one_batch()?` (`scheduler_worker/scheduler.rs:389`). `PlanningRecoveryResponseWorkerPort::tick` calls `self.inner.tick(..)?` (`orchestration.rs:707`) before `correlation_ingress.drain_once` and `planner.resume_incomplete_pass`, so correlation re-drive and response planning are skipped for the whole backoff window. The worker also goes Degraded. The same mismatch breaks `drain_to_zero` (`outbox.rs:204`), which runs from `reconcile_and_drain_startup` (`orchestration/teardown.rs:715`) and from `SqliteResponseWorkerPort::shutdown` (`scheduler.rs:402`). As a result the host refuses to start and cannot shut down cleanly until the backoff expires. Failure scenario: the receipt sink is down for about two hours, so retries grow to the 1 h cap. After the sink recovers, active-response planning for new findings stays halted for up to an hour, and restarting the process does not help.

Fix direction: Report `remaining_due` separately from `remaining_total`. Count lack of progress only against due rows, and return Ok with a Pending health state when every remaining row is backed off. In `PlanningRecoveryResponseWorkerPort::tick`, run ingress drain and planning even when the inner tick fails on declassification maintenance, the same decoupling already applied to rollback. Make the startup and shutdown drains either wait for the earliest due time within their budget or accept backed-off rows as durable pending work.
