### V01 P1 (confirmed): Cluster authority sync now fails on an unpinned database or a lagging clock, and that failure returns before the revocation lane, so followers stop learning about revocations

- Where: `crates/platform/chio-control-plane/src/trust_control/cluster/deltas.rs:459` (introduced by 0fd0a9d66)
- Reviewer area: control-plane

**Scenario.** This affects a trust-control cluster with authority_db_path (SQLite capability authority) and two or more nodes. Writes go to the leader (forward_post_to_leader). Followers serve GET /v1/revocations?capability_id from their local store (authority_handlers.rs:489-524, no leader forward), so they only learn about a revocation through the per-peer sync round. This PR changed sync_peer_authority from snapshot()/apply_snapshot() to signed_snapshot()/apply_signed_snapshot(). Both new calls now fail deterministically in two cases. (a) The authority DB has no out-of-band replication pin. require_replication refuses with 'authority replication requires an out-of-band pinned anchor'. Pinning is a manual CLI step (chio-cli federation replication), and trust-control startup never checks for it. That describes every existing cluster after upgrade until an operator runs the step. (b) A follower's clock trails the signer by 1 s or more. The envelope's issued_at is the signer's now in whole seconds, and verify refuses `proof.issued_at > now`. Either failure makes sync_peer `return Err` at deltas.rs:459-462, before lane 1, before the Lane 2 revocation pull at :487-505 that the code says must never be starved, and before finalize_peer_sync_round. The forced-snapshot path has the same ordering: apply_signed_snapshot at snapshots.rs:326 runs before the revocation import at :330. Result: an operator revokes capability X on the leader. The leader returns success after leader-only visibility. Every follower keeps answering revoked=false for X indefinitely. A kernel or verifier that points --control-url at a follower (or a load balancer) keeps accepting X. On origin/main the same early return existed, but the unsigned apply_snapshot did not fail under these conditions, so revocations still replicated. A related intermittent failure in clusters of three or more nodes (plausible): the leader pulling from a follower gets that follower's relayed envelope. When another follower has pulled the leader more recently, apply_signed_snapshot refuses it as 'authority envelope replay regresses issuance time', which also skips finalize_peer_sync_round (the only production caller of update_peer_budget_acks).

**Evidence at fd8bfdc.** deltas.rs:459-462 `if let Err(error) = sync_peer_authority(state, &client) { update_peer_sync_error(...); return Err(error); }` precedes deltas.rs:487 `// Lane 2: revocations replicate on their OWN round budget, INDEPENDENT ... can never starve security-critical revocation propagation` and :498 sync_peer_revocations; deltas.rs:643-656 sync_peer_authority now `let snapshot = client.authority_snapshot()?; authority.apply_signed_snapshot(&snapshot)?;` (origin/main: `authority.apply_snapshot(&authority_snapshot_from_view(client.authority_snapshot()?))`); chio-store-sqlite authority/replication.rs:141-147 apply_signed_snapshot -> `let mut replication = require_replication(&transaction)?;` then `snapshot.verify(..., now.as_secs())`, :159-164 regression check `proof.issued_at < old.issued_at` -> refused("authority envelope replay regresses issuance time"), :116-121 signer path signs with `now.as_secs()`, :122-126 a follower relays `replication.latest` or refuses "follower has no authenticated live envelope to relay"; authority/replication/persistence.rs:76-80 require_replication -> refused("authority replication requires an out-of-band pinned anchor"); chio-kernel authority/replication.rs:346-352 `if proof.issued_at > now || proof.expires_at <= now ... { return Err(refused("authority envelope outside freshness window")) }`; the only production callers of initialize_replication/pin_replication_anchor are chio-cli dispatch/federation/replication.rs:30,117 (none in trust_control init); snapshots.rs:326 `authority.apply_signed_snapshot(&authority_view)?;` before :330 revocation store import; authority_handlers.rs:497-509 handle_list_revocations answers is_revoked from the local state.revocation_store().

### V03 P2 (confirmed): Canonical release signatures are minted before the exact-source gate, and the documented verifier does not bind the source commit

- Where: `.github/workflows/release-binaries.yml:545` (introduced by 0fd0a9d66)
- Reviewer area: ci-supply

**Scenario.** Someone with tag-push rights pushes v1.2.3 at the wrong commit. That could be a commit whose CI later fails, a commit not on main, or a mis-tag that is later deleted and re-pushed at the right commit. The matrix build job signs each archive at once with the canonical keyless identity (release-binaries.yml@refs/tags/v1.2.3). It also uploads the signed archive plus .sig/.pem as run artifacts, which anyone signed in can download on this public repo, and Rekor logs the signature. The exact-source gate runs only later, in the release job, and refuses publication. By then a signed archive from an unqualified commit already exists. The consumer recipe in docs/install/VERIFY.md calls verify-release-identity.py verify, which checks only the certificate identity and issuer, so it accepts that archive as a genuine v1.2.3 release. The npm and PyPI lanes have the same order: they sign in the build job and run check-release-source-gates.py only in the publish job. The PR's claim that publication requires matching successful source checks therefore does not cover the artifact-authenticity check that consumers actually run.

### V06 P2 (confirmed): Registries the trust-control service writes without a size limit become unreadable once they pass the new 16 MiB read cap, and the never-pruned OID4VCI offer registry gets there in normal use

- Where: `crates/platform/chio-control-plane/src/passport_verifier.rs:441` (introduced by f16d4e781)
- Reviewer area: control-plane

**Scenario.** A long-running trust-control issuer handles POST passport issuance offers. Each issue_offer inserts a PassportIssuanceOfferRecord that embeds the full AgentPassport and the OID4VCI offer. Nothing ever removes offers (no retain/remove/prune in passport_verifier.rs). Each request loads the registry, changes it, and calls save, which writes serde_json::to_vec_pretty(self) with no size check. After enough offers the pretty-printed file passes 16 MiB. From then on every offer, token redemption and credential redemption returns 409 CONFLICT (passport_handlers.rs:150-153, :191-194, :222-225), and the only operation that could shrink the file (save) never runs again. ### V17 P2 (confirmed): Flow classification re-parses the whole payload JSON once per field-path finding (unbounded total parse work per tool output)

- Where: `crates/security/chio-flow/src/classification.rs:197` (introduced by 6ea79bb5d)
- Reviewer area: security

**Scenario.** A tool returns a JSON output close to MAX_CLASSIFICATION_PAYLOAD_BYTES (4 MiB) that contains many classifier-matching leaves (for example 256 PII-looking strings at distinct JSON paths). The production StructuredClassificationAdapter maps each match to a FindingLocation::FieldPath finding, so the ClassificationResult carries up to 256 field-path findings. CategoryLabelMap::verify_result loops over every finding and calls validate_finding, which for each field path calls validate_field_path, which re-decodes the entire payload with UntrustedJsonText::from_wire(...).decode_signed() into a serde_json::Value and then runs a JSON pointer lookup. One classification therefore performs up to 256 full decodes of a 4 MiB document (about 1 GiB of JSON parsing and Value allocation) on the synchronous post-invocation flow path. The work is multiplicative in tool-controlled content, not bounded by any per-request budget; concurrent invocations amplify it. Parsing the payload once and resolving all pointers against the single Value removes the amplification.

### V24 P2 (confirmed): Re-importing a retained exported copy deletes the destination's rollback anchor, letting a store that already served be rolled back to the export point

- Where: `crates/platform/chio-store-sqlite/src/serving_owner/relocation.rs:706` (introduced by 7599eb9d1)
- Reviewer area: store-sqlite

**Scenario.** Store exported at P1, imported at P2 under lock root L2, then serves (owner epoch rises, admissions, budget captures and nonce reservations commit; L2/<uuid>.lock anchors that history).
