# Execution review: product, CLI and provider reader batches, October 1, 2026

Scope: the four September 30 reader batches. `943482d2cb` covers product authority readers and proof custody, `da4086017f` CLI authority and proof input, `82eec927b2` the remaining CLI readers and private custody, and `6ef28e8f4d` provider readers and streaming capture. I reviewed them against their plans (`docs/superpowers/plans/2026-09-30-product-authority-readers.md`, `...-cli-authority-proof-readers.md`, `...-cli-remaining-readers.md`, `...-provider-reader-boundaries.md`), their execution records (`docs/reviews/2026-09-30-*-execution.md`) and their artifact logs. Base `07e963e8f5`, tip `a2630c20a1`. Method: I read each diff and then the resulting code at the tip, traced every changed decoder to the producer of its input, checked test counts and census numbers against the retained logs and inventory history, and read the repository's own fixture writers and CI workflows for the readers whose contract changed. I ran no cargo builds. Every finding below rests on source traces and, for PR1, on an existing passing core test.

**Judgment: The batches fixed real defects at the network edges. Provider responses were collected with an unbounded `.bytes()`. Provider error bodies and request URLs (including Gemini's query-string key) appeared in error text. Fragmented streaming tool calls were evaluated before they were complete. A stale request-ID cleanup could release a newer owner. Certificate session selection used a `LIKE` prefix. Read-only trust queries created signing keys. Their main failure is choosing a decode mode by lexical habit instead of by who produced the input. The signing canonicalizer now rejects ordinary provider output and tool results such as `21.0` (PR1, High). `decode_signed` rejects Python SDK floats and hand-written JSON policies (PR2). Byte-canonical, 0600 key custody was imposed on relay keys that the repository's own xtask writer and committed fixture cannot satisfy, which breaks four CI fixture workflows (PR6, High). The records are accurate about what they ran (every test count and census number matches its log), but they ran only focused tests, so these regressions went unseen. The reader-census goal (278 to 166 baseline files) drove a large amount of uniform migration and five more duplicated `input.rs` owners. The provider, API-protect, proof-room upload and CLI network-peer readers sit on real trust boundaries, and that work was worth doing. The operator-local CLI readers (policies, certificates, local key files, bundles the operator built) gained parser strictness that protects nothing, and in PR2 and PR6 it rejects valid input.**

## PR1. High: provider adapters apply the signing canonicalizer to whole provider responses and to tool results, so ordinary output such as `21.0` or a 64-bit ID now fails the call

`6ef28e8f4d` replaced `serde_json::from_slice` with `chio_provider_adapter_core::input::json` at every non-OpenAI adapter entry point. That helper is not an I-JSON reader; it is the signing-input canonicalizer: `crates/protocol/chio-provider-adapter-core/src/input.rs:17-23` calls `UntrustedJsonText::canonicalize`, which is `canonical_json_bytes_from_str`. Its visitor rejects every integer-valued float token at any depth (`crates/core/chio-core-types/src/canonical.rs:781-787`) and every integer outside +/-(2^53-1) (`canonical.rs:740-744`). The core crate's own test pins `"1.0"`, `"100.0"`, `"0.0"`, `"-5.0"`, `"1e2"` and `"2.5e1"` as rejections (`canonical.rs:1243-1254`). RFC 7493 I-JSON permits all of those float spellings; the rule exists to stop a signer from signing a value it did not see, which is not what these readers do.

The new contract now sits on two production paths that carry arbitrary numbers:

1. Tool results being lowered back to the provider. `parse_tool_result_envelope` and `parse_tool_result_content` (`crates/protocol/chio-anthropic-tools-adapter/src/adapter.rs:286-316`), Bedrock `parse_tool_result_content` (`crates/protocol/chio-bedrock-converse-adapter/src/adapter.rs:360-363`) and the `parse_value` helpers used by every allow-path `lower` in Groq (`crates/protocol/chio-groq-tools-adapter/src/lib.rs:395-397`, caller `:431`), Mistral (`lib.rs:432`, caller `:367`), Cohere (`lib.rs:367`, caller `:403`), Ollama (`lib.rs:389`, caller `:313`) and Gemini (`src/adapter.rs:341`, caller `:377`). A tool result is whatever the host application serialized. A Rust host that serializes an `f64` of 21 with `serde_json::to_vec` emits `21.0`; Python's `json.dumps` does the same; database tools routinely return nanosecond timestamps or 64-bit row IDs above 2^53. Each of those results now fails `lower` with `signed-json-canonicalization` after the call was already allowed and executed, so the model never receives the result.
2. Provider response bodies and tool arguments. `tool_use_blocks` (`chio-anthropic-tools-adapter/src/adapter.rs:184-189`), the Groq, Mistral, Gemini and Ollama `response.rs` readers, the Bedrock response interceptor that canonicalizes the entire Converse body before the SDK sees it (`crates/protocol/chio-bedrock-converse-adapter/src/transport/bounded_response.rs:92-101`), the NDJSON reader (`crates/protocol/chio-provider-adapter-core/src/http.rs:728`) and every assembled streaming argument string (`streaming/assembly.rs:195`) all reject a model that writes `{"amount": 100.0}` or `{"user_id": 1234567890123456789}`.

Before the commit, every one of these entry points used `serde_json::from_slice`, or `serde_json::from_str` for argument strings (`chio-provider-adapter-core/src/response.rs:92-96` at `82eec927b2`), and accepted these values. The same commit also switched `ContractResponse::json` in the egress contract (`crates/protocol/chio-egress-contract/src/reqwest_helper.rs:46-53`) to this reader. That widens the rule to OAuth introspection and session-identity responses in `chio-mcp-remote`, although those documents rarely carry floats. The numeric contract is also inconsistent across adapters. OpenAI response bodies still use `decode_signed` (`crates/protocol/chio-openai-adapter/src/input.rs:10-12`), which accepts `100.0`. The SSE frame reader also uses `decode_signed` (`crates/protocol/chio-provider-adapter-core/src/sse.rs:221-225`), which accepts `100.0` and rejects `2.50`. The non-streaming bodies of the other six adapters use the strict canonicalizer, which rejects `100.0` and accepts `2.50`. So the same model output is accepted or refused depending on the provider and on whether the call streamed.

The safety argument for strictness does not apply here. The gate evaluates the canonical projection and returns the original bytes (`GatedStream::new(raw.to_vec(), ...)`, `crates/protocol/chio-provider-adapter-core/src/streaming.rs:71`). Duplicate-key rejection is the part that closes the evaluate-one-value, execute-another gap, because parsers disagree on which duplicate wins. Every conforming parser reads `100.0` and `100` as the same number, so rejecting `100.0` buys no safety. Integers above 2^53 are a real cross-language ambiguity, but rejecting them belongs in an explicit, documented provider policy, not a side effect of reusing a signing helper. The provider fixtures contain no integer-valued floats or large integers (`grep` over the 103 files under `crates/protocol/chio-provider-conformance/fixtures`), so the 596 recorded passing tests could not have caught this.

Fix: give provider ingress its own documented contract: duplicate-key rejection at every depth, a size bound, and ordinary float acceptance. The canonicalizer's stated reason for refusing `100.0` is that the original lexeme cannot be recovered (`canonical.rs:758-780`). That reason does not hold on this path, because `reject_over_precise_numbers` already scans the original tokens (`canonical.rs:611-656`). A token whose fractional digits are all zero and whose magnitude is below 2^53 can therefore be accepted safely. `decode_document` (added later at `377ee5b773`) is close to this. Decide explicitly whether integers above 2^53 reject, then apply that one rule to responses, frames, NDJSON and arguments in all eight adapters, OpenAI included. Do not apply ingress strictness to `ToolResult` at all: the host produced it, and the provider only needs valid JSON. Add fixtures with `1.0`, `0.0`, `1e-05` and a 19-digit integer in arguments and in tool results.

**Confidence:** Confirmed. The step-by-step source trace from each adapter entry point to `canonical.rs:781`, together with the existing passing core test that rejects `"100.0"` and `"0.0"`, establishes the behavior. How often models emit `N.0` is a judgment, but serializers emitting it for tool results is not.

**Independent verification:** Confirmed, High, by a probe test against the real functions and
through `AnthropicAdapter::lift`: a tool `input` of `21.0`, `0.0` or `9007199254740993` fails with
`signed-json-canonicalization` while `21` and `21.5` pass, and `lower()` rejects a tool result
that `serde_json::to_vec` produced from the `f64` `10.0`, so Chio rejects its own serializer's
output. The whole response document is checked, so a float anywhere fails the call. Corrections:
seven adapters moved from `serde_json::from_slice` in `6ef28e8f4d` (anthropic, bedrock, cohere,
gemini, groq, mistral, ollama); OpenAI's argument path was already strict from `53858afa39`. The
rule is I-JSON `canonicalize`, which accepts `1e-05` and `0.50`; the integer ceiling is 2^53-1.
No adapter test or committed conformance fixture contains a non-shortest float, which is why
nothing caught it. The measured numeric contract of each mode:

| Decoder | Rejects | Accepts |
| --- | --- | --- |
| `canonicalize` / `decode_external` | `21.0`, `0.0`, `10.00`, `1e+16`, integers above 2^53-1 | `0.50`, `1e-05`, `1e-5` |
| `decode_signed` | `10.00`, `0.50`, `1e-05`, `1e-5` (only `0.00001` passes) | `21.0`, `0.0`, `9007199254740993` |
| `decode_document` | no numeric spelling | every valid number |

No strict mode accepts what ordinary serializers emit: Python `json.dumps` writes `1e-05`, which
`decode_signed` rejects, and serde writes `10.0` for an `f64`, which `canonicalize` rejects.

## PR2. Medium: `decode_signed` is applied to input that Chio's own writers did not produce, so ordinary float spellings from Python clients and hand-written policies now reject

`943482d2cb` changed every sidecar body reader from `serde_json::from_slice` to `input::decode`, which is `decode_signed` (`crates/products/chio-api-protect/src/proxy/input.rs:10-15`). This covers `/chio/evaluate`, `/v1/evaluate`, `/v1/reconcile`, mint, release, receipts and aliases (`sidecar.rs:25,92`, `mediated.rs:288,683`). `decode_signed` accepts a number token only if it equals serde_json's ryu rendering or the ES6 canonical rendering (`crates/core/chio-core-types/src/canonical/signed_json.rs:137-146`). Python's `json.dumps(1e-05)` emits `1e-05` (float `repr` uses a two-digit exponent below 1e-4 and from 1e16 upward), which equals neither the ryu form `1e-5` nor the ES6 form `0.00001`; Python's `1e+16` is likewise neither `1e16` nor `10000000000000000`. JavaScript and Go emit ES6-compatible spellings and are unaffected. The mediated request carries arbitrary `parameters: serde_json::Value` (`mediated.rs:226-231`). The Python SDK builds `"parameters": parameters` and posts it to `/v1/evaluate` through `httpx` with `json=` (`sdks/python/chio-sdk-python/src/chio_sdk/client.py:646,656,991`). A LangChain tool called with `learning_rate=1e-05` therefore now receives HTTP 400 `signed-json-invalid-input` from a sidecar that accepted the same call before this commit.

`decode_signed` is the right reader for the `X-Chio-Capability` header and the signed nonce (`proxy/http.rs:121,155`), because Chio's own writer produced those signed records with full-width integers. It is the wrong reader for SDK-produced request envelopes. Their numbers come from other languages' serializers, and Chio hashes and evaluates the parsed value, not the original spelling. No test sends a Python-shaped float.

The same mode error recurs in the CLI. `input::config::load` (`crates/products/chio-cli/src/cli/input/config.rs:9-20`) sends every non-YAML policy file through `decode_signed`. `UnderwritingDecisionPolicy` carries `f64` fields such as `reduce_ceiling_factor` and `minimum_approve_reputation_score` (`crates/economy/chio-underwriting/src/decision.rs:102-110`). An operator's `policy.json` containing `"reduceCeilingFactor": 0.50` now rejects, because `0.50` is not the shortest spelling, while the same value parses through the YAML branch. Before `da4086017f`, both `trust/underwriting.rs` and `trust/shared.rs` parsed these files with `serde_json::from_str`. `decode_signed` protects nothing on a local, unsigned operator policy. Its contract exists so the signature verifier can rebuild the bytes a Chio writer signed.

The scale shows the selection was not made per reader. The three CLI commits add 208 lines that call `crate::input::{text,json,decode}` (a few of them in tests), and every one of those helpers is `decode_signed`. The first batch's 28 reader dispositions use 9 distinct contract strings, and one of those strings is repeated verbatim for 7 files (`artifacts/2026-09-30-product-authority-readers/reviewed-readers.json`). The working queue requires that "every assertion or decoder needs its real contract, not a mass syntactic replacement" (`docs/reviews/2026-09-28-remaining-security-work.md:60-61`). For the operator-local and SDK-facing readers, a mass syntactic replacement is what this is.

Fix: decode request envelopes and operator policies with duplicate-key rejection and ordinary numeric conversion (`decode_document`, added later at `377ee5b773`, or an equivalent), and keep `decode_signed` for embedded signed objects such as the capability token. Add regressions that post `{"parameters":{"x":1e-05}}` and load a JSON policy containing `0.50`.

**Confidence:** Confirmed for the decoder behavior, by source trace of `validate_number_tokens` against Python's float `repr`. That a deployed client sends such a value is Plausible.

**Independent verification:** Confirmed, Medium. Commit `943482d2cb` moved every sidecar
handler from `serde_json::from_slice` to `decode_signed`; the Python SDK's `_post` sends
`httpx json=`, so a parameter of `0.00001` arrives as `1e-05` at `/v1/evaluate/advisory` and is
refused with 400. On the CLI side (`da4086017f`), the affected JSON inputs are the underwriting
decision policy (with `f64` fields such as `reduceCeilingFactor`), credit, passport-verifier and
runtime-attestation inputs and the liability and capital request files. The main guard policy
loader (`chio-control-plane/src/policy/loader.rs`, `serde_yml`) and the `.yaml` variants are not
affected.

## PR3. Medium: the API-protect service clock turns any backward wall-clock step into a full outage that lasts as long as the step

`943482d2cb` replaced the scattered `chrono::Utc::now()` reads in API-protect with one `ProxyClock` (`crates/products/chio-api-protect/src/proxy/clock.rs:6-51`). The proxy, the embedded HTTP authority, the mediation kernel (`state.rs:672,783`), the replay stores and the reaper all share it. Every read passes through `ClockFence::observe` (`crates/security/chio-security-types/src/clock.rs:204-215`). After the first reading, `observe` returns `WallClockRegression` whenever the new wall time is below the stored high water, and it does not advance the high water on that error. Suppose NTP steps the host clock back 90 seconds, or a VM resumes from a snapshot. Then every `ProxyClock` read fails until real time passes the old high water. For that whole interval the mediated endpoint and the sidecar mint, release and receipt endpoints return 503 through `clock::rejection` (`clock.rs:53-59`, used at `mediated.rs:497` and `sidecar.rs:238,452,578,731,1146`). The embedded kernel shares the same clock, so it denies as well, and the reaper skips its sweeps (`state.rs:32-37`). A step of minutes is an outage of minutes. The only remedy is a restart, which discards the fence because it is in memory. That restart also shows the fence enforces nothing durable.

The fence is meant to keep TTL and replay windows from running backward inside the process. Clamping achieves that without the outage: return `max(reading, high_water)` and log the regression. Time then never decreases, replay windows stay monotone, and availability survives an ordinary NTP correction. The record presents the fence as a feature ("wall and monotonic high-water fence is serialized with observation") and never states the availability cost. The unit test `clones_share_high_water_and_faults_do_not_reset_it` (`clock.rs:79-92`) asserts the failure as intended behavior.

**Confidence:** Confirmed by source trace: `observe` keeps the old high water on error, and every mediated handler maps the error to 503.

## PR4. Medium: each crate grew its own `input.rs` with copied limits and readers, and the copies already disagree on the numeric contract

The four commits add five crate-local input owners: `crates/products/chio-cli/src/cli/input.rs`, `crates/products/chio-proof-room/src/input.rs`, `crates/products/chio-api-protect/src/proxy/input.rs`, `crates/protocol/chio-provider-adapter-core/src/input.rs` and `crates/protocol/chio-provider-conformance/src/input.rs`. Each restates the same pieces. A 16 MiB document constant appears 13 times as a crate-level `MAX_DOCUMENT_BYTES`-style constant across the workspace, and the 4,096-entry, depth-64 and 128 MiB collection budgets appear in both the CLI (`cli/input/collection.rs:5-7`) and proof-room (`input.rs:7-10`). The `O_NOFOLLOW | O_NONBLOCK`, `is_file`, `take(bound + 1)`, `TooLarge` reader is written out in `cli/input.rs:77-90`, `chio-proof-room/src/input.rs:30-52` and `chio-provider-conformance/src/input.rs:9-42`. Inside the CLI crate alone, the new shared reader sits beside three older private copies that were not folded in: `process_host/diagnostics.rs:131-154`, `process_host/state.rs:172-176` and `mcp/provision.rs:1687-1712`. In total, 31 workspace files carry a nofollow-plus-`take` reader.

The cost is not only style. The copies already chose different decode modes for the same class of input. Provider responses are `decode_signed` in OpenAI (`chio-openai-adapter/src/input.rs:10-12`) and the strict canonicalizer in the other six adapters (PR1). SSE frames are `decode_signed` while NDJSON frames are canonicalized (`chio-provider-adapter-core/src/sse.rs:221-225` against `http.rs:728`). CLI documents are `decode_signed`. `chio-core-types` already owns `UntrustedJsonText`. One shared owner there, holding the bounded regular-file reader, the bounded stream reader and a named mode per input class, would let the trust-boundary gate check one helper instead of tracking 31. Standard rule 1.5 ("one invariant, one implementation") applies.

**Confidence:** Confirmed. The copies and their differing modes are cited above.

## PR5. Medium: compliance certificates now fail for any ACP session with more than 4,096 receipts, and any one oversized row anywhere in the receipt table fails every session

`load_session_receipts` (`crates/products/chio-cli/src/cert.rs:225-270`) now charges each row to the proof-collection `Budget` (`budget.enter(0)` at `:261`) and requests `MAX_ENTRIES + 1` rows (`:248`). Certificate generation (`:34`) and verification (`:106`) both call it. When a session has 4,097 receipts, the command fails with "artifact collection entry limit exceeded". It offers no streaming path or override, and the message names the wrong subsystem. Long agent sessions where every file read is a tool call reach this count, and before this commit the command handled them.

The `WHERE` clause also selects every row that is not text, is larger than 1 MiB, or is not valid JSON (`ELSE 1`, `:241`). The projection maps those rows to `NULL`, so `row.get::<_, String>` fails. One malformed or oversized receipt from an unrelated session therefore blocks certification of every session. Failing closed is the intent, but these rows are not in the requested session, and a corrupt row should be reported, not used to block every certificate.

The exact-session selection is a real fix. The old `LIKE 'acp-session:{id}%'` matched `target-extra` and treated `_` and `%` as wildcards, and the new tests cover both. The cap and the global failure are new costs that the record does not mention.

Fix: give certificates their own documented session limit, or stream and hash receipts incrementally. Report rows that fail to decode by `rowid` instead of selecting them into every query.

**Confidence:** Confirmed by source trace of the query and the shared budget.

## PR6. High: relay and iroh key readers now demand byte-canonical JSON at mode 0600, but the repository's own fixture writer and committed example key produce neither, so the relay fixture CI jobs fail

`82eec927b2` moved `load_relay_signing_key` (`crates/products/chio-cli/src/cli/chio/dispatch/pheromone/io.rs:43-61`) and `load_transport_secret_key` (`iroh_mount.rs:226-233`) from `serde_json::from_str` to `input::private::read` (`crates/products/chio-cli/src/cli/input/private.rs:22-30`). That reader first calls `read_private_signing_custody`, which refuses any file that is not singly linked, owned by the effective user, and free of group and other permission bits (`crates/platform/chio-control-plane/src/signing_custody.rs:98-117`). It then calls `decode_canonical`, which refuses any file whose bytes differ from the canonical re-serialization (`untrusted.rs:83-93`). The rejected differences include whitespace, key order and a trailing newline.

No Chio command writes these key documents. The two writers that exist both violate both rules:

1. `xtask/src/fixtures_facets.rs:1479-1491` writes the relay key with `serde_json::to_string_pretty` plus `"\n"`, using default permissions. It then runs `chio pheromone relay tick --signing-key` on that file (`:999-1044`, `:1612-1625`). `cmd_chio_pheromone_relay_tick` loads the key unconditionally (`relay.rs:486-515`).
2. The committed example key `examples/chio-3vendor/fixtures/pheromone/relay/alert-assurance/relay-alert-assurance-export-signing-key.json` is pretty-printed, ends in a newline, and is stored at git mode `100644`. `xtask/src/fixtures_facets_assurance.rs:50-51,428,484` passes it to `relay alert assurance export` and `archive package`. Both call `load_relay_signing_key` (`assurance/package.rs:134`, `assurance/archive.rs:136`).

The workflows `chio-pheromone-relay.yml`, `chio-pheromone-relay-ops.yml`, `chio-pheromone-relay-alert-assurance.yml` and `chio-pheromone-relay-alert-assurance-archive-package.yml` run these xtask facets on every change under `crates/products/chio-cli/**`, so they now fail deterministically. Operators are in the same position. The runbook (`docs/release/CHIO_PHEROMONE_RELAY_RUNBOOK.md:78`) says only `--signing-key relay-signing-key.json`, and the doc comment on `load_transport_secret_key` (`iroh_mount.rs:226`) describes the file as `{ "seedHex": ".." }`, a spelling that the new reader rejects. Nothing tells an operator to write sorted, whitespace-free bytes with no trailing newline.

The execution record ran 266 focused tests and its source ratchets. It did not run the xtask fixture facets, and it describes the change only as "Relay and transport seeds use canonical private wiping custody". The plan's "no pre-ship compatibility paths" rule rules out a fallback parser. It does not excuse leaving the repository's own writer and fixture on the old format.

Fix: canonical equality buys nothing for a local seed file that is not signed. Read these files with duplicate-key rejection into a zeroizing field, keep the 0600 and single-link checks, and accept a trailing newline. If byte-canonical custody is required, ship a `chio pheromone relay keygen` that writes it, update `write_signing_key` and the committed fixture, document the format in the runbook, and run the xtask facets as part of the batch's qualification.

**Confidence:** Confirmed by source trace: the xtask writer's output fails both the `mode & 0o177` check and canonical equality, and the CI path filters include `crates/products/chio-cli/**`. I did not run the workflows.

## PR9. Note: several custody and clock mechanisms cost more than the protection they provide

These mechanisms work as described. The question is whether they are proportionate.

- `finding_operator_profile/custody.rs` (293 lines) mirrors every private profile struct field by field so that partial deserialization wipes secrets. The target structs still expose the secrets as `pub String` fields with derived `Clone`, `Serialize` and `PartialEq` (`finding_operator_profile.rs:43-60,86-130,161-176`). Any consumer can copy a token into a non-wiping `String`, and comparisons are not constant-time. A `SecretString` field type with redacted Debug and no Clone would protect more with less code and without two field lists that must change together.
- `read_private_signing_custody` preallocates and zero-fills `maximum_bytes + 1`. The federation signing-keys path passes 16 MiB (`cli/chio/dispatch/authority.rs:27-29,103-105`), so it allocates 16 MiB to read a keys file of a few hundred bytes.
- `cli/input/time.rs:5-11` keeps a process-global `ClockFence` in a one-shot CLI process. The fence can only catch a regression between two reads inside a single short command.
- The fixture recorder's subprocess capture (`chio-provider-conformance/src/bin/record/process.rs`, 212 lines) adds process-group ownership, kill-on-drop and descendant-reaping tests for a developer tool that shells out to `aws` to record fixtures. Removing the API key from `curl` argv was the valuable part.
- `Budget::read` zeroes the shared budget on any failed read (`cli/input/collection.rs:47-53`). All 20 production callers propagate that error with `?`, so the extra state change protects no current path.

## PR10. Low: the worker-response reader was declared bounded, but its recursive parser copies each subtree once per nesting level

`943482d2cb` put a 16 MiB check in front of `checked_json::parse` (`crates/products/chio-cli/src/cli/process_response_verify/json.rs:13-19`) and recorded the reader as bounded. The parser underneath predates the commit. At every object or array level it deserializes the children into `Box<RawValue>` (`:31-50`). `Box<RawValue>` owns a copy of its text, and the copy for the subtree being descended stays alive for the whole recursion. Take a 16 MiB document whose payload string sits 63 objects deep, for example `{"a":{"a":...{"a":"<16 MiB>"}}}`. That document holds about 64 copies of the string at the deepest point, roughly 1 GiB, and scans the text 64 times. The input is an offline worker response file (`process_response_verify.rs:1`), so the exposure is an operator running verification on a hostile file, not a network service. The fix is a single pass: deserialize once through a duplicate-rejecting visitor such as `signed_json`'s `StoredValue` and check number tokens with `decimal_identity` in that same pass. The same file also declares its own `MAX_DOCUMENT_BYTES: u64` (`process_response_verify.rs:14`), next to `crate::input::MAX_DOCUMENT_BYTES` (PR4).

**Confidence:** Confirmed by source trace. `Box<RawValue>` deserialization allocates an owned copy, and the loop variable keeps the parent copy alive during the child call.

## Verified clean

- Provider HTTP collection bounds each chunk before appending, and checks `Content-Length` first (`http.rs:605-629`). The old `.bytes()` was unbounded. `reqwest`'s client timeout covers body reading, so a slow-drip stream ends at the total deadline (60 s default).
- Gemini's API key travels as a query parameter. `map_send_error` and `collect_response` call `without_url()`, and the old `Timeout { url }` and `Status { body }` Displays were removed. Before this slice, a timeout or provider error could print the key or echoed prompt content.
- Streaming assembly (`streaming/assembly.rs`) checks per-call 1 MiB argument bounds before append, a 1,024 call and choice cap, id and name stability, duplicate call ids, terminal state and the `[DONE]` sentinel before any evaluator call. The old per-frame evaluation could evaluate partial argument fragments.
- API-protect request bodies are capped by `to_bytes` before decode. The capability header and signed nonce correctly use `decode_signed`. Request-ID capacity cannot be filled by unauthenticated callers, because claims are released on any non-allow verdict and claims serialize under the kernel lock.
- Proof-room upload: the 32 MiB body limit applies before allocation, path validation covers the whole namespace before `create_dir_all`, and the verified identity comes from the sealed result.
- CLI shared readers (`cli/input.rs:61-90`) use `O_NOFOLLOW | O_NONBLOCK`, an `is_file` check and `take(bound + 1)`, so FIFOs and oversized files cannot block or allocate past the bound.
- `decode_signed` followed by `serde_json::from_value` is lossless for the domain it accepts. The workspace enables `float_roundtrip` but not `arbitrary_precision`, `decode_signed` rejects integers above `u64` at the token check, and `Value` keeps `i64`, `u64` and `f64` exactly. The strict canonicalizer re-renders accepted floats in shortest form, which `from_slice` parses back exactly.
- `input::literal` (`cli/input.rs:57-59`) replaces `serde_json::from_str(&format!("\"{value}\""))`, closing quote injection into enum arguments.
- Proof export captures a private snapshot, verifies it, and packages those same bytes (`proof/export.rs:108-116`).
- No em dashes, no process vocabulary in code comments, and no production `unwrap`/`expect` in the added lines of the four commits. Oversized allowlisted files (`proof/fixture.rs`, `proof.rs`, `iroh_mount.rs`) shrank rather than grew.
- The secret-bearing types touched here (`Seed`, `RelaySigningKeyDocument`, `IrohTransportKeyDocument`, `HttpTransportConfig`, `AuthScheme`, `HttpTransportError`) have either no `Debug` or a redacted one.

## Recommendations for the remaining plan

1. Before the next reader batch, write down a decode-mode policy keyed by producer, and make the trust-boundary inventory record the producer for each reader. Chio-written signed artifacts use `decode_signed`. Chio-written canonical storage uses `decode_canonical`. External protocol input (provider, SDK, MCP, OAuth) and operator-authored files use duplicate-key rejection with ordinary numbers. Re-audit the 112 baseline entries retired in these four batches (278 to 166) against that table. PR1, PR2 and PR6 are three instances of the same missing rule.

The few positive controls use canonical or hand-picked spellings (for example, the private-key test's only accepted file is `{"seed":"value"}`), not real serializer output.
