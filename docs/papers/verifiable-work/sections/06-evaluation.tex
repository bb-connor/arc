\section{Evidence and comparison}
We distinguish current D1, S1 and composed funded qualification from retained
F1 experiments and September process evidence. Each has a source inventory; historical tests are
checked against their preserved source tree rather than attributed to modified
native code. All reported executions use author-controlled infrastructure.
Fixture balances and development-chain tokens have no economic value.

\subsection{Dynamic delegation in the native kernel}
The Rust allocator implements root creation, signed subdivision, revisioned
selection, sealing and portable verification. The native guard is an opt-in
public installation API. Sixteen allocator tests cover recursive holders,
concurrent sibling overcommit, selection/dispatch races, reopen, malformed
predicates, expiry, integer bounds, authority substitution and offer reuse
against changed terms, cross-owner namespace replay and persistent allocator
identity. The full workflow crate run also exercises its existing
tests; the artifact does not count those as new delegation experiments.

Nine substantive native tests cover dynamic provider choice, exact request and
capability binding, offline-allocator execution, receiver substitution, output
rejection before and after transforms, the configured receiver clock, required
durable custody, governed-context payload preservation, and actual
process-kill recovery with useful sibling progress. The native runner reports
ten test labels because one is the subprocess worker. Recovery retains the
original request and produces zero new tool dispatches after the selected cut.
Rejected output yields a signed zero-charge denial in the qualified fixture.

The runnable example constructs a tree after startup, delegates through a
second holder, replaces one selected provider before sealing, and executes
through the replacement's kernel. Reopening its independent native store
returns the same receipt without another call. A sibling then completes, and
fixture balances conserve their initial 1,000 units. Receivers hold separate
keys and stores under one administrator; no remote network interoperability,
independent operator or LLM planning result follows from this example.

A semantic negative test exposed an offer that authenticated only a slot name:
the offer could be reused with different acceptance terms. Binding the full
slot digest closes that case; the failing and passing outputs are retained.
Fresh review also exposed signed mutations crossing honest allocator namespaces;
binding the allocator, root and slot closes subdivision and selection replay.
A further native regression found that a guard bypassed the configured clock;
the guard now uses the kernel's fenced authority clock.
Compiler and fixture-configuration failures are retained separately and are
not presented as protocol counterexamples. The qualification also reruns the
existing three-owner native regression, checks Rust lints and formatting, runs
the example and tests artifact provenance. These are bounded engineering
checks, not a statistical estimate of production reliability.

\subsection{Evolution through existing swarm and treaty authority}
Five new verifier tests exercise checked growth, individually valid re-signed
rewrites, caller-owned time and trust, duplicate attempts and budget bounds.
Four store tests cover exact history after reopen, rollback after a rejected
extension, simultaneous proposals through separate SQLite connections, and
corrupted historical data. The race produces exactly one successor.

Three native trajectories exercise the effect boundary. First, an original
worker executes, the graph grows, and the added worker executes. After reopen,
replay returns the exact original receipt and physical claim; a fresh request
for its consumed continuation is denied even though its ordinary capability
still has invocation headroom. Second, an original unstarted worker executes
under its historical graph after extension. Third, a combined bilateral-treaty
and swarm operation retains its three physical resources across extension and
restart. The test explicitly revalidates the original claim, rejects a request
with treaty context removed, and replays without another effect.

The qualification runs the complete swarm-authority and runtime-core crate
suites, their all-target lints and formatting, alongside D1's checks. These are
tests of one implementation under author-controlled stores. They establish no
new consensus mechanism, automatic receiver migration or independently operated
network. The companion preserves the initial compiler and fixture failures
separately from terminal passing evidence.

\subsection{One evolving funded execution}
The composed trajectory begins with a 300-unit declared envelope, a scout and
an unstarted intermediary. The scout's actual review finds an operation without
required authentication. The program then allocates an enrolled specialist,
seals its exact request, deposits its own 100-unit backing, and adds its task.
The graph grows from three nodes to four, counting the planning root. Enrollment
precedes discovery; the specialist's task, capability, agreement and funding do
not. All three executed leaves retain separate native custody and allocations.

The intermediary invokes the specialist. The existing Python W0 checker accepts
the retained child result and the escrow records \textsf{Payable}. The parent
process is then killed with SIGKILL before its return is captured. Its execution
remains \textsf{OutcomeUnknownAfterDispatch}; an observed refund resolves its
funding without rewriting that uncertainty. Parent and verifier rail signing
are disabled, and a child collector withdraws the original claim. Repeated
collection performs no second work invocation or payment.

The acceptance test checks one execution per receiver, unchanged operation,
allocation, hold, authorization and physical claim identities, and two native
continuation resources per operation. The scout's original execution evidence
is unchanged after growth and reopen. The final token balances are buyer 900,
intermediary 1,000, child 100 and escrow zero, from total supply 2,000. The scout
and child are paid 100 each; the parent's 100 is refunded. These are observed
mock-token balances, not the declared swarm pool.

Controls exercise sealed-allocation conflict, re-signed continuation refresh,
missing treaty and receiver substitution. Additional receiver tests sign the
actual adversarial request and agreement, including a valid signed swarm route
to the wrong receiver, and require rejection before funding observation or
native work. Export regressions preserve the distinction between local execution
and remote completion. The qualified campaign also runs the existing funded
child crash/rebroadcast cases. Compiler, missing-dependency and integration
failures remain in the companion record; only terminal passing campaigns are
qualified. This result establishes the composed local execution, with no claim
of independent administration or commercial usefulness.

\subsection{Transitions and negative controls}
The finite graph starts with a three-unit parent and a two-unit child. It
explores alternative submissions, conflicting and unauthorized decisions,
payment, refund, expiry and execution uncertainty over the selected timestamps.
Every reachable transition is checked against the invariants. Exploration is
exhaustive only within this bounded alphabet and starting configuration.
Funding and failed-transfer boundaries have separate unit tests.

The \TraceCount\ shortest representative financial traces cover selected
state-transition classes. The Solidity runner compares contract states,
commitments, decisions and actual token balances with the model after each
step. It does not replay all \ModelTransitions\ graph transitions against
bytecode. Additional contract tests exercise failed and asymmetric transfers,
unauthorized calls, duplicate funding, replay, verifier changes and delayed
withdrawal. No confidence interval for deployed failure rates can be derived
from this deterministic regression suite.

Two negative controls test whether the harness can detect the property it
claims to enforce. A deliberately weakened model allows a payable job to
expire; the explorer finds the sequence submission, acceptance, refund. A
corresponding in-memory mutation of the compiled escrow is rejected by the
earned-withdrawal regression. Neither negative control changes the source
contract. Separately, the older escrow characterization exhibits a timely
certificate losing payment eligibility at expiry. That historical contract has
different semantics; the paper does not describe it as an attempted equivalent
implementation of the new rule.

\subsection{An ordinary transactional alternative}
We implement the monetary state machine using ordinary SQL transactions and
conditional updates, without Chio kernel code. It receives the same role
identities, deadlines and predicate outcomes as the model. It checks every
observable snapshot and source balance along the same representative traces.
The result is \MatchedSteps\ matched steps and no mismatch. Additional tests
preserve an uncollected child's payment after parent refund, deny reuse of its
funds, and keep unknown execution distinct from verifier rejection.

This is evidence that the tested monetary safety is available through standard
mechanisms. The comparator trusts the database operator; replacing it with the
same external escrow gives an ordinary application access to the same scarce
backing. We have not benchmarked that application's full integration effort or
implemented every native admission feature in it. Accordingly, the comparison
supports neither a Chio speedup nor an impossibility claim against alternatives.
Both implementations were written within this project, so it is also not an
independently authored replication.

A later conditional-backing experiment gives a stronger conventional allocator
the same knowledge of earned, unknown, fenced-absent and exclusively selectable
future claims. The proposed structural bound and an independent exhaustive
oracle match in all 4,095 finite profiles. Selection before dispatch saves
capacity relative to reserving every alternative, but the conventional
construction obtains exactly the same saving. The companion retains this
rejected exclusive-capital hypothesis. D1 consequently claims a reusable
implementation boundary, not a uniquely available conservation rule.

\subsection{Comparison with upstream ERC-8183}
We also test the existing agent-commerce implementation at upstream commit
\texttt{142e669c1f}. Its \UpstreamTests\ unchanged tests pass. We add
\PairedTests\ comparison tests, using the same mock token, zero fees, a
100-unit buyer and a separately capitalized 60-unit intermediary. Each escrow
uses its native authorization and deadline rules; distinct trusted evaluator
addresses make decisions. The artifact retains compiled-bytecode traces,
compiler and dependency pins, and reproduction after relocation.

Both implementations pay the child after parent refund, reject funding two
60-unit jobs from 100, and deny spending the unsettled parent reserve. The
upstream implementation also supports a stronger milestone case: it pays an
approved 60-unit claim from one 100-unit job, then refunds the remaining 40 when
the job is rejected. Chio's fixed-price allocation has no partial-settlement
entrypoint. These results reject an exclusive claim to either funded agent
jobs or surviving child payments.

The observed differences concern state-machine policy. Chio separates recorded
acceptance from withdrawal, rejects new acceptance after its resolution cutoff,
and preserves earned withdrawal through a funding pause or allowlist change.
Upstream completion pays immediately; after its expiry grace period, completion
can still win if refund has not executed. Upstream refunds are blocked while
paused. These are properties of the pinned implementations, not expressiveness
limits of ERC-8183, whose evaluators and hooks admit extensions. No gas,
performance or security superiority follows from the comparison.

\subsection{Execution, verification and security integration}
The existing funded prototype binds actual Rust-produced output to a separately
implemented Python check, signed custody, a claim and payment. Its workload
inventories supported OpenAPI authentication declarations. It checks the listed
properties, not the security of a running API. September evidence records
payment, rejection, missing custody, an earned child after parent refund,
transaction recovery and native execution witnesses. Its later process
experiments isolate role keys and pass public evidence between separate roles.

We reconciled funded source \texttt{7755d3762b} with security source
\texttt{491f585e90} in integration commit \texttt{71e5cbc3bf}. Their changes
overlap in durable admission, recovery and evidence handling; compatibility
cannot be inferred from their independent tests. \IntegrationSummary
The companion retains the exact integration record and each remaining gate.

The deterministic workload deliberately makes acceptance easy to inspect. It
does not demonstrate an asymmetry between expensive production and cheap
verification: a buyer can often compute this inventory itself. There is no
held-out repair corpus, economic-margin result, live-agent advantage or
independently operated company trial in the reported evaluation. Those omissions
bound the broader economy claim rather than the tested escrow behavior.
