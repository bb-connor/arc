\section{Evolution, execution and recovery}
\label{sec:execution}
A commitment gives a running program a stable object to preserve. The program
can discover further work, but extending its plan must not enlarge an earlier
permission, reassign a sealed invocation or reset a consumed execution right.

\subsection{Grow the plan without replacing its history}
Let $G_i$ be the current signed swarm graph. An extension supplies the expected
digest of $G_i$ and a signed candidate $G_{i+1}$. The store first runs ordinary
live-authority verification on both, then checks that the candidate retains
the earlier graph envelope, tasks, edges, routes, witnesses, allocations and
revocation epoch. New tasks must fit within the original depth, fan-out and
pool bounds.

Each task has at most one allocation and one single-use continuation. An old
continuation retains its identity and all fields except the graph digest and
signature that bind it to the successor. A new task receives a new continuation.
Signing a new graph therefore does not issue another attempt for an old task.

The installer atomically compares the expected head, archives the exact parent
bundle and installs the successor. Two contenders using the same old head
cannot both commit. A receiver resolves the graph version named in the original
request, so old work remains interpretable after growth. Native custody owns
the continuation by its stable identity across those versions. Fresh work still
passes current capability, expiry, revocation and treaty checks.

In the running example, the survey's result creates the specialist task.
The program seals the specialist's invocation, binds and funds its agreement,
then installs the checked graph extension. The survey retains its original
execution evidence. The intermediary can still execute its previously sealed
request under the earlier graph.

\subsection{Admit one invocation}
The receiver checks local authority and the complete evidence binding before
dispatch. It also verifies observed backing for the funded agreement.
One native operation acquires the treaty and swarm continuation resources and
binds the original financial allocation to its budget hold. The kernel records
admission durably before invoking the tool.

For delegated work, the guard checks the exact output after transformations
against the slot's predicate. Funded acceptance adds the agreement's verification
procedure. The native execution statement binds the retained original request
and output so that verification cannot silently consume another invocation's
result.

A federated execution statement is exported from the original frozen admission
provenance: treaty, participants, request and recorded admission time are checked
against the retained outcome. Export supplies evidence of receiver-local
execution. Final bilateral receipt delivery is a separate operation that may
still require a remote co-signer.

\subsection{Recover the fact that was established}
A timeout describes a missing response. It does not establish whether the
receiver dispatched, whether the tool had an effect, or whether a verifier
recorded acceptance. Recovery therefore consults the resource owner's durable
history.

Before sealing, revision checks permit another provider choice. After sealing,
the original allocation and request remain bound even if a crash strands their
permit. After native dispatch, recorded output can be recovered without another
tool call. Where authoritative completion evidence is absent, the native state
remains \textsf{OutcomeUnknownAfterDispatch}. Independent sibling work can
continue from its own allocations.

The same rule governs settlement transactions. The reference implementation
persists the exact signed transaction before broadcast. A restart reobserves
or rebroadcasts those bytes; it does not choose a new nonce or substitute a
different allocation. This preserves particular durable transitions. Arbitrary
external tool effects still depend on the tool's own effect and recovery model.

\subsection{Earn, then collect}
The funded lifecycle is
\[
 \textsf{Funded}\to\textsf{Submitted}\to
 \begin{cases}
  \textsf{Payable}\to\textsf{Paid},\\
  \textsf{Rejected}\to\textsf{Refunded}.
 \end{cases}
\]
Undecided work can time out and refund under its agreed deadlines. An earned
claim has no transition from \textsf{Payable} to timeout or refund.

The selected verifier's decision binds the allocation, agreement, submission,
beneficiary, asset and amount through typed signed data~\cite{eip712}. The
escrow authenticates that decision. A claim is \emph{earned} when an accepting
decision is recorded under the selected settlement observation rule.
An output or an unrecorded signature alone does not reach that state.
An identical decision replay changes nothing; a conflicting replay fails.

Once the claim is earned, its beneficiary can withdraw without a new payer
authorization. Parent completion, failure and refund concern a different
allocation. In the running example, the specialist's right to its reserved
100 survives the intermediary's loss; the intermediary bears that subcontract
cost. Its own refund does not establish that its unknown native invocation had
no effect.

The owners commit in order: seal, bind the funded agreement, deposit backing,
install graph growth, admit and dispatch, then record acceptance. There is no
distributed transaction across those steps. A failure can leave capacity or
funds committed until their existing lifecycle resolves them. Preserving that
obligation is what prevents recovery from manufacturing a second promise.
