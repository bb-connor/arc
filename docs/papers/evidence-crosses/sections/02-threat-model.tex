\section{Threat model and trusted base}

The kernel sits between an agent and the tool servers whose transport it owns:
child processes it spawned and speaks to over their standard streams, HTTP tools
it fronts, and sidecars it proxies. It does not
confine the agent: the model, the orchestrator, the prompt, and any library the
agent imports are untrusted, and an agent that opens its own socket reaches
whatever that socket reaches.

The adversary is given everything outside the receiving kernel. It controls every request
field this paper names; it controls the peer
kernel and can make it sign anything with the peer's key; it controls the
network and may drop, delay, reorder, duplicate, and replay; and it may present
any receipt, statement, lease, or governance record it has ever observed, in any
combination, to any kernel. It does not hold the receiving kernel's signing key
and cannot write to its stores. The question is what such an adversary can cause
a receiving kernel to dispatch.

The trusted base is the receiving kernel's process, its signing key, and its
stores; everything outside it is verified or assumed. The assumptions appear
once, in Table~\ref{tab:assumptions}.

\normalsize

One assumption is deliberately absent: we do not assume the two signing keys on
a co-signed statement are held by two different organizations, because one
operator holding both satisfies every check in this paper. Key independence is a
deployment property and the protocol carries no evidence of it.
