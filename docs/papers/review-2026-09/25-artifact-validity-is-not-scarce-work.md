# Artifact validity is not scarce work

2026-09-13. The [portable artifact checker](24-portable-artifact-checking.md)
removed publisher truth from one finite acceptance predicate. The next
candidate considered here was to use verified agent work as the resource
supporting a shared history without a trusted receiver. That would require
more than knowing that an artifact passes its tests.

The experiment rejects a specific shortcut: counting authenticated claims,
distinct source hashes or distinct syntax trees does not establish fresh
repair-solving work. A public repair can be copied, varied and rebound to new
challenges. The stronger existing rule, one effect per receiver-owned logical
job, correctly stops all repeated effects in both backends.

This is research on one possible direction toward the broader objective. A new
consensus mechanism is not being made a requirement for an agentic breakthrough,
and no production Chio consensus rule is claimed to use these counting metrics.

## The candidate and the missing condition

The tempting construction is: locally verify useful work, attach signed
producer and challenge information, and give each accepted result a unit of
influence over a shared history. The verification step checks artifact validity.
The influence step additionally needs a resource or membership assumption that
an adversary cannot cheaply multiply. Nothing in our finite repair checker
proves how much reasoning, search or computation produced its input.

Bitcoin's original design links history selection to proof-of-work effort,
rather than counting network identities, under its honest-computational-power
assumption. That is a different security condition from accepting a correct
source artifact. This comparison supplies no new consensus construction.
[Bitcoin, section 4](https://bitcoin.org/bitcoin.pdf).

## Executed reuse, with real behavioral checking

The new [harness](../../../examples/outcome-ledger-comparison/src/graph/repair_work.rs)
loads the two-file Git-hook repair before generating fresh challenges. It makes
six signed claims in each of four families. Each claim binds the same logical
job and checker contract, its source artifact hash, a challenge, a producer key
and a claim identifier. All 24 producer keys are generated by one harness;
they are not independently administered workers.

| Family | Accepted signed claims | Distinct artifact hashes | Distinct syntax hashes | Distinct challenges |
| --- | --- | --- | --- | --- |
| Fresh identities, unchanged repair | 6 | 1 | 1 | 1 |
| Distinct appended comments | 6 | 6 | 1 | 1 |
| Distinct appended unreachable branches | 6 | 6 | 6 | 1 |
| Fresh challenge values appended as comments | 6 | 6 | 1 | 6 |

Every construction copies the cached repair and appends inert text. The
generator asserts that removing the appended suffix reproduces the cached
source exactly. It does not invoke a model or another repair search. This is
not zero-cost work: copying, hashing, signing and checking still cost resources.
The result is that these counts do not demonstrate additional repair synthesis
or its claimed cost.

Nineteen distinct valid source artifacts receive native behavioral checks.
Each passes all seven real Git commit cases, with no hook markers. The original
buggy source receives the same seven checks and fails, producing 21 hook
markers. The complete run therefore executes 140 Git commit cases across
twenty checker invocations. Exact duplicate artifact bytes reuse the already
checked result within this harness.

The [syntax helper](../../../examples/outcome-ledger-comparison/src/graph/repair_ast.py)
parses source using Python's AST representation with source locations excluded.
It runs as a trusted script in a separate namespace and never imports the
candidate modules. Comments disappear from this representation; unreachable
branches remain. There are seven distinct syntax fingerprints overall despite
every valid candidate retaining the same repair as its source prefix.

Fresh challenges are generated after the cached solution is loaded. The claim
verifier checks the selected challenge exactly. Substituting another challenge,
substituting the buggy artifact, or changing a signed claim identifier without
resigning fails for every claim, giving 72 negative binding checks. Merely
including a fresh challenge in a signature and a source comment does not force
a fresh solution of the repair problem.

The [retained result](evidence/25-artifact-validity-is-not-scarce-work/work-reuse-comparison.json)
summarizes the run; adjacent evidence files retain the claims, source variants
and fingerprints. Across the four families
there are 24 valid claims, 24 producer keys, 19 artifact hashes, 7 syntax hashes,
7 challenge values and one logical job. These are observations of this
construction, not a general lower-bound theorem or a consensus benchmark.

## The stronger control is already present

An informed alternative would not grant a new reward or effect merely because
a worker changed its key or source hash. To preserve that objection, the same
24 validated candidates are submitted to each existing outcome gate under one
immutable receiver-owned rule. The receiver signs fresh outcome evidence at
distinct valid times. It does not activate another job or replenish the budget.

Both Chio and the independent ledger admit the first candidate, append one
effect record, and deny the remaining 23 attempts. After reopening, both stores
still report `completed` and exactly one effect. The append is a direct gate
control, not another claim of kernel-mediated Git publication. The previous
integration tests retain that separate coverage.

This control matters: the experiment does not find a replay vulnerability in
Chio or prove that artifact reuse defeats a properly bound job. Deduplication
by stable job identity solves this example's repeated-effect problem. It does
not, by itself, supply the independent resource, challenge or membership model
needed for permissionless history selection. Assigning fresh job names is not
evidence of fresh computational difficulty either, but this run does not test
arbitrary job issuance or a proposed replacement policy for it.

## Prior art raises the standard for this direction

Ball, Rosen, Sabin and Vasudevan's revised work studies non-amortizability:
producing proofs for many challenges must not become disproportionately easier
than solving them separately. It also records that an earlier useful-work
definition admitted a naive construction. The revised paper supplies
conditional proofs for structured computational problems and explicitly does
not establish every property a cryptocurrency protocol needs. We read the
primary paper but did not implement its algebraic construction.
[Proofs of Work From Worst-Case Assumptions](https://eprint.iacr.org/2018/559.pdf).

Ofelimos couples its blockchain protocol to Doubly Parallel Local Search and
formalizes moderate hardness, including advantages from grinding and previously
published computations. Its construction uses pre-hashing, exploration,
post-hashing and succinct arguments; separate block roles help decouple useful
progress from ranking difficulty. It does not simply award consensus weight
for a previously solved task. Our recycling example does not refute that
construction or its conditional analysis, which we have not reproduced.
[Ofelimos, CRYPTO 2022](https://crypto.iacr.org/2022/papers/538804_1_En_12_Chapter_OnlinePDF.pdf).

The current abstract for Komargodski and Weinstein's matrix-multiplication
preprint specifically treats inputs chosen by the miner, prescribed hardness
and adversarial advantage. It states a security conjecture. Only its abstract
and metadata were reviewed here; the PDF fetch failed, and no theorem or
implementation from it is reproduced in this work.
[Proofs of Useful Work from Arbitrary Matrix Multiplication](https://eprint.iacr.org/2025/685).

These sources describe substantially stronger obligations than artifact
correctness. Attaching proof-system terminology or a block hash to the current
checker would not satisfy them. The implemented examples invalidate the
counting shortcut, not useful-work research as a whole.

## Judgment and the next useful boundary

No breakthrough is established. The strongest objection to calling this a new
result is that reuse of a solved task is expected, and stable job identity
already handles repeated effects. The experiment makes that objection
executable and prevents the artifact checker from being presented as a
Sybil-resistance or work-difficulty mechanism.

This finding also separates two possible directions. Verified artifacts can
support acceptance and one authorized effect under a chosen receiver or
settlement model, without pretending they create a new consensus resource.
Removing that receiver from settlement would require an explicit way to agree
on eligibility and spend state, including duplicate submissions and dishonest
participants. Alternatively, using the work itself to support consensus would
require a real hardness and adversarial-input construction, followed by a
consensus analysis. Neither follows from the current counters.

The next discriminating implementation should target one of those remaining
trust boundaries with a useful workload and an equally provisioned alternative.
It should not implement an open network whose security silently depends on
claim, artifact or syntax counts. This preserves the broader breakthrough
objective while rejecting an unsupported mechanism.

## Reproduction and qualification

```sh
CARGO_TARGET_DIR=target cargo run --locked --offline \
  --manifest-path examples/outcome-ledger-comparison/Cargo.toml -- \
  --repair-work-reuse examples/outcome-ledger-comparison/fixtures/git-hook-repair/base .
CARGO_TARGET_DIR=target cargo test --locked --offline \
  --manifest-path examples/outcome-ledger-comparison/Cargo.toml
```

An optional final argument chooses a new output directory. Existing Linux,
bubblewrap, Git and Python prerequisites remain in the
[README](../../../examples/outcome-ledger-comparison/README.md). Offline Cargo
needs cached dependencies. The new eighth integration test covers the reuse
counters and both protected-job controls; all earlier integration cases remain.
This mode changes no production runtime, Python repair source, dependency
manifest, lockfile or outcome-gate implementation. No live model is invoked,
and the source checkout is not modified by the experiment.

Final validation passed all eight integration tests in 66.62 seconds, Clippy
for all targets with warnings denied, Rust formatting, and Ruff lint and format
checks for the new Python syntax helper. The paper build passed its log,
bibliography, macro, page and word checks at 12 pages and 4,960 body words.

The [manifest](evidence/25-artifact-validity-is-not-scarce-work/manifest.json)
records final validation, source hashes and retained artifacts. The work is
local and uncommitted on `paper/roadmap-phase-0-1`, based on
`2b3b5af8cbfbc6f16ce6005de3f97cd149803b81`, without exact-commit CI, release
qualification or an achieved-breakthrough claim.
