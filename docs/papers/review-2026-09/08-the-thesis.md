# The Thesis: Candidates, Judges, and the Recommended Direction

Five independent authors were asked to propose the thesis of a foundational Chio paper from five angles (operating systems, cryptographic protocol, economics and institutions, AI safety, distributed systems), each grounded in the repository at HEAD. Two judges scored them (1 to 10 per criterion) and synthesized a recommendation. The lead reviewer's own recommendation, which draws on these and on Wave 1, is in `01-executive-summary.md` and `10-roadmap.md`.

## The five candidate theses


### Evidence Crosses, Authority Does Not: Chio as an Operating-System Kernel for Agents

#### In one sentence

Chio is a kernel for agents with one syscall: the kernel admits a tool call as a fail-closed function of signed objects it verifies against trust roots it activated itself, records the decision as a signed content-addressed receipt before the caller can see the result, and treats a call from another organization as that same syscall with the peer kernel's receipt and co-signature supplied as evidence rather than as authority, so organizations interoperate with no shared kernel and no transferred authority.

#### The problem

An agent that reaches a tool directly holds whatever authority the surrounding process holds and leaves whatever record that process chooses to keep. MCP and A2A define how to call a tool and how agents talk; neither has a kernel, a per-action decision record, or a way for a second organization to admit a foreign agent's call without trusting the sender's runtime. Operating systems solved the local half: a reference monitor every program must pass through, capability kernels (KeyKOS, EROS, seL4) that remove ambient authority, Capsicum that retrofits capability mode onto UNIX. But an OS audit log is trusted only by the machine that wrote it, and OS authority stops at the machine's edge; distributed capability systems (Amoeba, Kerberos tickets) crossed that edge by transferring authority, which is exactly what a receiving organization cannot accept from an autonomous agent. The open question is what the syscall boundary should look like when the caller is an untrusted model, the effect has a price, and the next hop is another organization's kernel.

#### The insight

Separate what may happen from what happened. Authority (a capability, a budget, a delegation link, a treaty) is minted and verified only inside the kernel that dispatches, against roots that kernel activated, and nothing carried in a request can add a root. Evidence (a receipt, a continuation, a co-signed statement) is a signed, content-addressed object whose meaning does not depend on where it is stored. Once those are kept apart, cross-organization calls need no second protocol: the receipt of one kernel's syscall is admissible input to another kernel's syscall, the receiver resolves every referenced object from its own stores, and it denies on anything it cannot resolve. This feels inevitable afterward because a signature only ever proves who signed some bytes; it can never decide whether the receiver should act on them, so the decision has to live in the receiving kernel, and the only safe thing to send across is evidence.

#### The construction

Objects. A CapabilityToken is Ed25519-signed by a trusted issuer, subject-bound, time-bounded, scoped to tool grants with per-grant budgets, and carries a delegation chain in which every hop is a signed link with an attenuation proof (parent scope hash must equal the last chain link, budget split in basis points, caveats). A ChioReceipt body has id = SHA-256(JCS(body without id)); the kernel signs JCS({id, body}) only after recomputing content_hash from the content preimage it holds (WYSIWYS), and every allow, deny, cancelled, and incomplete decision is such a receipt. Receipts form a DAG (parentReceiptIds, parentSetHash, dagOrdinal, HLC) committed into RFC 6962 checkpoints (chio.checkpoint_statement.v2). A TreatyScope names two kernels, their keys, allowed action classes, validity window, revocation epoch, and the SHA-256 of each participant's signed GovernanceLadderManifest; a LadderIntersection is computed per action class by taking the higher-intensity mode (observation < guarded < receipt_backed < partition_contingency < maintenance), the strictest co-sign requirement, and rejecting mismatched consistency models. A CrossKernelContinuation is single-use and binds parent receipt, session anchor, capability, action class, target tool, nonce, source and target kernels, and validity. The bilateral statement is a DSSE envelope of predicate type chio.bilateral-cosign-invocation.v1 whose single subject is the receipt digest, whose predicate carries a treaty_binding_ref (treaty id, treaty scope hash, ladder intersection hash, admission report hash, continuation hash, lineage bundle hash, action class, consistency model, request hash, outcome hash, local and remote receipt hashes, lease refs, governance refs, signer kernel ids), and which carries exactly two signatures over the same PAE bytes from two distinct pinned keys.

The syscall (one pipeline, in order, every failure a signed deny). 1. Verify the token signature against the kernel's own trusted issuer set, time bounds, revocation (token and every presented ancestor against the Merkle revocation oracle), and scope; resolve matching grants. 2. Begin a durable admission operation: a fenced write-ahead record (18-state machine, Prepared through ReadyToDispatch, DispatchCommitted, terminal Completed, CompensatedBeforeDispatch, OutcomeUnknownAfterDispatch, DeniedAfterDelivery) so a crash on either side of dispatch is classified, not lost. 3. Run pre-invocation guards; custom guards run as fuel-metered WASM with no host access, and a guard deny or error dominates. 4. Run the runtime admission hook: if the request carries governed context (chioAdmission, chioTreaty, chioSwarm) or arrives from a federated origin, resolve treaty scope, ladder intersection, continuation, lineage, bilateral invocation, receipts, leases, governance receipts, peer pins, and revocation epoch from receiver-owned stores; reject any request key that tries to carry a trust root, peer directory, signing key, treaty scope, ladder manifest, or dynamic trust bundle; reserve the continuation; verify the DSSE envelope; check policy verdict agreement, lease freshness, and governance receipt when the class is receipt_backed; install VerifiedFederationTreatyMaterial for this request only. 5. Take the budget hold. 6. Revalidate mutable admission state immediately before dispatch and mark dispatch started (consuming the continuation). 7. Dispatch to the tool server over a transport the kernel owns. 8. Run output guards. 9. Build the receipt, recheck its fields against the admitted decision inputs and the verified treaty material, sign it in the pure core, persist it locally, then request the peer's co-signature, then return the response. A kernel that cannot persist a receipt denies.

Cross-kernel call. Org A's kernel admits its agent's call as above and emits its receipt; Org B's kernel receives the request classified as federated, runs the identical pipeline with B's own trusted issuers (the foreign agent holds a B-issued capability, minted after B evaluated its passport), and step 4 is where A's receipt, continuation, and co-signature enter as evidence. Nothing A sends can change what B trusts; if any referenced object is missing, stale, replayed, or inconsistent, B returns a signed denial with a stable code and the tool is never invoked. Verification of any receipt, checkpoint, or bilateral statement needs only public keys and canonical JSON, so it runs offline in any language.

#### Why it would be cited in ten years

It will be the paper that named the syscall boundary for agents and stated the rule that survived: authority is local to the dispatching kernel and only signed evidence crosses organizations. Later agent runtimes, whether or not they use Chio, will cite it for three things: the receipt as a content-addressed, offline-verifiable object that is simultaneously audit record, billing event, and admissible input to another kernel; the receiver-owned admission rule for cross-organization calls (resolve everything locally, require a co-signature over identical bytes, deny on anything missing); and the durable two-phase admission operation that makes the receipt log a write-ahead record rather than a best-effort trace. That is the same role Capsicum plays for capability mode on UNIX and the UNIX paper plays for the small set of uniform primitives that everything else composes from.

#### Biggest risk

A hostile OS reviewer says: this is a userspace proxy with a signed log, not a kernel. The agent is not confined by Chio (only tool servers behind kernel-owned transports are), process isolation is delegated to the OS (ASSUME-SUBPROCESS-ISOLATION), the proofs cover roughly twenty pure helpers plus hand-mirrored bounded models rather than the running pipeline, and the only cross-organization experiment ever run is a single-host loopback with both keys generated by one process (PS-A-01). If the paper lets "kernel", "complete mediation", or "verified" slide even slightly past what CLAIM_REGISTRY.md permits, that reviewer is right and the paper is rejected. The mitigation is to make the boundary the contribution: define the syscall boundary as the set of tool servers whose transport the kernel owns, present the formal estate as mirror-hashed tripwires with an explicit assumption list, and deliver the two-kernel networked experiment so the "no shared kernel" claim is demonstrated rather than argued.

#### Comparable foundational paper

Capsicum (Watson, Anderson, Laurie, Kennaway, USENIX Security 2010): one primitive that retrofits capability discipline onto an existing world without replacing it, evaluated by porting real programs and measuring the boundary cost. The UNIX paper supplies the register (a few uniform primitives: token, syscall, receipt) and seL4 supplies the discipline of stating exactly where the proof boundary ends.

#### Draft opening paragraph

An agent that reaches a tool directly holds whatever authority the process around it holds, and leaves whatever record that process chooses to keep. A second organization asked to act on that agent's behalf has nothing to check but the sender's word. Operating systems solved the first half decades ago with a kernel that every program must pass through, but a kernel's audit log is trusted only by the machine that wrote it, and its permissions stop at the machine's edge. We propose a kernel for agents that closes both gaps with one rule: authority stays inside the kernel that dispatches, and only evidence leaves it. Every tool call is a syscall the kernel admits as a fail-closed function of signed objects it verifies against roots it activated itself, records durably before the tool runs, and records again as a signed, content-addressed receipt before the caller sees the result. A call from another organization is the same syscall. The receiving kernel resolves the treaty, keys, continuation, and prior receipts from its own stores, requires the sending kernel's co-signature over the identical canonical statement, and denies on anything missing, stale, replayed, or inconsistent. No organization has to trust another's runtime, only verify its signatures, and no shared kernel is required.

### Co-Signed Receipt Chains

#### In one sentence

A tool call between two organizations runs only when both kernels have signed one statement over the hash of a receipt the receiving kernel already holds, naming the treaty, the request hash, and a single-use continuation drawn from the prior receipt, and the receiver checks all of it against nothing but its own keys and its own log; so authority crosses an organization boundary as a chain of co-signed, content-addressed receipts, and nothing that arrives in a request can add trust.

#### The problem

When an agent in organization A calls a tool in organization B, B must decide before the tool runs whether this exact call is one both sides agreed to, and afterward both sides (and a buyer or auditor who trusts neither) need a record they can check without asking the other party. Every existing signed-statement system answers a different question. DSSE and in-toto prove that some key signed some typed bytes; SLSA proves how an artifact was built; Certificate Transparency and Rekor prove that a statement was logged; Macaroons prove that a chain of caveats was discharged; capability systems prove a local principal held authority. None of them makes a foreign action admissible at a receiver, because a signature authenticates bytes and says nothing about whether those bytes name the treaty the receiver expected, the request the receiver is about to execute, or the history the receiver already holds. The concrete attacks are substitution (a valid vendor receipt re-presented under a different treaty, request, or outcome), replay (a continuation used twice), trust injection (request metadata that installs a key, peer directory, or trust bundle), and mix-and-match (two signatures over different statements presented as one agreement). The problem is to define the smallest signed object that a receiving kernel can accept as sufficient for one dispatch, state exactly what accepting it proves, and show that the proof reduces to standard signature and hash assumptions plus the receiver's own store.

#### The insight

A signature transfers no authority across an organization boundary; only a reference to something the receiver already holds does. So make the signed object a pointer, not a bearer credential. Its subject is the content hash of a receipt already in the receiver's log; the two keys that must sign it are named inside it and must be keys the receiver pinned for the named treaty before the request arrived; its freshness is a continuation the receiver itself stored and will spend exactly once; its request binding is the hash of the arguments the receiver is about to execute. Under that framing the envelope carries zero trust of its own. Every bit of trust it invokes was placed in the receiver's store out of band, and the cryptography's only job is to bind those pre-placed facts to each other and to the request bytes, so that any deviation (a different treaty, a different request, a different receipt, a reused continuation, a missing signer) is a hash mismatch, a signature failure, or a store miss, never a judgment call. Once you see it this way, a co-signed receipt is not a stronger signature; it is the unit in which two organizations' logs are joined, and the chain of such units, each one's continuation spent by the next, is the cross-organization history. The receipt was already Chio's unit of local truth (content-addressed, WYSIWYS-signed, Merkle-checkpointed); the bilateral construction makes it the unit of cross-organization truth without inventing a second primitive.

#### The construction

Objects. (1) Receipt r: body fields {id, timestamp, capability_id, tool_server, tool_name, action{parameters, parameter_hash}, decision, receipt_kind, boundary_class, actor_chain, content_hash, policy_hash, evidence, metadata, trust_level, kernel_key, ...}; id = SHA-256(JCS(all body fields except id)) with a signing nonce bound into metadata first; signature = Ed25519 over JCS({id, body}) by the kernel key k; the signer recomputes content_hash from the content preimage and refuses on mismatch, and refuses if body.kernel_key != k. (2) Treaty T: TreatyScope{treaty_id, participant_kernel_ids [A,B], participant_public_keys, ladder_manifest_sha256s, allowed_action_classes, issued/expires, revocation_epoch_sha256, trust_bundle_sha256} plus LadderIntersection{per action class: mode, destructive, consistency_model, co_sign, evidence_required}, computed higher-intensity-wins from the two kernels' ladder manifests and co-signed by both; both records are installed in each kernel's store out of band and addressed by (id, sha256). (3) Continuation c: {continuation_id, source_kernel_id A, target_kernel_id B, parent_receipt_sha256, parent_session_anchor_sha256, capability_id, action_class_id, audience_tool, nonce, issued/expires}, stored at B. (4) Admission statement S: in-toto Statement v1, predicateType chio.bilateral-cosign-invocation.v1, subject = [{name: "chio-receipt:" + r.id, digest.sha256 = SHA-256(JCS(r.body))}], predicate = {invocation_id = r.id, tool_server_a{kernel_id, passport_key_fingerprint = SHA-256(pk_A), alg}, tool_server_b{...pk_B...}, tool_name, tool_args_hash = r.action.parameter_hash, capability_lease_ref{lease_id, issuer, expires_at, scope_digest?}, policy_evaluation_summary{server_a_verdict, server_b_verdict, joint_disposition?}, governance_receipt_ref? (required for receipt_backed classes), co_sign, consistency_model, consistency_anchor?, cross_org_visibility, timestamp_unix_ms, treaty_binding_ref{treaty_id, treaty_scope_sha256, ladder_intersection_sha256, admission_report_sha256, continuation_sha256, lineage_bundle_sha256, action_class_id, consistency_model, request_sha256, outcome_sha256, local_receipt_sha256, remote_receipt_sha256, lease_refs, governance_refs, signer_kernel_ids}}. (5) Envelope E: DSSE {payloadType "application/vnd.in-toto+json", payload = base64(JCS(S)), signatures = [{keyid fp_A, sig Ed25519_A(PAE)}, {keyid fp_B, sig Ed25519_B(PAE)}]}, PAE = "DSSEv1" SP len(type) SP type SP len(payload) SP payload; both kernels sign identical PAE bytes.

Receiver algorithm at kernel B for a request q with federated origin A. (a) Run the ordinary local checks: capability signature, expiry, scope subset, revocation oracle, budget hold, input guards. (b) Parse only identifiers and hashes from the request's chioTreaty context; if the context contains any of trustRoot, trustRoots, trustBundle, treatyScope, ladderManifest, signingKey, peerDirectory deny request_smuggled_trust_root; if it contains dynamicTrust, dynamicTrustBundle, runtimeTrustInput, peerDiscovery deny request_smuggled_dynamic_trust. (c) Resolve TreatyScope, LadderIntersection, continuation, lineage bundle, bilateral invocation record, and DSSE envelope from B's own store by (id, sha256); any hash mismatch or missing required artifact denies. (d) Validate: treaty within validity, participants exactly {A, B = self}, action class allowed and present in the intersection, intersection hash equals the stored one, continuation inside its window with capability_id = q.capability, action class match, target = self, source = A, audience tool = q.tool; lineage statement binds continuation_sha256 and the parent receipt digest. (e) Verify E: payloadType, exactly two signatures, decoded payload bytes byte-equal to JCS(S), _type, predicateType, predicate schema, exactly one subject named chio-receipt:<invocation_id>, pk_A != pk_B and distinct keyids, predicate fingerprints equal SHA-256 of the pinned keys, Ed25519 verify both signatures over PAE. (f) Cross-bind: tool_args_hash == SHA-256(JCS(q.arguments)) and == treaty_binding_ref.request_sha256; both policy verdicts allow; lease resolves in B's registry with matching issuer and expiry > now; treaty_binding_ref.{treaty_id, treaty_scope_sha256, ladder_intersection_sha256, action_class_id, consistency_model} equal B's own accepted admission report; B overwrites admission_report_sha256 with its local value so peer-supplied report hashes never enter B's receipt. In the offline verifier the same step additionally resolves the subject receipt from the store, re-verifies its signature under the pinned B key, recomputes SHA-256(JCS(body)) against the subject digest, and requires outcome_sha256 == receipt.content_hash and remote_receipt_sha256 == the receipt's hash. (g) Spend c: INSERT OR IGNORE (continuation_id, admission_id) into the consumed table; zero rows inserted denies chio_treaty_continuation_replay; the row is released if a later pre-dispatch step denies or the kernel aborts. (h) Dispatch. (i) Sign the new receipt r' with the verified treaty material attached as metadata (lease, verdicts, governance ref, treaty_binding_ref) after rechecking request id, participants, tool, and action hash against the material; then obtain A's co-signature over JCS(r') and emit a DSSE envelope whose subject is r'.id with both signatures; persist the dual-signed receipt and the envelope durably before caching. A missing cosigner or mismatched participants is an error, never a single-signed allow. (j) Any third party verifies a package of receipts, envelopes, leases, governance receipts, and the ladder intersection against a verifier-owned trust bundle; the package cannot supply pins, action classes, or revocation state.

Security statement to prove (Admission Binding). Fix receiver B with store S. If B dispatches federated request q at time t under treaty T, then there exist a receipt r in S whose kernel signature verifies under the key S pins for B, an envelope E whose subject digest equals SHA-256(JCS(r.body)) and whose two signatures verify under exactly the keys S pins for T's participants A and B, with E.predicate.tool_args_hash = SHA-256(JCS(q.arguments)), and a continuation c in S bound to T, A, B, q.capability, the action class, and a parent receipt digest, such that c is spent by at most one dispatch. Reduction sketch: a dispatch without A's participation yields an Ed25519 forgery under pk_A (EUF-CMA, ASSUME-ED25519); substituting any bound object without re-signing yields a SHA-256 collision or a JCS non-injectivity witness (ASSUME-SHA256, ASSUME-CANONICAL-JSON, Lean digest_injective under hash_collision_resistant); two dispatches on one c contradict the primary-key uniqueness of the consumed table (ASSUME-SQLITE-ATOMICITY); installing a key or treaty through the request is syntactically rejected before any lookup. Corollary (receiver locality): the accept set is a function of (S, E, q, t) only. Corollary (audience binding): E accepted by B is rejected by any B' whose pinned key differs, because E names B's fingerprint and B' checks its own. What the construction does not prove: that pk_A and pk_B are held by different operators (PS-A-01), that either policy was honestly evaluated, or that the tool did what its receipt says.

#### What must be built or proven

1. The security definition and its reductions, on paper first. Neither existing paper states a game. Define Admission Binding, Receiver Locality, Single-Use, and Audience Binding as in the construction, and prove each by reduction to EUF-CMA (Ed25519), collision resistance (SHA-256), JCS injectivity, and consumed-table uniqueness under single-row atomic commit. #### Why it would be cited in ten years

Because it will be the paper that named the unit. Certificate Transparency is cited for the SCT and the append-only log contract, in-toto for the link and attestation, Macaroons for the caveat and discharge; when agents transact across companies, the question "what did both sides agree happened, and can a third party check it offline" will be answered by pointing at the co-signed receipt: a content-addressed, kernel-signed record whose admission statement names its two signers, its treaty, its request hash, and the continuation it spends, and whose verification depends on nothing but the receiver's own store. The construction is small enough to reimplement from the paper, the security property is precise enough to be a theorem, and the assumption boundary (two keys, not two operators; a receiver that owns its store; standard signatures and hashes) is explicit enough that later work can strengthen exactly one edge (TEE-attested keys, public witnessing, threshold signing) and cite this as the base. A secondary reason: the paper would set the discipline of separating a bounded mechanized model from runtime qualification and audited assumptions, with a claim registry that constrains wording; systems that follow will copy that discipline, and the copies will cite the original.

#### Biggest risk

A hostile applied-crypto reviewer says the primitive is thin: two Ed25519 signatures over identical DSSE bytes plus hash pointers plus local lookups, each of which exists elsewhere, and the "chain" is just a nonce table. The paper survives only if the security statement is stated as a theorem with a clean reduction and the binding structure is shown to be the minimal one that defeats the named attacks (drop any field and exhibit the attack), because the value of the construction is entirely in the exactness of the verifier contract, not in a new cryptographic object. Two related exposures: the cryptography can never deliver "two organizations", only "two authorized keys" (PS-A-01), and any sentence that implies otherwise will be rejected; and the reproducibility story is currently broken at HEAD with inconsistent numbers, environment, and pinned commits, which a USENIX artifact evaluator will find in the first hour.

#### Comparable foundational paper

Certificate Transparency (Laurie, Langley, Kasper, RFC 6962, 2013): a deliberately small primitive (a signed statement plus a Merkle log and inclusion proofs) whose entire contribution is a precise verifier contract that turns misbehavior into checkable evidence rather than preventing it by fiat. The co-signed receipt plays the role the SCT plays there. The nearest second analogy is Macaroons (Birgisson et al., 2014), where a third-party caveat must be discharged by another authority before a bearer token is valid; here the treaty is the caveat and the peer kernel's co-signature over the receiver-held receipt is the discharge, except that the object is never bearer because its subject is the receiver's own log.

#### Draft opening paragraph

An agent in one organization that calls a tool in another needs the receiving organization to decide, before the tool runs, whether the call is one both sides agreed to, and needs a record afterward that either side or a third party can check without asking the other. Digital signatures provide part of the solution, but a signature only proves that a key signed some bytes; it does not prove that the bytes name the treaty the receiver expected, the request the receiver is about to execute, or the receipt the receiver already holds. We propose a construction in which the unit of cross-organization trust is a co-signed receipt. Each kernel signs a receipt whose identifier is the hash of its own content. A cross-organization call is admitted against a statement whose subject is the hash of such a receipt, which names the two keys that must sign it, the treaty under which the action is allowed, the hash of the request, and a single-use continuation drawn from the previous receipt. The receiving kernel resolves the treaty, the keys, the receipt, and the continuation from its own store; the request may carry identifiers but never trust. If both signatures verify and every reference resolves to what the receiver already holds, the call runs, the continuation is spent, and the new receipt is co-signed by both kernels and becomes the next link. If not, the call does not run. The result is a chain of receipts that cannot be forged without a signing key, altered without a hash collision, or replayed without spending a continuation twice, and that anyone holding the public keys can verify offline.

### The Receipt Is the Transaction

#### In one sentence

Chio makes an agent's authorization, the audit record of what it did, and the accounting entry for what it cost one kernel-signed object that anyone can verify offline, so agents and organizations transact on verified receipts instead of on trusted intermediaries.

#### The problem

Commerce between software agents has to answer three questions after every action: was the agent allowed to do it, what actually happened, and what does it owe. Today those answers live in four systems owned by different parties (an identity or IAM service, an application log, a metering or billing service, and a payment rail), none of which can verify the others, and each of which is written by a party with an interest in the answer. Reconciling them is the transaction cost of agent commerce. Inside one organization that cost is paid in audit work; across organizations it is paid by trusting the counterparty or a shared platform that sits between them and keeps the only ledger. Spending controls are advisory rate limits that reset on restart; delegation to sub-agents silently amplifies authority (two children at 4000 bps each under a 5000 bps parent); the audit trail is self-reported by the party being audited; and a vendor's signature on a record says only that the vendor signed it, not that the buyer's rules admitted it. No deployed system produces, at the moment of the action, a record that settles all three questions at once and that a third organization can check without trusting anyone who was party to the trade.

#### The insight

Produce the record at the only place it can be produced honestly: the mediator that alone can run the action, at the instant it decides. If that mediator (a) takes the budget hold before the call, (b) signs the decision, the reconciled charge, the payer lineage, and the guard evidence as one content-addressed object whose hash it recomputes itself, and (c) signs denials in the same form, then the authorization record is the accounting record is the audit record, and it was written by neither payer nor payee. Once such receipts exist, every economic relation between agents (billing, credit, insurance, markets) can be a pure function over receipts instead of a contract about trust, and commerce between two organizations needs only mutually verifiable receipts: no shared ledger, no shared key store, no shared intermediary. Authority then behaves like a conserved quantity, which is what makes a budget a property right rather than a rate limit: it can be split (basis-point shares that sum to at most the parent), narrowed (scope subset, shorter expiry, smaller cap), and revoked (a cut through the delegation tree), but never created, and the receipt is the ledger entry that records its consumption. Bitcoin made the transaction record self-verifying so money no longer needed a trusted issuer's ledger; Chio makes the authorization record self-verifying so obligations between agents no longer need a trusted reconciler. Treaties are the same move at the institutional level: rules agreed in advance, evaluated by each receiving organization against its own stores, intersecting to the stricter party's mode, and amendable only by narrowing, so sovereignty over what crosses your boundary is retained without a central authority.

#### The construction

1. Authority as a conserved right. A capability token (chio.capability.v1) carries id, issuer, subject key, scope (grants of server, tool, operations, constraints, max_invocations, max_cost_per_invocation, max_total_cost), issued_at, expires_at, a delegation_chain whose every link signs the scope_hash authorized at that hop, an attenuation_proof {parent_scope_hash, child_scope_hash, normalized subset witness}, budget_share_bps at most 10000, and caveats. Verification order: issuer trusted, signature, time window, chain binding (parent_scope_hash equals the last link's scope_hash, or the verifier's trust-root scope hash for direct issue), subset witness over normalized scopes, sibling-sum admission against a per-parent registry (admitted sibling shares plus the proposed share must not exceed the parent's share; unknown parent denies; same child id with a different share denies; sums in u32), revocation of the token and every ancestor against an epoch-rooted Merkle oracle, DPoP when the grant requires it, then guards. Every delegation mints a signed DelegationReceipt alongside the link.
2. Hold before execute. For a cost-bearing grant the kernel calls BudgetStore::try_charge_cost, which atomically checks invocation count, per-call cap, and exposed + realized + cost against max_total_cost, records exposure under a hold_id and event_id, and returns true or false; a pre-dispatch denial reverses the exposure; after execution the hold is reconciled to realized spend or released. The pure ledger is a four-cell state {outstanding, committed, released, retained} with ops reserve, commit, release, retain; an op on a terminal ledger or an overflow is a no-op that returns false; the total is invariant except for reserves.
3. The receipt. Body: id, timestamp, capability_id, tool_server, tool_name, action (canonical params plus parameter_hash), receipt_kind, boundary_class, decision, content_hash, policy_hash, per-guard evidence, metadata, trust_level, kernel_key. id = SHA-256(JCS(body without id)); the signing input is {id, body}; the signer recomputes content_hash from the output preimage and refuses on mismatch. Only receipt_kind = mediated_decision with boundary_class = prevent and decision = Allow is authorization; Deny, Cancelled, and Incomplete are signed receipts of the same shape. metadata.financial = {grant_index, cost_charged, currency, budget_remaining, budget_total, delegation_depth, root_budget_holder, payment_reference?, settlement_status, attempted_cost?}; metadata.budget_authority = {hold_id, authorize{exposure_units}, terminal{disposition, realized_spend_units}, execution_nonce_id, guarantee_level, profile = chio.mediated_spend.v1}. A receipt is an authoritative spend iff: signature valid, kernel key admitted, mediated + prevent + Allow, hold reconciled, and a kernel-signed execution nonce is bound to (subject, request_id, capability_id, tool_server, tool_name, parameter_hash) and to that hold. Receipts fold into RFC 6962 Merkle checkpoints, which anchor to EVM, Bitcoin via OpenTimestamps, Solana, and Rekor.
4. Paying on receipts. An Allow receipt with positive cost is handed to a credit hook that mints a signed IOU {receipt_id, receipt_timestamp, tool_server, tool_name, capability_id, amount_units, currency, issuer_key}; a settlement hook receives {receipt_id, finalized_at, amount, content_hash, policy_hash}, processes in (finalized_at, receipt_id) order, and routes to a rail; rail payloads (x402 requirements, EIP-3009 authorizations, escrow and bond calls, PSP records) are digest-bound subordinate evidence and never authority; obligations derived from receipts are netted in signed clearing rounds (balance_match.v1). Reputation, underwriting, and insurance placement are pure functions over receipt corpora.
5. Treaties. A TreatyScope fixes treaty_id, participant kernel ids and keys, hashes of each participant's signed ladder manifest, allowed action classes, validity window, revocation epoch, and trust-bundle digest. A ladder manifest maps each action class to a mode in the order observation < guarded < receipt_backed < partition_contingency < maintenance, a destructive flag, a co-sign requirement, a consistency model, and required evidence. The intersection takes the stricter mode per class, denies unknown classes, and denies destructive classes below receipt_backed. For a cross-organization call the receiving kernel resolves treaty, intersection, continuation, lineage, peer pins, revocation state, and prior receipts from its own stores (the request may carry identifiers only), then verifies one DSSE envelope: payload type, exactly two signatures, canonical bytes, predicate type chio.bilateral-cosign-invocation.v1, subject digest = SHA-256(JCS(receipt body)), two distinct pinned keys, both Ed25519 over the PAE, agreeing policy verdicts, a fresh lease, a governance receipt when the class is receipt_backed, and a treaty binding {treaty_scope_sha256, ladder_intersection_sha256, continuation_sha256, request_sha256, outcome_sha256, local_receipt_sha256, remote_receipt_sha256, signer_kernel_ids}. The continuation is consumed once; any failure denies before dispatch; accepted material is carried as a validated type into the local receipt. A treaty's predicate set may be amended only if the candidate admits no receipt on the declared domain that the current set rejects (backward refinement).

#### Why it would be cited in ten years

Because it names and proves the primitive that agent commerce will standardize on: a mediated receipt that is at once permission, proof, and price, produced by neither party to the trade and verifiable by anyone. Just as "UTXO" and "capability" became vocabulary, "receipt" in this sense (authorization equals account, authority conserved along delegation, cross-organization rules evaluated by the receiver) becomes what later systems say they implement or improve on. The conservation-of-authority proofs (subset witness, sibling-sum, reservation ledger, backward-refining amendments) become the reference for how delegated budgets must behave, and receiver-owned treaties become the reference alternative to platform intermediaries for actions between organizations. Papers on agent billing, agent credit, agent insurance, and inter-organizational agent protocols will cite it the way payment-channel and rollup papers cite Bitcoin: as the paper that showed the record itself can carry the institution.

#### Biggest risk

A hostile economist will say: a kernel-signed receipt is an obligation record, not settlement finality (the spec itself keeps reconciliation state in a mutable sidecar and marks settlement_status pending); the conservation that would make a budget a property right is proved only per ledger cell and per sibling split, not across the store or across netting rounds (P11 is open); and no independent operator yet treats a receipt as authoritative for billing (ADOPT4-02 unproved), so "institution" is architecture, not evidence. A systems reviewer adds: attenuation-only delegation is UCAN, Biscuit, Macaroons. The thesis survives only if it is stated exactly as the code delivers it: authorization, audit, and accounting entry in one object, settled by rails that cite it rather than replace it; conservation proved for the pure ledger, the sibling split, and the treaty intersection, assumed across the durable store; and the novelty located in the fusion (hold before execute, mediator-signed cost and payer, denials as receipts, receipts as the object treaties bind), not in attenuation. Overstate any of the three and the paper is rejected.

#### Comparable foundational paper

Bitcoin: A Peer-to-Peer Electronic Cash System (Nakamoto, 2008). It is a systems paper whose entire claim is that a self-verifying record can replace an institution, the trusted financial intermediary; Chio's analogue is that a self-verifying authorization-and-account record replaces the trusted reconciler between organizations. The economic lineage is Coase, The Nature of the Firm (1937), and Williamson on transaction costs: the receipt is a device for lowering the cost of verifying authority and obligation between parties. The design lineage is Dennis and Van Horn (1966) for capabilities and Ostrom, Governing the Commons (1990), for the polycentric treaty layer, used as rationale rather than as results.

#### Draft opening paragraph

Commerce between software agents relies almost entirely on trusted intermediaries to answer three questions after the fact: was the agent authorized, what did it do, and what does it owe. Authorization lives in an identity service, the audit trail in a log, the charge in a metering system, and the payment on a rail, and none of these records can verify the others. Each is written by a party with an interest in the answer. The cost of reconciling them is the transaction cost of agent commerce, and when the parties are different organizations the reconciliation is done by trusting the counterparty or a shared third party that keeps the only ledger. What is needed is a record produced at the moment of the action, by the one component that alone could run it, that any party can verify offline and that answers all three questions at once. We propose a kernel that mediates every tool call an agent makes and signs a receipt that is simultaneously the authorization decision, the audit entry, and the accounting entry. Authority enters the kernel as a capability whose scope, budget, and lifetime can be split and narrowed but never enlarged; a budget hold is taken before the call runs and reconciled into the receipt; a denial is a receipt too. Organizations bind their receipts to each other through treaties evaluated by the receiving kernel alone, so two organizations can transact on verified receipts without sharing a ledger, a key store, or a trusted third party.

- 1. Introduction: The reconciliation problem. Authorization, audit, and billing for agent actions live in four systems owned by interested parties; reconciling them is the transaction cost of agent commerce, and across organizations it is paid in trust.

- 3. The receipt. One kernel-signed, content-addressed object is the decision, the evidence, and the account: hold before execute, WYSIWYS signing, execution-nonce binding, denials as receipts, the authoritative-spend predicate, checkpoints and anchors.
- 4. Paying on receipts. IOU minting, the settlement hook, rails as digest-bound subordinate evidence, signed clearing rounds, reputation and underwriting as functions over receipts, and the cognition market as a worked economy where reveal is a governed tool call.
- 5. Treaties: rules, not orders. Receiver-owned admission from local stores, ladder intersection to the stricter mode with a destructive floor, two signatures over one canonical statement binding both receipts, continuations consumed once, amendments admissible only by backward refinement.
- 6. What is proved and what is assumed. Lean (monotonicity, sibling-sum, reservation ledger, revocation cut, treaty intersection, amendment refinement, finite-domain refinement), Aeneas equivalence for ledger_apply and budget helpers, Kani, Apalache ReceiptBeforeAllow and ReservationConservation, hashed mirrors, and the published assumption boundary (one crypto axiom, single-row SQLite atomicity, key custody).

### The End-to-End Argument for Agent Safety: Receiver-Owned Admission

#### In one sentence

Whether an agent's action is safe can only be decided by the party whose state it changes, so Chio moves the safety decision out of the model and into a kernel owned by that party, which checks the action against its own policy, budget, revocation state and (across an organization boundary) its own copy of the treaty and prior receipts, refuses by default, and writes a signed verdict before any effect, so that a misaligned model, a fooled monitor, or a foreign organization's agent can at most be denied and can never act unrecorded.

#### The problem

Safety for tool-using agents is currently sought in three places, none of which can be complete. In the model: alignment training, RLHF, and Constitutional AI shape what the model wants to emit, but a model cannot know the policy, budget, or history of the file system, payment rail, or vendor it is about to act on, and an alignment-faking model emits well-formed, plausibly benign calls by design. In the middle: transcript monitors and guardrails read the request without the receiver's state and so cannot distinguish a permitted refund from a forbidden one under a different treaty. At the sender: a signature or a SAGA-style token proves who issued the request, not that the receiver allows it (Paper P1, sections/01-introduction.tex: "A signature identifies a key; it does not decide whether the receiver should admit the action"). Today the request then reaches a passive dispatcher (MCP) that executes it, and the record of what happened is a log line the receiver cannot verify. The hard case is the one that combines all three: a foreign organization's agent presents a correctly signed request that names a stale treaty, a replayed continuation, or a substituted argument set; upstream checks all pass, and the receiver's ledger changes before any audit runs. The problem is placement: the safety check sits where the information to make it does not exist.

#### The insight

Saltzer, Reed and Clark's end-to-end argument says a function placed below the endpoint that needs it can only be a performance enhancement, never a correctness guarantee, because only the endpoint has the knowledge to check it. Read the action of an agent as a message whose endpoint is the party that bears the effect. Then alignment (in the sender), monitoring (in the middle), and sender signatures are all "functions placed in the communication subsystem": they lower how often something harmful is attempted, and that is valuable, but they cannot decide admissibility, because admissibility is a fact about the receiver's policy, trust roots, budget, revocation epoch, treaty, and history. Once this is accepted, four design consequences are forced rather than chosen. (1) The request may carry evidence but never trust: peer keys, treaty state, revocation, and continuations are resolved from receiver-owned stores, and a request that tries to install any of them is denied. (2) Observation must be typed apart from authorization at the level of the data structure, so that a monitor's output can never be mistaken for a verdict. (3) Authority can only narrow along a delegation chain, so no swarm of agents can manufacture what the receiver did not grant. (4) The verdict must itself be a signed artifact that exists before the effect, so that the receiver can prove, offline and to a third party, what it allowed. The receiver's kernel is a reference monitor in the Saltzer-Schroeder sense, but with two additions that capability systems never made: the allow is preceded by a persisted receipt, and the receipt's evidence class is part of its signed body. Model alignment is then the thing that decides how often the kernel says no; it is not the thing that decides.

#### The construction

Local boundary (one organization). (a) Every tool call an agent makes is a request to a kernel; the agent holds an Ed25519-signed capability token (subject, scope of server/tool/operations/constraints, invocation and monetary budgets, expiry, caveats) and never a tool handle. (b) The pure decision core is four functions, `verify_capability`, `resolve_matching_grants`, `evaluate`, `sign_receipt` in `chio-kernel-core` (no_std, clock and RNG as traits), reached from the shell through `ChioKernel::evaluate_portable_verdict` and `ChioKernel::build_and_sign_receipt`. Evaluation is total and denies on any failure: bad signature, time window, revoked token or revoked presented ancestor, out of scope, invalid DPoP or session anchor, exhausted budget, missing threshold approval. (c) A guard pipeline runs before and after dispatch; a deny or error from any guard dominates; an allow requires core authorization; custom guards run as fuel-metered WASM with advisory mode structurally non-blocking. (d) A budget hold is taken before the call and sealed into the receipt. (e) The kernel persists a signed receipt before returning allow (ReceiptBeforeAllow); the signer recomputes the content hash from the preimage and refuses on mismatch (WYSIWYS). Every terminal is a receipt: `Allow`, `Deny{reason,guard}`, `Cancelled`, `Incomplete`. Receipts are content-addressed, chained parent-to-child, and committed in RFC 6962 Merkle checkpoints; they verify offline from the kernel public key. (f) Receipt bodies carry a typed evidence class: `mediated_decision` with boundary `prevent` is the only kind that may carry a `Decision`; `trace_observation`/`detect_only` and `advisory_evaluation`/`advisory_only` reject a `Decision` at construction; reports may not relabel asserted or observed evidence as verified. (g) Delegation is a signed link carrying an attenuation proof whose parent-scope hash must equal the last chain link, a basis-point budget split checked against siblings, and the revocation epoch; the kernel rechecks the chain against a Merkle revocation oracle on every call; for recursive swarms a signed task graph with depth and fan-out ceilings, continuation tokens, and a pooled budget is verified before a child runs. (h) A post-admission drop guard makes a pre-dispatch abort release every reservation and, if a release fails, record a signed cleanup-fault receipt naming the possibly stuck hold ids; exactly one terminal receipt per committed evaluation. Cross-organization boundary. (i) A request classified as federated with no treaty context is denied. The request may carry only identifiers; `treaty_ref_from_request` rejects request-borne trust roots, peer directories, keys, revocation records, and dynamic trust bundles. (j) The receiver resolves treaty scope, ladder manifests and their intersection, continuation, lineage, bilateral invocation, leases, governance receipts, peer pins, and revocation epoch from its own stores; validators check schema, hashes, validity windows, participant sets, action class, consistency model, and required evidence. Ladder manifests are validated at load: unknown classes must default to deny, a destructive class below the destructive floor (receipt_backed) is rejected, a destructive class with CRDT consistency or no required evidence is rejected. (k) The strict DSSE verifier checks payload type, exactly two signatures, canonical bytes, statement and predicate type, one subject equal to the SHA-256 of the canonical receipt body, two distinct configured keys, then both Ed25519 signatures; the operational verifier then checks peer pins, fresh ladder manifests, revocation epoch, receipt resolution, args hash, policy verdict agreement, lease, governance receipt for receipt-backed classes, and every treaty binding reference. (l) The continuation is reserved during admission, consumed exactly once before dispatch, released on abort. (m) Accepted treaty material becomes a validated `VerifiedFederationTreatyMaterial` that receipt construction rechecks against the request before attaching treaty metadata to the signed receipt. Composition seams. (n) Monitors attach as guards (prevent) or advisory signals (observe); operators promote advisory to prevent by configuration; advisory can add denials, never allows. (o) Human oversight attaches as a signed threshold-approval proposal with a distinct eligible-key set and deadline; a governed operation without a valid approval token fails. (p) Law attaches through the treaty (signed scope, participants, action classes, validity, governance ladder), the governance receipt required for destructive classes, and the offline-verifiable receipt as evidence; verifier failures file as governance disputes.

#### Why it would be cited in ten years

Because it will be the paper that relocated the safety question. Alignment work asks how to make a model want the right thing; this paper shows that for actions with consequences the deciding party is the receiver, gives the end-to-end argument for why nothing upstream can substitute, and ships the reference construction people will compare against: receiver-owned resolution (evidence in the request, trust never), receipt before effect, evidence classes typed into the signed record so observation cannot pose as authorization, narrowing-only delegation, and a receiving kernel that replays the whole evidence graph before a foreign agent's call crosses an organization boundary. Later systems will cite it the way people cite Saltzer and Schroeder for complete mediation, the end-to-end paper for placement, and seL4 for the idea that the small boundary can carry the proof: as the place where "admission" became a first-class layer of agent safety with a formal and an implementation-linked boundary, and where the composition rule was stated plainly: alignment and monitors change the denial rate, the receiver decides, and the receipt is what the law reads.

#### Biggest risk

Admissible harm. A hostile safety reviewer will say the hard problem is deciding what is harmful, and that a kernel only enforces what the policy says: an in-scope exfiltration, a slow-roll harm spread across many individually admissible calls, or an operator who signs willingly under manipulation all pass with a perfect receipt, so the paper reduces to complete mediation plus signatures. The claim survives only if it is stated as exactly what the code delivers (no effect the receiver's policy did not admit, and no unrecorded effect) and if the composition argument is real: alignment lowers the rate at which admissible-harm calls are attempted, monitors add denials and can be promoted to prevent, threshold approval and destructive floors force a human or a second organization onto the irreversible classes, and receipts give law something to act on after the fact. The secondary risk is over-claiming reversibility, which the repo does not ship; if the paper says "reversible by construction" it will be rejected on the evidence. The third is complete mediation in real deployments (agent-native tools outside the kernel, MCP servers not wrapped), which the paper must scope rather than wave at.

#### Comparable foundational paper

Saltzer, Reed and Clark, "End-to-End Arguments in System Design" (1984), for the form of the argument: a check placed away from the endpoint that owns the relevant knowledge is an optimization, not a guarantee. The construction pattern is seL4 (Klein et al., 2009): a small enforcement boundary, an explicit assumption ledger, and a machine-checked core linked to the running code, with Saltzer and Schroeder (1975) supplying the principles the design derives (complete mediation, fail-safe defaults, least privilege).

#### Draft opening paragraph

A tool-using agent acts by asking something else to act on its behalf: a file system, a payment rail, another organization's service. Whether that request is safe is not a fact about the model that produced it. It is a fact about the policy, budget, and history of the party that will bear the effect, and only that party holds those facts. Today the request goes straight to the tool, and safety is sought upstream: in the training of the model, in a monitor that reads the transcript, in a signature that names the sender. None of these can be complete, because none of them has the receiver's state. We propose a different placement. Every action passes through a kernel owned by the receiver. The kernel checks the request against the receiver's own policy, trust roots, budget, and revocation state, and, across an organization boundary, against its own copy of the treaty and the prior receipts. If the check does not pass, the tool does not run. If it passes, a signed receipt of the verdict is written before the effect, and the receipt verifies offline with the receiver's public key. A model that is misaligned, a monitor that is fooled, or a foreign agent that presents a perfectly signed request can each be denied, and none can act unrecorded. Alignment and monitoring still matter, but they change how often the kernel says no, not whether the receiver decides.

### Admission Without Agreement

#### In one sentence

A federation of agent kernels can let actions cross organizational boundaries safely without any consensus protocol, because each receiving kernel admits a call from three facts it checks locally (two named keys signed the same bytes, its copy of the origin's signed revocation epoch is fresh, and the continuation edge from the parent receipt has not been spent), so the network only ever carries evidence and never carries a decision, safety holds in every partition, and liveness is a named assumption about delivery rather than a property of the protocol.

#### The problem

When an agent in organization A calls a tool in organization B, B has to decide whether to run it. Every existing answer routes that decision through shared state: a shared authorization service, a shared log, a shared ledger, or a replicated policy store, each of which needs some form of agreement between A and B to be correct, and each of which becomes unavailable or unsafe when the link between A and B is slow, lossy, or cut. The two hard sub-problems are revocation and causality. Revocation: when A revokes an agent's authority, B must stop honoring it, but B cannot see A's state, and any protocol that makes B wait for A is not partition tolerant while any protocol that lets B guess is not safe. Causality: a cross-organization call is a child of a specific parent receipt on A, and B must not run that child twice, or under a parent that did not happen, or for a different tool than the parent authorized, but B holds none of A's history. Consensus (Raft, PBFT) solves a different problem, replicating one state machine among peers who trust each other's liveness; it is the wrong tool between sovereign organizations that will never replicate each other's policy stores and will never accept each other's leader. P1 and P2 solved the local half (receiver-owned verification of one bilateral envelope) but say nothing about what happens across time and across a broken network: how revocation reaches the receiver, what the receiver does when it stops arriving, why a continuation cannot be replayed, and which of these properties are safety and which are liveness. That separation is the paper.

#### The insight

Authority does not need to be replicated; it only needs to be verified, and verification is local. Agreement is what you need when two parties must hold the same state; a receiving kernel never needs to hold A's state, it needs to check evidence about A's state that A cannot forge and that can only move in one direction. Three objects make every cross-organization admission a pure function of local data. First, the co-signed statement: two named keys over identical DSSE bytes, checked against pinned keys the receiver provisioned itself, so a valid statement proves "these two kernels committed to this action" without asking anyone. Second, the revocation epoch as a per-origin logical clock: the origin signs a monotone epoch root, the receiver installs a root only if its epoch strictly advances, and the receiver refuses to evaluate against a root older than a fixed freshness bound. This turns partition from a safety problem into an availability problem by construction: a cut link makes the receiver's clock go stale, and a stale clock denies. Third, the continuation token as an explicit happens-before edge carried as data: the parent receipt hash on A, a nonce, the target kernel and tool, and a window, consumed exactly once in the receiver's own store before dispatch. Lamport's insight was that causality can be carried in messages instead of being derived from a global clock; here the causal edge between a receipt on one sovereign kernel and an admission on another is carried in the message, and single-use consumption makes the edge a set-once fact in local state. Once these three are in place, every safety property (no admission after revocation is observable, no admission on stale authority, no continuation admitted twice, no action outside the treaty intersection) is a local invariant that holds regardless of what the network does, and the only thing left to ask of the network is that evidence eventually arrives. Consensus disappears from the safety argument entirely and reappears only as an optional threshold signature (FROST) for action classes that opt into it, which the ladder forbids under partition because a quorum cannot be assembled there by definition. Afterward this feels inevitable: IBC already showed that two chains can interoperate by each verifying the other's commitments with its own light client and no shared consensus; Chio is the same shape for organizations that have no chain, where the light client is a pinned key set plus a signed monotone epoch.

#### The construction

Participants and pins. Each kernel has an Ed25519 passport key (did:chio). A receiver holds a PeerPinSet mapping kernel_id to public key plus an accepted signed ladder-manifest reference (crates/trust/chio-federation/src/bilateral_verifier/state.rs, PinnedPeer, PeerPinSet). All trust material is receiver-provisioned; a request that carries a trust root, peer directory, signing key, or dynamic trust bundle is denied (treaty_ref_from_request in chio-runtime-core).

Treaty as a lattice join. Each participant publishes a signed governance ladder manifest: for each action class, a mode in the total order observation < guarded < receipt_backed < partition_contingency < maintenance, a destructive flag, a consistency_model in {crdt-commutative, totally-ordered, quorum-required}, a co_sign mode in {none, bilateral_if_cross_org, bilateral_required, n_of_m}, and required evidence classes. A TreatyScope names the participants, their manifest hashes, allowed action classes, and a validity window. compute_ladder_intersection (crates/trust/chio-federation/src/treaty.rs L208) checks freshness of scope and every manifest, requires exactly one manifest per participant with hashes matching the scope, then for each allowed class takes mode = maximum rank across participants, co_sign = maximum requirement, unions evidence_required, and rejects if consistency models differ, if destructive and mode < receipt_backed, or if destructive and crdt-commutative. The intersection's canonical SHA-256 is pinned in the receiver's store; evaluate_cross_boundary_admission (L361) rejects a request whose expected intersection hash differs, whose class is absent, or whose required evidence is not both present and verified. Amendments that lower any class require co-signatures from every active peer (spec/CHIO_LADDER.md section 8).

Revocation as a per-origin monotone signed clock. Each origin runs a revocation oracle (sparse Merkle over revoked subjects, crates/trust/chio-revocation-oracle), ticks epochs, and signs EpochRoot {epoch, root_hash, issued_at_unix_ms} with a pinned oracle key (SignedEpochRoot). Push: RevocationGossipPushQueue::enqueue_signed_root then flush_batches_at per subscribed peer. Pull: RevocationCatchupRequest {from_epoch, to_epoch} with span at most 4096; respond_to_catchup returns only the contiguous suffix it retains, never fabricates, and RevocationCatchupResponse::validate_response rejects any gap or non-increasing epoch. Receiver install: validate_envelope, verify the signature against the pinned signer, build a RevocationSnapshot {epoch, root_hash, issued_at, revoked set}, then RevocationView::install_if_newer, which is a compare-and-swap that succeeds only if candidate.epoch > installed.epoch and otherwise leaves the view unchanged. Evaluate: consult_revocation_view_at loads the snapshot; if now < issued_at or now - issued_at > max_staleness (500 ms default in chio-kernel; FreshnessConfig::fail_closed() is 0 in the oracle crate) the call is denied; otherwise every delegation-chain link and the leaf are checked against the revoked set. The bilateral verifier additionally requires both participant fingerprints active at the receiver's PinnedEpoch.epoch_height (cosign.rs step 9).

Continuation as a single-use causal edge. The origin issues a CrossKernelContinuation {continuation_id, source_kernel_id, target_kernel_id, parent_receipt_sha256, parent_session_anchor_sha256, capability_id, action_class_id, audience_tool, nonce, issued_at, expires_at}. The receiver validates schema, hash shapes, non-empty fields, and a non-empty window (validate_cross_kernel_continuation, chio-runtime-core treaty.rs L937), checks the source equals the request's federated origin and the audience equals the target tool, and rejects staleness before dispatch. On the admitted path, before dispatch, the hook calls consume_treaty_continuation(continuation_id, admission_id) (admission_hook.rs L836); the SQLite store executes INSERT OR IGNORE INTO runtime_consumed_treaty_continuations (continuation_id, admission_id) and returns chio_treaty_continuation_replay if zero rows were inserted (store/sqlite/admission_replay.rs L121). On any pre-dispatch denial or kernel abort the hook calls release_treaty_continuation for that admission_id only (L615). A ReceiptLineageStatement binds parent and child receipt digests to the continuation hash and the bilateral invocation id, so the child receipt on B carries the edge to the parent receipt on A.

Bilateral statement and co-sign. Statement: in-toto v1, predicateType chio.bilateral-cosign-invocation.v1, exactly one subject {name chio-receipt:<id>, digest = SHA-256 of the canonical receipt body}, predicate fields per spec/CHIO_BILATERAL_COSIGN_INVOCATION.md section 5 plus a 15-field treaty_binding_ref (treaty id and scope hash, intersection hash, admission-report hash, continuation hash, lineage hash, action class, consistency model, request and outcome hashes, local and remote receipt hashes, lease refs, governance refs, signer kernel ids). Co-sign flow (BilateralCoSigningProtocol): the tool-host kernel B signs the DSSE PAE bytes, sends DsseCoSigningRequest {pae_bytes, org_b_signature} to the origin A either in process (InProcessCoSigner) or over the iroh QUIC lane (IrohBilateralCoSigner, ALPN-separated, DirectoryGate rejects any endpoint not bound to an admitted kernel before a handler runs); A verifies B's signature against B's directory-bound key, signs the identical bytes, and returns. Receiver verification order at HEAD: payload type, two signatures, decode and canonical-bytes equality, statement and predicate types, predicate schema, one subject, subject name, distinct keys and keyids, fingerprints match pins, Ed25519 A, Ed25519 B, fresh ladder manifests, both peers active at the pinned epoch, receipt resolves and hashes match, args hash, both policy verdicts agree, lease unexpired at pinned now, governance receipt present for receipt_backed classes, treaty binding refs equal the receiver's expectations.

Hook order. Ordinary capability checks (signature, scope, attenuation, ancestor revocation, budget, DPoP) run first. Then: classify federated; parse identifiers only; resolve scope, intersection, continuation, lineage, invocation, receipts, leases, governance, pins, and epoch from receiver stores; run validators; run the strict verifier; consume the continuation; dispatch; construct the receipt through VerifiedFederationTreatyMaterial, which rechecks request, participants, tool, and hashes before attaching treaty metadata. Any failure before dispatch returns a named code and releases reservations.

Optional threshold. Action classes declared quorum-required use a FROST-aggregated signature over a domain-separated authorization body with roster, epoch, and slot checkpoints (crates/trust/chio-federation/src/frost.rs, verify_chio_bilateral_invocation_with_frost); this is threshold signing, not state replication, and the spec forbids it under partition_contingency.

#### What must be built or proven

1. The exposure-bound theorem. From StaleEvaluationDenied and NoAllowAfterRevokeDistributed derive and check a named invariant (for example RevokedExposureBounded) in formal/tla/DistributedRevocation.tla: if origin o revokes target x at o's clock t_r, then no authority a records an allow for x at a local time later than t_r + SkewBound + FreshnessBound, whether or not a and o are connected. Add a registered negative mutant (skip-freshness must violate it), and a Rust projection in distributed_revocation_refinement.rs. The connected-case bound (delivery latency plus freshness) stays conditional on ASSUME-GOSSIP-FAIRNESS-PARTITION-BOUND and must be stated as liveness. This theorem is what makes "partition-safe without consensus" a precise claim instead of a slogan.

2. Partition-contingency mode. spec/CHIO_LADDER.md 3.4 defines a staged contingency lease with blast_radius_cap, ttl_secs, and a mandatory reconciliation case at heal, but at HEAD partition_contingency is only rank 3 in both ladder_mode_rank functions; no Rust type, store path, hook branch, test, or corpus case names a partition. Do not describe it as shipped.

#### Why it would be cited in ten years

Because it will be the reference statement of how sovereign agent runtimes interoperate: not by sharing a log or a leader, but by each verifying the other's signed commitments locally, the way IBC zones verify each other with light clients and the way SDSI principals name each other locally. The specific pattern (pinned peer keys, a per-origin monotone signed revocation epoch with fail-closed freshness, single-use continuation edges carried in the receipt graph, and a lattice join of per-organization governance ladders) is small enough to reimplement in an afternoon and strong enough that its safety argument does not depend on the network at all. Ten years from now, when every organization runs a kernel between its agents and its tools, the question "how do two kernels admit each other's calls during a partition" will be answered by citing the exposure-bound theorem and the safety/liveness split in this paper, in the same way "how do two chains talk" is answered by citing IBC and "how do we order events without a global clock" is answered by citing Lamport. The paper will also be cited for what it refuses to claim: it names delivery fairness as an assumption, registers a rejected finite-evaluation bound as a counterexample witness, and keeps consensus out of the trusted base, which is the discipline later systems will be measured against.

#### Biggest risk

A hostile distributed-systems reviewer will say the "no consensus" property is vacuous because nothing is replicated, that deny-on-stale is a lease heartbeat known since Gray and Cheriton (1989) and Lamport's leases, and that the only genuinely distributed behavior the design promises (partition-contingency leases with a blast-radius cap and heal-time reconciliation, quorum-required classes forbidden under partition) is unimplemented at HEAD, leaving a re-titled P1 plus a TLA+ model whose liveness is assumed. The rebuttal exists but must be delivered, not asserted: the exposure-bound theorem checked by Apalache with a killing mutant, the live multi-kernel partition experiment with measured time-to-deny at most the freshness bound, an at-most-once continuation model under crash, per-origin views, and either a shipped minimal contingency mode or an explicit narrowing of the claim. A second risk is wording: the claim registry forbids "distributed revocation propagation is formally verified end to end" and any finite evaluation-count bound, so every liveness sentence must be conditional on ASSUME-GOSSIP-FAIRNESS-PARTITION-BOUND, and the paper must not inherit P2's false verifier ordering, its five-code taxonomy, or P1's mismatched benchmark environment.

#### Comparable foundational paper

IBC (Goes, "The Interblockchain Communication Protocol: An Overview", 2020, and the ICS specifications): two sovereign domains interoperate with no shared consensus because each verifies the other's commitments through its own light client and a receiver-side channel state machine with exactly-once packet semantics. Chio is the same architecture for organizations that have no chain: the light client is a pinned key set plus a signed monotone revocation epoch, the packet is the co-signed DSSE statement, the exactly-once channel state is the single-use continuation consumed in the receiver's store, and the connection handshake is the co-signed ladder intersection. Lamport 1978 is the second anchor for the causal-edge idea, and SPKI/SDSI for receiver-local naming of principals.

#### Draft opening paragraph

An agent in one organization calls a tool in another. Today the receiving organization either trusts a shared service to say the call is authorized, or it trusts the caller's word. Both put a third party between two kernels that could each check the facts themselves. A shared service is a single point of failure and a single point of compromise; the caller's word is worth nothing once its key leaks. What is needed is a way for the receiving kernel to decide, alone, from evidence it already holds, whether the call may cross its boundary, and to keep deciding correctly when the network between the two organizations is slow, lossy, or cut. We propose a federation in which no kernel ever agrees with another about global state. Each kernel pins the keys of its counterparties, receives signed revocation epochs that can only move forward, and admits a cross-organization call only when two named keys have signed the same bytes, the epoch it holds is fresh, and the continuation token that links the call to its parent receipt has never been used. Every one of these checks reads local state. The network carries evidence between kernels; it never carries a decision. When the network fails, a kernel's revocation view goes stale and it stops admitting the affected authority; it does not guess. We show that the safety of this construction holds in every partition, that the exposure after a revocation is bounded by clock skew plus a fixed freshness window, and that the only property the network is asked to provide is that evidence eventually arrives.

#### Outline

- 1. Introduction: a call between two organizations needs a decision no third party can make for them; we make it a local function of evidence and prove what survives a partition.
- 2. Why consensus is the wrong tool: replication needs agreement, authority needs verification; the two hard sub-problems are revocation across a broken link and causality across sovereign histories.
- 3. System model: kernels as sovereigns over their own tool boundary, receipts as the only shared vocabulary, treaties as pairwise contracts, the adversary controls the network and the request but not the receiver's stores or pinned keys.
- 4. Treaties as a lattice join: signed ladder manifests, per-class maximum mode, equal consistency model, destructive floor, downgrade needs every peer; Lean intersection and floor theorems; what Lean does not say yet.
- 5. Revocation as a per-origin logical clock: signed epoch roots, push and gap-free catch-up, install-if-newer, fail-closed freshness; the receiver's epoch is the only clock two organizations share.
- 6. Continuations as single-use causal edges: parent receipt, nonce, target, window; consume before dispatch, release on pre-dispatch denial only; lineage statements make the edge visible in both receipt graphs; at-most-once, not exactly-once.
- 7. Bilateral admission at the boundary: the receiver-owned verifier condensed from P1 with the HEAD ordering and the 16-code taxonomy; two keys prove two keys.
- 8. Safety under partition: the five invariants of DistributedRevocation.tla, the exposure-bound theorem, the rejected finite-evaluation witness, and the Rust trace projection that keeps the model honest.
- 9. Liveness as a named assumption: conditional eventual observation under weak-fair catch-up and heal, what ASSUME-GOSSIP-FAIRNESS-PARTITION-BOUND says and does not say, and why no delivery-step bound is claimed.
- 10. Transport that authenticates but never authorizes: iroh lanes, issuer-signed directory, endpoint-to-signer binding, all-or-nothing batches; the contracts crate is untouched by the transport.
- 11. Evaluation: negative corpus, revocation refinement traces, gossip latency, the live N-kernel partition experiment with time-to-deny, continuation replay across kernels, pre-dispatch denial cost, with retained environments that match the prose.
- 12. Related work: Lamport clocks and leases, Dynamo and CRDTs, Raft and PBFT, IBC, SPKI/SDSI, SCITT and in-toto, Cedar-style verified authorization; what each solves and why none is the receiver's problem.
- 13. Limitations: contingency mode scope, single-origin view, two keys are not two operators, checkpoints are local audit evidence and not a public append-only log, threshold classes are unavailable under partition by design.
- 14. Conclusion: safety is local and unconditional, liveness is delivery, agreement was never required.
