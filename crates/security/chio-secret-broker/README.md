# Chio Secret Broker

`chio-secret-broker` is the production credential-use boundary for brokered Chio tool calls. The agent, kernel, and tool server exchange credential references only. The daemon resolves encrypted credential material inside its process, injects it into the configured HTTPS provider request, and never returns the material over IPC.

## Supported production composition

The supported daemon composition is `chio-secret-brokerd` on Linux, using a private Unix-domain socket, the generic HTTPS executor backed by rustls and Web PKI roots, four broker-owned durable SQLite databases, one externally anchored enterprise migration ledger, and a live authenticated authority connection. Non-Unix daemon construction fails closed. Sealed key custody is implemented only on Linux and Android; the reviewed daemon deployment is Linux.

Production mode requires durable attempt and receipt stores, fresh liveness and revocation snapshots, capture-before-dispatch execution quotas, authenticated `RegisterAttempt` and `ReleaseAttempt` messages, and signed success or failure receipts. There is no direct-provider fallback when broker IPC, authority state, receipt persistence, or credential custody is unavailable.

## Privileged migration audit

`BrokerDaemonRuntime::audit_compare_outbound_request` supports a designated-runner migration check without entering the execution state machine. The underlying service operation is crate-private. The runtime verifies a short-lived `chio.broker-audit-runner-authorization.v1` artifact against the configured runner key and exact deployment, broker, tenant, provider, request, authority-domain, audit-id, source, and blinded-reference bindings. It then validates the production capability, caller proof, parent liveness, revocation snapshot, provider binding, request constraints, and destination. A threshold-governed approval for that exact runner artifact is durably consumed before credential materialization. Reuse is denied across process restarts.

The API does not resolve DNS, register an attempt, authorize or capture a hold, mutate quota state, retain a prepared dispatch, persist an execution receipt, or call the network transport. It uses the same exact HTTP/1.1 serializer as production after provider injection, then compares the projected head and body with the blinded legacy reference inside broker memory. The reference salt, comparison salt, broker credential, injected provider header, and exact request head are zeroized or dropped before return. The signed `chio.broker-audit-comparison.v1` artifact contains only request, runner, governance, complete authority-snapshot, trusted-configuration, source, and blinded projection commitments, the equality result, and explicit zero counts for network dispatch and accounting mutation. Neither salt is returned, so the retained artifact is not an offline credential verifier.

The migration primitive is not exposed through the ordinary tool-call IPC endpoint. Brokerd publishes a second, audit-only Unix socket in a dedicated service-owned directory. The socket has an exact service UID, runner GID, and `0660` mode, and every accepted stream is pinned to the configured runner UID and GID with Linux `SO_PEERCRED`. One connection carries exactly two canonical, bounded phases under absolute deadlines. Before connecting, the runner generates and retains a typed, salted commitment over its original reference bytes. The first phase transfers the salt, commitment, and exact reference into zeroizing broker buffers. The broker recomputes the commitment and returns a signed challenge containing exactly that value, a random session nonce, the complete runner authorization body, and expiration. The runner rejects any challenge that differs from its retained precommitment. The second phase must return that exact nonce and commitment with the designated runner signature and fresh governed admin envelope. The daemon returns one canonical evidence bundle containing the broker challenge, runner authorization, governed approvals, and signed comparison, then closes the session. Reusing either phase fails its fresh challenge binding or durable governed-approval consumption. Migration automation must possess both the pinned runner signing key and fresh threshold operator approvals. Ordinary tool-call authorization cannot invoke this path.

The public `audit` module supplies the domain-separated reference commitment function and the opaque `BrokerAuditReferencePrecommitment` type. The public `privileged_audit` module supplies strict frame helpers for the two requests and two responses. Its challenge reader verifies the trusted broker signature and exact retained precommitment before the runner can sign. After signing the challenge body, a runner computes the exact operator intent with `broker_audit_governed_intent_for_runner_authorization`, obtains fresh approvals, submits the commit, and verifies the returned bundle against the original request, retained precommitment, and independently configured trust context. Bundle accessors reconstruct the two verified authority exchanges and the zeroizing admin authorization required by `verify_broker_audit_evidence`.

## Trust roots and custody

The canonical `chio.secret-brokerd.runtime-config.v5` configuration pins the deployment and broker instance, designated audit runner key and logical identity, audit runner UID and GID, distinct privileged audit socket, audit deadlines and authorization lifetime, capability issuer, admission authority, broker signing identity, broker and parent audiences, provider adapter identity and version, tenant scope, governed admin approvers, trusted service UID, authorized IPC client UID, bounded normal IPC deadlines, and the exact provider-scoped enterprise migration posture. The posture requires sorted trusted transition signers, exact externally stored minimum heads, and enforced or legacy-removed stages for both `broker_credential_custody` and `broker_quota_enforcement`. Earlier versions are rejected because they cannot express all supported production boundaries. Startup opens the signed append-only SQLite ledger and binds the configured stages and posture digests to its exact current records before either socket is published. Every credential materialization, credential mutation, quota capture, and dispatch commitment re-reads those records. A promotion, posture change, restored prefix, file replacement, or storage failure denies until the process is rebuilt with matching external heads and configuration. Startup also requires the trusted service UID to equal the kernel-observed effective UID and the owner of the config, sealed keys, persistent databases and SQLite sidecars, socket directories, and broker sockets. The daemon applies absolute read and write budgets as soon as each stream is accepted and authenticates clients with Linux `SO_PEERCRED`. Client framing, authorization, disconnect, and backpressure faults are contained to that connection. Handler invariant, storage, and custody faults, deadline setup or maintenance faults, response encoding faults, and unexpected operating-system write errors reach daemon supervision as fatal service errors. The normal and privileged listeners run on separate supervised serving threads, so a bounded two-phase audit cannot stall ordinary tool traffic. The control-plane client separately pins the broker process identity (`pid`, `uid`, and `gid`), validates the socket type, owner, permissions, and stable inode, and pins the receipt-signing public key.

The supervisor passes distinct read-only, fully sealed, owner-checked 32-byte descriptors for the tenant master key and broker signing seed. The daemon consumes each descriptor once. Credential blobs are tenant-scoped and encrypted at rest; administrative provision, disable, and delete operations require threshold-governed authorization with durable replay protection. The plaintext credential exists transiently in broker memory and in the outbound provider request only.

Each admitted credential mutation ends in a signed
`chio.broker-admin-mutation-receipt.v1` record. Remote issue, revoke, and
status operations persist a signed `chio.broker-admin-control-receipt.v1`
record with the exact validated response digest and bounded response bytes.
An exact retry recovers the same durable operation and completion even after
the original approval expires; changing the intent or authorization fails
closed.

## Deployment and recovery

Run the daemon as a dedicated service identity. Supply a service-private canonical JSON configuration, absolute and distinct database paths, private socket directories, the two inherited sealed key descriptors, an externally anchored migration ledger and minimum heads, and a reachable authenticated authority socket. Brokerd adopts each distinct raw key descriptor exactly once, sets `CLOEXEC` on the adopted descriptor without reopening `/proc`, consumes the sealed key, and closes the descriptor before IPC readiness. Preserve the four broker databases together with the tenant master key and broker signing seed. Preserve and anchor the migration ledger independently so restoring a valid prefix cannot silently roll production back.

The endpoint acquires an exclusive, owner-checked, `NOFOLLOW` lifecycle lock at `<ipcSocketPath>.lifecycle.lock` before binding. Orderly shutdown and fatal serve errors drop the endpoint and unlink only the socket device and inode that the endpoint created, after revalidating its type, owner, and permissions. A supervisor handling uncatchable termination such as `SIGKILL` owns stale-socket recovery: while the daemon is stopped, acquire an exclusive lock on that same owner-checked regular file, verify the socket is a private socket owned by the configured service UID, unlink that exact verified identity, and then restart. Brokerd does not probe or automatically unlink an existing socket because it cannot safely distinguish stale state from an active pre-v2 daemon.

Startup connects to the authoritative hold service and drains every recoverable attempt page before binding the broker IPC socket. Permanently ambiguous `unknown_outcome` records remain non-dispatchable, while authoritative denied, reversed, held, and captured states converge through the durable attempt state machine using the original deterministic identifiers.

After restart, the daemon reopens encrypted credentials, attempt state, admin replay state, and signed receipt state. Exact registration, transition, and receipt retries are idempotent. Reconciliation classifies non-terminal attempts from durable dispatch evidence; ambiguous execution remains denied instead of being redispatched. Restoring databases with a different tenant key or signing identity fails custody or receipt verification.

## Residual risks

The operating-system service boundary remains trusted: a host principal able to inspect broker memory can recover plaintext credentials while they are in use. The selected upstream provider receives the injected credential, and transport security depends on rustls validation plus the configured destination constraints. SQLite durability depends on the host filesystem, and authority or receipt-store unavailability stops execution. Request, attempt, and receipt metadata remain observable even though credential bytes are excluded from those records and from diagnostics.
